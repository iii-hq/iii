# Filter conformance vectors

Shared vectors for the observer filter language
([`tech-specs/2026-10-13-observe/filters.md`](../../../tech-specs/2026-10-13-observe/filters.md)).

**Every implementation runs the full set in CI**: the engine and the Rust SDK
(`crates/iii-filter`), and the Node (shared with `iii-browser`), Python and Go
evaluators. A file is never skipped, and a case is never marked as expected to
fail. Changing the language means changing these files first.

| Path | Content | Run by |
|---|---|---|
| `*.json` | one valid filter and the documents it must match or not | every implementation |
| `invalid/*.json` | filters that must be rejected, with the error code | every implementation |
| `normalize/*.json` | filters and their normal form | the engine (`crates/iii-filter`); other implementations may check that each normal form compiles (Go does) |
| `diff/corpus.json` | differential corpus generated by the Rust evaluator, `{"runs":[{"seed":N,"cases":[{"filters","doc","expect"}]}]}`; not hand-written vectors, see [`diff/README.md`](diff/README.md) | the Node, Python and Go evaluators; `crates/iii-filter` checks it is up to date |

Runners glob `*.json`, `invalid/*.json` and `normalize/*.json` only; `diff/`
has its own shape and must not be read as vectors.

Schema checks (`INVALID_FILTER_PATH`, against a function's `request_format`
/ `response_format`) run in the engine only and have no vectors here; they
are tested in `crates/iii-filter/tests/schema_paths.rs`.

Expected results are written by hand from the spec. Do not regenerate them
from an implementation.

## Formats

Valid vectors, `<topic>.json`:

```json
{
  "description": "what the file covers",
  "filters": { "input.op": { "$in": ["insert", "update"] } },
  "cases": [
    { "doc": { "input": { "op": "insert" } }, "expect": true },
    { "doc": { "input": {} }, "expect": false, "note": "optional explanation" }
  ]
}
```

- The filter must be accepted.
- `doc` is `{ "input"?, "output"?, "error"?, "caller"?, "metadata"? }`. A
  missing key is an absent root; `null` is the value `null`. Other keys are
  ignored.
- An implementation should also evaluate the normal form, when it has one, and
  get the same results.

Invalid vectors, `invalid/<topic>.json`:

```json
{
  "description": "what the file covers",
  "cases": [ { "filters": { "input.op": "insert" }, "code": "INVALID_FILTER", "note": "literal shorthand" } ]
}
```

Normalize vectors, `normalize/<topic>.json`:

```json
{
  "description": "what the file covers",
  "cases": [ { "filters": { "input.a": { "$eq": 1 } }, "normalized": { "$and": [ { "input.a": { "$eq": 1 } } ] } } ]
}
```

Compare `normalized` as JSON values: object key order does not matter, array
order does.

### Reading the files

Documents hold integers beyond 2^53 (`9007199254740993`,
`18446744073709551615`) and spellings such as `1.0`, `-0.0`, `1e0` and
`2.00`. Every number is compared as an IEEE-754 double, so a parser that reads
them as doubles is fine. A parser that keeps exact integers (Python, Go with
`UseNumber`) must convert to a double before comparing. Booleans are not
numbers.

## Differential test

```sh
cargo run -p iii-filter --example diffgen -- --seed 1 --count 1000
```

This prints `{"seed":1,"cases":[{"filters":…,"doc":…,"expect":bool}]}`:
random valid filters (all operators, nesting up to the depth limit, `$any` in
both forms, escaped keys, index segments, numbers near the integer / float
boundaries) and documents built from them, with the Rust result. About half of
the cases match. The output is the same for the same seed. Filters are given
as generated, not normalized. Three runs of it are committed as
`diff/corpus.json`, which the Node, Python and Go evaluators replay.

## Rules every implementation must follow

These are the choices `filters.md` leaves open. The vectors pin them down.

### Grammar

- A filter is a JSON object. Anything else is `INVALID_FILTER`, `null`
  included: a protocol layer maps an absent `filters` to `{}` before parsing.
- A filter object holds paths, `$and`, `$or` and `$not`. Any other `$` key is
  `INVALID_FILTER`, value operators included (`{ "$eq": 1 }` needs a path).
- `$and` and `$or` take a **non-empty** array of filter objects. `[]` is
  `INVALID_FILTER`, as in MongoDB. `$not` takes a filter object. `{}` is
  allowed there (`{ "$not": {} }` matches nothing), and as a member of `$and`
  or `$or` (it matches everything).
- A path clause takes a non-empty operator object, whose keys are all value
  operators: `$eq`, `$ne`, `$in`, `$nin`, `$gt`, `$gte`, `$lt`, `$lte`,
  `$exists`, `$prefix`, `$any`. A literal, an empty `{}`, an object with a
  non-`$` key (literal shorthand), an unknown operator, or `$and` / `$or` /
  `$not` inside an operator object is `INVALID_FILTER`.
- Operands: `$eq` / `$ne` take any JSON. `$in` / `$nin` take an array of any
  JSON, empty allowed. `$gt` / `$gte` / `$lt` / `$lte` take a number or a
  string. `$exists` takes a boolean, `$prefix` a string.
- `$any` takes an object. When it is non-empty and every key is a value
  operator, it is an operator object applied to each element. Otherwise it is
  a filter over the element, whose paths all start at `@` (also under `$and`,
  `$or` and `$not`). `{ "$any": {} }` is the empty filter: any non-empty array
  matches. Mixing operators and paths is `INVALID_FILTER`.
- Numeric literals anywhere in a filter, nested inside `$eq` objects and
  arrays and `$in` items too, must satisfy `|n| <= 2^53` (9007199254740992).
  The rule is on the value, floats included (`1e16` is rejected), because
  JavaScript cannot tell `1e16` from `10000000000000000`. The integers in the
  invalid vectors (`2^53 + 2`, `2^54`) are exactly representable as doubles,
  so a parser that reads every number as a double still sees them beyond
  2^53; the floats (`1e16`, `-1e300`) are beyond it however they are read.
- An integer literal is judged on its exact value by an implementation that
  sees the JSON text: the engine rejects `9007199254740993`. A parser that
  reads doubles sees 2^53 there and accepts it, and an SDK holding that double
  sends the rounded value, which is valid. The engine, which validates at
  `observe`, is the authority, so no shared vector depends on the
  difference.
- A literal nests at most 32 arrays / objects (see Limits).

### Paths

- A path splits on unescaped `.`. `\.` is a literal dot and `\\` a literal
  backslash. Any other backslash sequence (`\@`, `\n`, `\ `) and a trailing
  backslash are `INVALID_FILTER`.
- An empty path or an empty segment (`input.`, `.input`, `input..a`) is
  `INVALID_FILTER`.
- The first segment is the root: `input`, `output`, `error`, `caller` or
  `metadata`, case-sensitive. `@` is a root only inside `$any`, where it is the
  only root allowed, and only as the whole first segment. After the root, `@`
  is an ordinary key.
- A path may be the root alone (`"error": { "$exists": true }`, `"@": {…}`).

### Limits

| Limit | Value | What counts |
|---|---|---|
| Depth | 8 | The top-level filter is at depth 1. Each `$or` member, `$not` operand and `$any` operand (both forms) is one level deeper than the object holding it. `$and` members stay at the depth of the object holding the `$and`. |
| Nodes | 64 | Each value operator key (`$eq` … `$any`, inside `$any` operator objects too) and each `$or` / `$not` counts 1. Paths and `$and` count 0. |
| `$in` / `$nin` | 256 items | Per array. |
| Path segments | 16 | Segments after the root: `input` plus 16 keys is the maximum, and the same after `@`. |
| Literal depth | 32 | Arrays / objects nested in one `$eq` / `$ne` operand or one `$in` / `$nin` item. A scalar is 0, `[1]` and `[]` are 1, `{"a": [1]}` is 2. The `$in` array itself does not count. Documents have no limit. |
| JSON depth | 120 | Arrays / objects nested in the whole filter value, `$and` wrappers and literals included (`{}` is 1, `{"input.a": {"$eq": 1}}` is 2). Applies to normal forms too; a valid filter's normal form stays far below it. |
| Encoded size | 8192 bytes | UTF-8 bytes (not string length) of the compact JSON encoding of the filter **as written**: no whitespace, non-ASCII not escaped, as `JSON.stringify` writes it. |

`$and` is free and transparent because normalizing adds `$and` wrappers: the
filter depth, node, item, segment and literal limits are defined so that
normalizing never increases them. The wrappers do add JSON depth, but the
normal form of a valid filter stays far below 120 (65 levels at most).

The encoded size is measured on the filter as written, never on its normal
form, which can be longer (`limit-size-8192-as-written.json`) or shorter
(`invalid/limit-size.json`). A worker compiling a normal form pushed by the
engine does not apply the size limit (Rust: `Filter::from_normalized`); every
other rule still applies. Number spellings differ across languages (`1.0`
against `1`), so a filter with float literals within a few bytes of the limit
can measure differently; the engine, which validates at `observe`, decides,
and the vectors stay clear of that case.

The literal depth and JSON depth limits keep every filter within the nesting
that JSON decoders accept by default (the engine's stops at 128 levels for a
whole message, and a filter sits a few levels inside it), and let
implementations validate without deep recursion. Since `$and` adds no filter
depth, only the JSON depth limit bounds a chain of `$and`s
(`limit-json-depth-120.json`, `invalid/limit-json-depth.json`).

Every limit fails with `INVALID_FILTER`, so the order of the checks only
decides the message. The Rust crate checks the encoded size first, then the
JSON depth (both without recursion), then the structure: filter depth,
nodes, `$in` items, path segments and literal depth as it meets them. A
literal nested 121 levels deep is therefore reported as too deep for the
JSON depth limit, one nested 33 levels inside a shallow filter as too deep for
the literal depth limit.

### Evaluation

- Path resolution: on an object, a segment is an own key; inherited
  properties do not exist (`constructor`, `toString` and `__proto__` are
  ordinary keys). On an array, only a canonical decimal segment (`0` or
  `[1-9][0-9]*`) within range selects an element: `01` is a key, never an
  index, so on an array it is absent, like `-1` and indexes beyond any
  length. Strings, numbers, booleans and `null` have no
  children: no `length`, no characters. A numeric segment on an object is a
  key.
- There is no implicit fan-out over arrays: `input.items.sku` on an array of
  items is absent. Use `$any`.
- Absent: only `$ne`, `$nin` and `$exists: false` match an absent path. `null`
  is a value: `$exists: true` matches it.
- Equality is deep. Numbers compare as doubles: `1 == 1.0`, `-0 == 0`, and a
  payload integer beyond 2^53 is first rounded to the nearest double
  (`9007199254740993` equals `9007199254740992`). Object key order is ignored,
  array order is not. There is no coercion between types: `0`, `false`,
  `null`, `""` and `"0"` all differ. Strings are equal when their code points
  are; there is no Unicode normalization.
- `$in` tests deep equality with each item; an array value is compared as a
  whole. `$in: []` matches nothing; `$nin: []` matches everything, absent
  included.
- Ordering: numbers against numbers as doubles, strings against strings by
  Unicode code point (UTF-8 byte order). This is **not** UTF-16 code unit
  order, which is what JavaScript `<` uses: `"😀" > "｡"` must hold. Any
  other pairing (mixed types, `null`, booleans, arrays, objects, absent) is
  false for all four operators.
- `$prefix` matches a string value that starts with the operand, code point
  by code point. `""` matches every string.
- `$any` matches an array value when some element satisfies every operator of
  the operator object, or the filter with `@` bound to that element. A nested
  `$any` binds `@` to its own element. An empty array, a non-array and an
  absent path are false.
- The operators of one operator object are ANDed. `$not` negates its whole
  filter, so it matches when the inner path is absent. `{}` matches every
  document.

### Normal form

Only the engine normalizes. Workers receive the normal form (in
`functionregistered` and `observeradded`) and compile it like any other
filter, without the encoded-size limit (see Limits).

- Every filter, nested ones included (in `$or`, `$not` and the filter form of
  `$any`), is `{}` or `{ "$and": [ … ] }` holding one clause per object.
- Explicit `$and`s are flattened into the filter that holds them.
- Clauses sort by key in byte order (`$not` < `$or` < paths), then by the
  compact JSON of their operand (as `serde_json` writes it, object keys
  sorted). Exact duplicates are dropped.
- `$or` members keep their order. `$in` / `$nin` items and literals are kept
  as written. `$ne` / `$nin` are not rewritten.
- Operator objects stay operator objects (also under `$any`), with their keys
  sorted. Paths are kept as written: with only two escapes, every key sequence
  has one spelling.
