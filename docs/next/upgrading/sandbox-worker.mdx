  "Move sandboxes and VM workers from the engine to the sandbox-libkrun worker, and clean up what
  0.25 left behind."

---

iii 0.26 moves the VM code out of the engine. `iii-worker` and `iii-init` are gone, and so is the
`iii-sandbox` worker you configured under `engine.workers`. The engine keeps `iii-sandbox` as a small
router: it serves the `sandbox::*` triggers and forwards every call to a sandbox adapter. The
`sandbox-libkrun` worker is that adapter. It runs the VMs, it comes from the worker registry, and
Compose installs it when a project needs it.

Consumers keep calling `sandbox::*` in the `default` namespace, and no existing request field,
response field, or S-code changed. The `sandbox::exec` and `sandbox::run` replies gain two keys,
`stdout_truncated` and `stderr_truncated` (contract 1.1, see
[Sandboxes](../creating-workers/sandboxes#lifecycle)). What changes is where you configure sandboxes
and where their state is kept. Work through the sections that apply to your setup.

## What moved

| 0.25 | 0.26 |
| --- | --- |
| `engine.workers.iii-sandbox` | `engine.sandbox`, and `containers.sandbox-libkrun.config_override` for the settings |
| `iii-worker` boots bundle and `runtime.base_image` VMs | `sandbox-libkrun` boots them through Compose |
| `iii-worker` and `iii-init` in `~/.local/bin` | Not installed or updated by `iii update` |
| VM state in `<state dir>/vm/<key>/` | VM state in `~/.iii/sandbox/workers/<vm_id>/` |
| Error `docs_url` on GitHub | [Sandboxes](../creating-workers/sandboxes), where every S-code has an entry |

## Replace `engine.workers.iii-sandbox`

A compose file that still declares `iii-sandbox` under `engine.workers` fails `iii compose --up`
with `SANDBOX_CONFIG_MOVED`. The error prints the replacement with your old block filled in:

```yaml worker-compose.yaml
containers:
  sandbox-libkrun:
    worker: package://sandbox-libkrun
    version: '^1'
    config_override:
      image_allowlist:
      - python
      - node
```

Delete the `iii-sandbox` entry, add that container, and keep the keys you had (`image_allowlist`,
`custom_images`, the `default_*` limits, and the rest): they are the same under
`config_override`. You declared the container, so Compose never removes it.

`engine.sandbox.adapter` names the adapter's function prefix and defaults to `sandbox-libkrun`, so you
can leave the section out. `engine.sandbox.namespace` names the namespace the adapter runs in and
defaults to the project's namespace. See [Compose](../using-iii/compose#engine-fields).

## Re-enter stored configuration

Compose does not move a configuration entry that you stored under `iii-sandbox`, from the console or
with `configuration::set`. Read it in its template form:

```bash
iii trigger configuration::get --json '{"id": "iii-sandbox", "raw": true}'
```

Copy the keys it prints into the `config_override` of the `sandbox-libkrun` container, as in the
previous section. Do not store them under the adapter's id, `<namespace>-sandbox-libkrun`: Compose
sets that entry in memory at each start, from the package defaults and `config_override`, and
storing it with `configuration::set` fails with `NOT_REGISTERED`. A running project reads the
edited file on `compose::restart` without a `worker` argument. Check the adapter before you delete
the old entry.
See [Configuration precedence](../using-iii/compose#configuration-precedence).

## Engines that no Compose file manages

Compose binds the router to `sandbox-libkrun` only on an engine it owns. An engine started directly
with `iii --config config.yaml`, with no `engine:` section in any Compose file, has no adapter bound,
and its `sandbox::*` calls fail with S303. Set the top-level `sandbox:` section in that engine's
config:

```yaml config.yaml
sandbox:
  adapter: sandbox-libkrun
  namespace: default
```

`namespace` is where the adapter runs, `default` when omitted. Install the adapter in a Compose
project in that namespace with `iii trigger compose::add worker=iii-sandbox`. Until it runs, calls
fail with S301, which names the namespace. Leaving an `iii-sandbox` entry in the list-shaped
`config.yaml` fails startup with `UNSUPPORTED_CONFIG_WORKERS`.

## Frozen installs

`iii compose --up --frozen` and `iii compose build --frozen` never edit the compose file. A project
that needs the adapter (it sets `engine.sandbox` for its own namespace or has a VM worker) but does
not declare it fails with `SANDBOX_ADAPTER_NOT_DECLARED`. Run `iii compose --up` once without
`--frozen`, so Compose writes the container and the lock, then commit both.

## VM workers from `path://`

The adapter only mounts host directories under two roots: the compose file's directory and
Compose's package cache (`~/.iii/compose/packages`, or `$III_COMPOSE_STATE_DIR/packages`). A
`path://` worker with `runtime.base_image` anywhere else fails with S501, which names the
roots. Move the worker under the compose directory.

## Supported hosts

`sandbox-libkrun` is built for three targets:

- macOS on Apple Silicon (`aarch64-apple-darwin`)
- Linux with glibc on x86_64 (`x86_64-unknown-linux-gnu`)
- Linux with glibc on aarch64 (`aarch64-unknown-linux-gnu`)

On Linux, the user who runs Compose needs read and write access to `/dev/kvm`, and `libcap-ng0` must
be installed. A project that needs the adapter on a musl Linux or Intel Mac host fails with
`UNSUPPORTED_PLATFORM`. 0.25 shipped `iii-worker` for musl Linux, so Alpine hosts lose bundle and
sandbox support in 0.26. Windows has no VM: a bundle worker there still fails with
`BUNDLE_NEEDS_A_VM`.

## Upgrade the binary

The first `iii update` from 0.25 still runs 0.25 code. It installs 0.26 to `~/.local/bin/iii`,
then prints `Release asset not found for platform <target>: iii-init` (and the same for
`iii-worker`) and exits 1. That is expected: the 0.26 release has neither asset.

Check that your shell now runs 0.26 with `iii --version`. If it still prints 0.25, the `iii` on your
`PATH` (`command -v iii`) is not `~/.local/bin/iii`, for example a Homebrew install in
`/opt/homebrew/bin`. Running `iii update` from it only repeats the errors above. Upgrade that copy
with `brew upgrade iii`, or remove it and put `~/.local/bin` on your `PATH`.

Once `iii --version` prints 0.26, run `iii update` again. It finishes cleanly and lists the leftover
binaries. It deletes nothing, so remove them yourself:

```bash
rm ~/.local/bin/iii-worker ~/.local/bin/iii-init
```

To roll back, `VERSION=0.25.0` with the install script installs only `iii`: the script no longer
fetches `iii-worker` or `iii-init` for any release. Download `iii-worker-<target>.tar.gz` and
`iii-init-<target>.tar.gz` for your host from the
[iii/v0.25.0 release](https://github.com/iii-hq/iii/releases/tag/iii/v0.25.0) and put both
binaries next to `iii` in `~/.local/bin`. Without them, 0.25 runs no VM workers and no sandbox.

Errors from a 0.25.x engine carry a `docs_url` that points to
`crates/iii-worker/src/sandbox_daemon/README.md` on GitHub. That file is gone. The S-codes now live
on [Sandboxes](../creating-workers/sandboxes).

## Clean up VM state

0.25 kept each VM worker's state in `<state dir>/vm/<key>/`, where `<state dir>` is
`<compose-dir>/.iii/compose/<namespace>/`, or the directory under `$III_COMPOSE_STATE_DIR` when you
set it. Nothing reads these directories now, so delete them. The first boot of each VM in 0.26
starts from fresh state and reinstalls its dependencies.

`iii-worker` also left the paths below. `sandbox-libkrun` reads none of them, so delete them too:

- `~/.iii/managed/`, the state of each VM worker it ran.
- `~/.iii/workers/` and `~/.iii/workers-bundle/`, the binary and bundle workers it installed.
- `~/.iii/cache/bundles/`, the bundle archives it downloaded.
- `~/.iii/logs/` and `~/.iii/pids/`, its worker logs and PID files.
- `~/.iii/lib/iii-init`.
- `~/.iii/rootfs/` and `~/.iii/images/`, left by releases before 0.25.

Keep the rest of `~/.iii/lib/`: `sandbox-libkrun` still loads `libkrunfw` from there. Keep the rest
of `~/.iii/cache/` too. It holds pulled images, where 0.25 put them, so those are not pulled again.

The state is now in `~/.iii/sandbox/workers/<vm_id>/`, owned by the adapter. Compose deletes it
when you remove the VM container. Two cases leave it behind for you to delete by hand:

- You removed a VM container while the adapter was down, for example after `iii compose down`. The
  warning names the container, the adapter, and the `vm_id`, and says where the state stays.
- You moved or renamed the project directory, or changed `III_COMPOSE_STATE_DIR`. Every VM then
  starts from fresh state, and the directories of the old location remain in
  `~/.iii/sandbox/workers/`.
