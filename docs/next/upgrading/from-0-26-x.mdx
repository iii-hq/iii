iii 0.27 changes every SDK: TypeScript (Node and browser), Python, Rust, and Go. Streaming between
functions no longer has an API of its own: a stream is a value of a call. Put a file, a readable, or
a generator in a payload or a result, and the function on the other side receives an `InputStream`
to read; put a writable or a file to create there, and it receives an `OutputStream` to write.

- **The Channels API is removed from all five SDKs.** `createChannel`, `ChannelReader`,
  `ChannelWriter`, `readerRef`, and `writerRef` (Python `create_channel`, `create_channel_async`,
  `reader_ref`, `writer_ref`; Rust `iii_sdk::helpers::create_channel` and `iii_sdk::channel::*`; Go
  `CreateChannel`, `Channel`, `ChannelReader`, `ChannelWriter`, `OpenReader`, `OpenWriter`, and
  `ExtractChannelRefs`; the browser's `createChannel`, `Channel`, `ChannelReader`, and
  `ChannelWriter`) give way to `InputStream` and `OutputStream`, and to `iii.pipe()` for an explicit
  pipe. This is a breaking change with no deprecated aliases.
- **The wire is unchanged.** A 0.26 engine serves 0.27 SDKs, and a ref has the same JSON in every
  SDK, so workers on 0.26 and 0.27 SDKs work together in one project. The 0.27 engine changes only
  the text of its `payload_too_large` errors, which now link to
  [Streaming / Payload size](../creating-workers/streaming#payload-size), as the errors of every
  0.27 SDK do.

## Before you upgrade

### Who needs to migrate

Only the workers whose SDK you upgrade to 0.27, and in them only the code that uses channels. A
project that keeps its SDKs on 0.26 needs no change, an engine upgrade alone changes nothing for
streaming, and you can move one worker at a time.

### Compatibility

| SDK          | On a 0.26 engine                                                                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **0.26 SDK** | Unchanged.                                                                                                                                                  |
| **0.27 SDK** | Everything works. Streams use `engine::channels::create` and the `/ws/channels` sockets, which the 0.26 engine already serves: no engine upgrade is needed. |

### Mixed fleets

A ref is the same JSON whichever SDK sent it, so a stream crosses SDK versions. What the receiving
worker gets depends on its SDK:

| A stream or a ref sent | Reaches a 0.27 worker as              | Reaches a 0.26 TypeScript, Python, or browser worker as | Reaches a 0.26 Go or Rust worker as |
| ---------------------- | ------------------------------------- | ------------------------------------------------------- | ----------------------------------- |
| in a call payload      | an `InputStream` or an `OutputStream` | a `ChannelReader` or a `ChannelWriter`                  | the ref JSON                        |
| in a function's result | an `InputStream` or an `OutputStream` | the ref JSON                                            | the ref JSON                        |

The 0.27 lifecycle rules apply on the 0.27 side only. A handler on a 0.26 SDK that receives a writer
still has to close it, and a 0.27 caller that passed it a sink waits until it does: its call
resolves only after the sink has received the whole stream. If the 0.26 handler never opens the
writer, the call fails with `TIMEOUT` when its timeout expires, and the SDK aborts the sink.

A 0.26 TypeScript or Python writer that closes without writing anything never opens its socket, so
its reader, on any SDK version, waits until the engine expires the pipe. This is 0.26 behavior: a
0.27 writer opens the socket to close it, so its reader sees an empty stream at once. Upgrade the
writing side to fix it.

### Find what to change

Search each worker for the removed APIs. A few hits, such as `sendMessage` on another library's
socket, may be unrelated:


The SDK also detects streams in what it sends and turns refs back into streams in what it receives,
in handler input and, new in 0.27, in call results. See [Streaming](../creating-workers/streaming)
for the full API.

## Send a stream

Put the source in the payload. The SDK creates the pipe, sends the ref, and pumps the data while the
call runs, so the caller no longer writes a channel next to the call. The handler reads the field
the same way as before, without `.stream` in TypeScript. The payload field keeps its name: it is
your function's contract.

<Tabs>
  <Tab title="Node / TypeScript">
    **Before (0.26)**

    ```typescript
    import { createReadStream } from "node:fs";
    import type { ChannelReader } from "iii-sdk/channel";
    import { createChannel } from "iii-sdk/helpers";

    // Caller
    const channel = await createChannel(worker);
    createReadStream("report.csv").pipe(channel.writer.stream);
    const result = await worker.call({
      function_id: "files::process",
      payload: { filename: "report.csv", reader: channel.readerRef },
    });

    // Handler
    worker.registerFunction("files::process", async (input: { reader: ChannelReader }) => {
      let bytes = 0;
      for await (const chunk of input.reader.stream) bytes += chunk.length;
      return { bytes };
    });
    ```

    **After (0.27)**

    ```typescript
    import { createReadStream } from "node:fs";
    import type { InputStream } from "iii-sdk";

    // Caller
    const result = await worker.call({
      function_id: "files::process",
      payload: { filename: "report.csv", reader: createReadStream("report.csv") },
    });

    // Handler
    worker.registerFunction("files::process", async (input: { reader: InputStream }) => {
      let bytes = 0;
      for await (const chunk of input.reader) bytes += chunk.length;
      return { bytes };
    });
    ```

## Return a stream

In 0.26, refs in a result were not turned into readers, so a function that produced a stream needed
its caller to create a channel and pass a `writerRef` in. In 0.27 the function returns the stream
and the caller reads it from the result. The caller no longer passes a writer, so this changes the
function's payload: move its callers in the same change. When the caller has a place for the bytes,
such as a file, [pass a sink](#write-into-the-callers-sink) instead.

<Tabs>
  <Tab title="Node / TypeScript">
    **Before (0.26)**

    ```typescript
    import { once } from "node:events";
    import type { ChannelWriter } from "iii-sdk/channel";
    import { createChannel } from "iii-sdk/helpers";

    // Caller: create the channel and pass the writer ref in
    const channel = await createChannel(worker);
    const done = worker.call({
      function_id: "reports::export",
      payload: { report_id: "r-42", writer: channel.writerRef },
    });
    done.catch(() => {});
    for await (const chunk of channel.reader.stream) render(chunk);
    await done;

    // Handler: write into the caller's channel
    worker.registerFunction(
      "reports::export",
      async (input: { report_id: string; writer: ChannelWriter }) => {
        for await (const row of db.rows(input.report_id)) {
          if (!input.writer.stream.write(`${row.id},${row.total}\n`)) {
            await once(input.writer.stream, "drain");
          }
        }
        input.writer.stream.end();
        return { ok: true };
      },
    );
    ```

    **After (0.27)**

    ```typescript
    import type { InputStream } from "iii-sdk";

    async function* csvLines(reportId: string) {
      for await (const row of db.rows(reportId)) yield `${row.id},${row.total}\n`;
    }

    // Handler: return the stream
    worker.registerFunction("reports::export", async (input: { report_id: string }) => ({
      csv: csvLines(input.report_id),
    }));

    // Caller: the field arrives as an InputStream
    const { csv }: { csv: InputStream } = await worker.call({
      function_id: "reports::export",
      payload: { report_id: "r-42" },
    });
    for await (const line of csv.lines()) render(line);
    ```

## HTTP `request_body` and `response`

The HTTP worker still passes a route's request body and response as refs in `request_body` and
`response`, and it reads the status and the headers from the same JSON messages. Only their SDK
types change: `request_body` is an `InputStream` and `response` is an `OutputStream`. The
`request_body` of the TypeScript `HttpRequest` and `StreamRequest` types and of the Python
`StreamRequest` is an `InputStream` too. In Go, the `RequestBody` of `iiihttp.Request`,
`iiihttp.InternalRequest`, and `iiihttp.StreamRequest` is an `*iii.InputStream`, and
`InternalRequest.Response` is an `*iii.OutputStream`.

### Streaming response helpers

The `StreamResponse` helpers (the `res` of the TypeScript `http()` wrapper, of the Python
`StreamResponse`, and of the Go `iiihttp.Wrap`) wrap the `OutputStream` now. In TypeScript and
Python, every method that writes is asynchronous:

| 0.26                                                                 | 0.27                                                                               |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| TypeScript: `res.status(code)`, `res.headers(h)` returned nothing    | `await res.status(code)`, `await res.headers(h)`                                   |
| TypeScript: `res.stream.write(chunk)`, `res.close()`                 | `await res.write(chunk)`, `await res.close()` (`res.stream` stays, a `Writable`)   |
| Python: `res.stream` (a writable wrapper), `res.close()`             | `await res.write(data)`, `await res.close()`; `res.stream` is removed              |
| Python: `res.writer` was a `ChannelWriter`                           | `res.writer` is the `OutputStream`                                                 |
| Go: `iiihttp.Wrap(client, fn)`                                       | `iiihttp.Wrap(fn)`: the request's streams carry their client                       |
| Go: `iiihttp.NewStreamResponse(ctx, *iii.ChannelWriter)`             | `iiihttp.NewStreamResponse(ctx, *iii.OutputStream)`, and `res.Stream()` returns it |
| Go: a write after `res.Close()` returned `iiihttp.ErrResponseClosed` | it fails with an `*iii.InvocationError` with the code `iii.CodeStreamClosed`       |

In Go, `Status`, `Headers`, `Write`, and `Close` keep their signatures. `Wrap` closes the response
when the handler returns and aborts it when the handler fails, as before:

**Before (0.26)**

```go

	}
	_, err := io.Copy(res, req)
	return nil, err
}))
```


## Abort

In 0.26 each SDK aborted differently: Node with `writer.stream.destroy()` and no argument, Rust by
dropping the writer without `close()`, Go with a `Close()` after a failed `Write`, and Python and
the browser had no abort call. In 0.27 the SDK aborts for you in the common cases, and
`abort(reason)` is one call everywhere:

- A source the SDK pumps (a generator, a readable, a file) that fails aborts its stream.
- A handler that throws aborts every received `OutputStream` it has written to.
- `await output.abort(reason)` aborts on purpose. If the stream's socket never opened, it opens it
  first, so the reader always learns of the failure.

A handler that throws before it touched a received `OutputStream` leaves that stream alone, as in
0.26: the caller learns of the failure from the call's error.

The reader gets a typed error after the data that was already sent.

<Tabs>
  <Tab title="Node / TypeScript">
    **Before (0.26)**

    ```typescript

      for await (const page of renderPages(id)) input.out.stream.write(page);
    } catch (err) {
      input.out.stream.destroy(); // no argument: destroy(err) crashes the worker
      throw err;
    }
    input.out.stream.end();

    // Reader: the stream emits 'error', so the loop throws
    for await (const chunk of channel.reader.stream) save(chunk);
    ```

    **After (0.27)**


    ```go
    if errors.As(err, &closeErr) {
    	discard()
    }
    ```

    **After (0.27)**

    ```go
    // Writer: returning an error aborts Out; Out.Abort(reason) aborts on purpose
    for _, page := range pages {
    	if err := req.Out.Write(ctx, page); err != nil {
    		return nil, err
    	}
    }

    // Reader
    data, err := body.ReadAll(ctx)
    var streamErr *iii.InvocationError
    if errors.As(err, &streamErr) && streamErr.Code == iii.CodeStreamAborted {
    	discard()
    }
    ```

  </Tab>
</Tabs>

The reader's `reason` is the engine's description of the close, such as
`channel writer aborted: closed with code 1011`: the engine does not relay the writer's own reason.
Report the cause in the call's error or result. A caller that passed a sink gets the abort as its
call's error, with the code `STREAM_ABORTED`, even when the function returned.

## Ref helpers move to the protocol module

The SDK now finds refs and turns them into streams, so most code that called `extractChannelRefs` or
`isChannelRef` can drop it. Code that still works with the raw ref JSON, such as a router that
inspects payloads, imports the helpers from the low-level protocol module:

| 0.26                                                                                                        | 0.27                                                                                                         |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `import { extractChannelRefs, isChannelRef, ChannelDirection, ChannelItem } from "iii-sdk/helpers"`         | `import { extractChannelRefs, isChannelRef, ChannelDirection, ChannelItem } from "iii-sdk/protocol"`         |
| `import type { StreamChannelRef } from "iii-sdk/channel"`                                                   | `import type { StreamChannelRef } from "iii-sdk/protocol"`                                                   |
| `from iii.helpers import extract_channel_refs, is_channel_ref, ChannelDirection, ChannelItem`               | `from iii.protocol import extract_channel_refs, is_channel_ref, ChannelDirection, ChannelItem`               |
| `from iii.channel import StreamChannelRef`                                                                  | `from iii.protocol import StreamChannelRef`                                                                  |
| `use iii_sdk::helpers::{extract_channel_refs, is_channel_ref, ChannelDirection, ChannelItem};`              | `use iii_sdk::protocol::{extract_channel_refs, is_channel_ref, ChannelDirection, ChannelItem};`              |
| `use iii_sdk::channel::StreamChannelRef;`                                                                   | `use iii_sdk::protocol::StreamChannelRef;`                                                                   |
| `import { extractChannelRefs, isChannelRef, ChannelDirection, ChannelItem } from "iii-browser-sdk/helpers"` | `import { extractChannelRefs, isChannelRef, ChannelDirection, ChannelItem } from "iii-browser-sdk/protocol"` |
| `import type { StreamChannelRef } from "iii-browser-sdk"`                                                   | `import type { StreamChannelRef } from "iii-browser-sdk/protocol"`                                           |

In Go, `iii.StreamChannelRef` and `iii.ChannelDirection` stay in package `iii`, and
`iii.ExtractChannelRefs` is removed: unmarshal the raw ref JSON into an `iii.StreamChannelRef`.

The helpers see refs as JSON. A handler on a 0.27 SDK receives streams, not refs, so call them on
the raw JSON you hold, such as a value read from storage.

## `createChannel` to `iii.pipe()`

Most channels become a value in the payload or the result, as above. Keep an explicit pipe when the
stream has to exist before its data, when it goes to a call made later, or for a two-way session
(two pipes). `iii.pipe()` returns its two ends, `input` and `output`; put the end the other side
uses in the payload, where 0.26 code put a ref.

<Tabs>
  <Tab title="Node / TypeScript">
    **Before (0.26)**

    ```typescript
    import { createChannel } from "iii-sdk/helpers";

    const channel = await createChannel(worker, 64);
    const done = worker.call({
      function_id: "llm::complete",
      payload: { prompt, tokens: channel.writerRef },
    });
    channel.reader.onMessage((msg) => print(JSON.parse(msg).token));
    await channel.reader.readAll();
    await done;
    ```

    **After (0.27)**

    ```typescript
    const { input, output } = await worker.pipe({ bufferSize: 64 });
    const done = worker.call({
      function_id: "llm::complete",
      payload: { prompt, tokens: output },
    });
    done.catch(() => {});
    for await (const { token } of input.messages<{ token: string }>()) print(token);
    await done;
    ```

  </Tab>
  <Tab title="Python">
    **Before (0.26)**

    ```python
    from iii.helpers import create_channel_async

    channel = await create_channel_async(worker)
    payload = {"prompt": prompt, "tokens": channel.writer_ref.model_dump()}
    ```

    **After (0.27)**

    ```python
    pipe = await worker.pipe_async()  # worker.pipe() outside asyncio
    payload = {"prompt": prompt, "tokens": pipe.output}
    async for message in pipe.input.messages():
        print(message["token"], end="")
    ```

  </Tab>
  <Tab title="Rust">
    **Before (0.26)**

    ```rust
    use iii_sdk::helpers::create_channel;

    let channel = create_channel(&worker, None).await?;
    let payload = json!({ "prompt": prompt, "tokens": channel.writer_ref });
    ```

    **After (0.27)**

    ```rust
    let pipe = worker.pipe().await?;
    let payload = json!({ "prompt": prompt, "tokens": pipe.output });
    let mut messages = pipe.input.messages::<Token>();
    ```

  </Tab>
  <Tab title="Go">
    **Before (0.26)**

    ```go
    channel, err := worker.CreateChannel(ctx, nil)
    if err != nil {
    	return err
    }
    payload, err := json.Marshal(map[string]any{"prompt": prompt, "tokens": channel.WriterRef})
    ```

    **After (0.27)**

    ```go
    input, output, err := worker.Pipe(ctx)
    if err != nil {
    	return err
    }
    payload, err := json.Marshal(map[string]any{"prompt": prompt, "tokens": output})
    if err != nil {
    	return err
    }
    messages := input.Messages(ctx)
    ```

  </Tab>
</Tabs>

| 0.26 channel                     | 0.27 pipe                        |
| -------------------------------- | -------------------------------- |
| `channel.writer`                 | `pipe.output`, an `OutputStream` |
| `channel.reader`                 | `pipe.input`, an `InputStream`   |
| `channel.readerRef` in a payload | `pipe.input` in the payload      |
| `channel.writerRef` in a payload | `pipe.output` in the payload     |

In Go, `client.Pipe(ctx)` returns the two ends as `(input, output, err)`: `channel.Writer` becomes
`output`, `channel.Reader` becomes `input`, and the ends go in the payload where `channel.ReaderRef`
and `channel.WriterRef` went. In the browser, `createChannel(worker, bufferSize)` becomes
`worker.pipe({ bufferSize })`.

The worker that calls `pipe()` owns the pipe, as with `createChannel`: keep it connected until the
other side has attached.

## The browser SDK

The browser SDK follows the TypeScript API, with Web streams only. A `File` or a `Blob` from an
`<input type="file">`, a `ReadableStream` such as `response.body` of a `fetch`, and an async
generator are sources. A `WritableStream`, such as the one a File System Access handle returns from
`createWritable()`, is a sink.

Send a file from a page:

**Before (0.26)**

```typescript
import { createChannel } from "iii-browser-sdk/helpers";

// Caller: write the file into the channel while the call reads it
const channel = await createChannel(worker);
const call = worker.call({
  function_id: "files::process",
  payload: { filename: file.name, reader: channel.readerRef },
});
channel.writer.sendBinary(new Uint8Array(await file.arrayBuffer()));
channel.writer.close();
const result = await call;
```

**After (0.27)**

```typescript
// Caller: the File is the stream
const result = await worker.call({
  function_id: "files::process",
  payload: { filename: file.name, reader: file },
});
```

Read a stream that a function returns:

**Before (0.26)**

```typescript
import { createChannel } from "iii-browser-sdk/helpers";

// Caller: pass the writer ref in, read the other end
const channel = await createChannel(worker);
const call = worker.call({
  function_id: "reports::export",
  payload: { report_id: "r-42", writer: channel.writerRef },
});
const csv = new TextDecoder().decode(await channel.reader.readAll());
await call;
for (const line of csv.split("\n")) if (line) render(line);
```

**After (0.27)**

```typescript
import type { InputStream } from "iii-browser-sdk";

// Caller: the field arrives as an InputStream
const { csv }: { csv: InputStream } = await worker.call({
  function_id: "reports::export",
  payload: { report_id: "r-42" },
});
for await (const line of csv.lines()) render(line);
```

There is no `toReadable()` or `toWritable()` in the browser: `toWebStream()` returns the Web stream
of an `InputStream` or an `OutputStream`. `abort(reason)` closes the stream's socket with code 4011,
because a browser can only send 1000 or a code from 3000 to 4999. The engine treats it as an abort,
so a reader on any 0.27 SDK gets `STREAM_ABORTED`, with the reason `channel writer aborted: closed
with code 4011`.

## Behavior changes

Beyond the renamed API, these rules are new for a worker on a 0.27 SDK:

- **A received `OutputStream` is closed when the handler returns, and aborted when it throws.** A
  0.26 handler that returned and kept writing in the background calls `keepOpen()` (Python and Rust
  `keep_open()`, Go `KeepOpen()`) first, and then closes or aborts the stream itself. A stream the
  handler never touched is closed as well when it returns, except in a call through an observer (an
  HTTP route, for example), where it is closed only when the handler returns nothing.
- **A received `InputStream` that the handler started reading and did not finish is cancelled when
  the handler returns.** Finish reading before returning: a read still running after it, in a
  background task for example, fails with `STREAM_CLOSED`.
- **Refs in call results arrive as streams.** In 0.26 a ref in a result stayed JSON. Code that read
  a ref out of a result and opened it now receives an `InputStream` or an `OutputStream` instead.
- **A stream has one reader.** A second read of the same `InputStream` fails; call `tee()` before
  the first read for copies in the same process. Go has no `tee()`: copy the bytes with
  `io.TeeReader` or `io.MultiWriter` as you read.
- **Streams need a live call.** A call sent with `CallAction.Enqueue` (Go
  `iii.EnqueueAction(queue)`) and a stream or a ref anywhere in its payload is refused before it is
  sent, with the code `STREAM_NOT_ALLOWED`. Store the data and enqueue its key. `CallAction.Void` is
  allowed.
- **Observers receive `StreamInfo`.** When an observer captures the `input` or `output` of a call
  that carried a stream, its target receives `{ stream: true, direction, id }` in that field (Go
  `iii.StreamInfo`). A 0.26 TypeScript, Python, or browser target got a live reader there, and a
  0.26 Go target got the ref; opening either raced the observed function for the bytes. See [Observe
  a call that carries a stream](../creating-workers/streaming#observe-a-call-that-carries-a-stream).
- **Rust streams bind lazily.** An `InputStream` or `OutputStream` decoded from JSON binds to the
  handler's worker inside a handler, and to the only client in the process elsewhere. A process with
  several clients calls `stream.bind(&worker)` before using a stream decoded outside a handler.
- **Go streams bind lazily too.** A stream unmarshalled from a handler's input or from a call's
  result binds to that client. One unmarshalled from other JSON binds to the only client in the
  process; with several, call `stream.Bind(worker)` before using it.
- **The `payload_too_large` error links to the new page:**
  `https://iii.dev/docs/creating-workers/streaming#payload-size`.

## Checklist

- [ ] Upgrade one worker's SDK at a time; workers on 0.26 SDKs keep working unchanged on the same
      engine
- [ ] Replace each `createChannel` / `create_channel` / `create_channel_async` whose writer feeds a
      call with the source itself in the payload
- [ ] Replace each `writerRef` / `writer_ref` passed in for a function to fill with a returned
      stream, or with a sink in the payload, and move that function's callers in the same change
- [ ] Type stream fields as `InputStream` and `OutputStream`; in Rust, replace
      `extract_channel_refs` and `ChannelReader::new` / `ChannelWriter::new` with typed struct
      fields; in Go, replace `ExtractChannelRefs`, `OpenReader`, and `OpenWriter` with
      `*iii.InputStream` and `*iii.OutputStream` fields
- [ ] In Go, wrap what you send with `iii.InputStreamFromReader`, `iii.InputStreamFromBytes`, or
      `iii.OutputStreamToWriter`, and change `iiihttp.Wrap(client, fn)` to `iiihttp.Wrap(fn)`
- [ ] In the browser, pass a `Blob`, a `File`, or a `ReadableStream` in the payload instead of
      writing a channel
- [ ] Replace `reader.stream` and `writer.stream` with the stream itself, `write`, or the native
      bridges (`toReadable`, `toWritable`)
- [ ] Replace `sendMessage` / `send_message` with `send`, and `onMessage` / `on_message` with
      `messages()`, without your own JSON encoding
- [ ] Replace `writer.stream.destroy()`, dropping a Rust writer, and a Go `Close()` after a failed
      `Write` with `abort(reason)` or a throw, and catch `StreamAbortedError` (Rust
      `Error::StreamAborted`, Go an `*iii.InvocationError` with `iii.CodeStreamAborted`) where you
      caught the old errors
- [ ] Remove explicit closes the handler no longer needs, and call `keepOpen()` (Go `KeepOpen()`)
      where a handler keeps writing after it returns
- [ ] Import `extractChannelRefs`, `isChannelRef`, `StreamChannelRef`, `ChannelDirection`, and
      `ChannelItem` from the protocol module
- [ ] Move calls queued with `CallAction.Enqueue` that carried a ref to stored data and a key
- [ ] Update observer targets that read a captured stream field to expect a `StreamInfo`
