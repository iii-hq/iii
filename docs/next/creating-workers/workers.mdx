Use this page to create a worker, connect it to the engine, inspect the live registry, handle
disconnects, and shut the worker down.

<Note>
  For the full SDK surface each Worker can use when interacting with iii, see the complete SDK
  reference by language: [Node](../reference/sdk-node), [Python](../reference/sdk-python),
  [Rust](../reference/sdk-rust), or [Browser](../reference/sdk-browser).
</Note>

## Create a new worker

Create a TypeScript, JavaScript, Python, Rust, or Go project with the package tools of that
language. Add the iii SDK for that language and an entrypoint such as `src/index.ts` or
`src/main.py`. The Go SDK is the `github.com/iii-hq/iii/sdk/packages/go/iii` module. For what a
worker is, see [Worker](../understanding-iii#worker).

Compose needs a start command for a local worker. Put it in `scripts.start` in an `iii.worker.yaml`
at the root of the worker directory:

```yaml iii.worker.yaml
name: my-worker
description: One-line summary of what this worker does.
scripts:
  start: pnpm start
```

Declare the directory as a container in `worker-compose.yaml`:

```yaml worker-compose.yaml
containers:
  my-worker:
    worker: path://./workers/my-worker
```

A `scripts.run` value on the container in `worker-compose.yaml` replaces it.

Or add it to a running project with `iii trigger compose::add worker=./workers/my-worker`. When the
Compose daemon uses a namespace other than `default`, add `-n <namespace>` to the `iii trigger`
commands on this page. See
[Declare workers with Compose](../using-iii/workers#declare-workers-with-compose).

<Info title="Engine and SDK versions">
  The engine and SDK packages can have different patch versions within the same minor line. Keep the
  engine and SDKs on the same minor version, for example `0.11.x`, unless a release note says
  otherwise.
</Info>

## Connecting to the engine

A worker connects to the engine over WebSocket. When you do not pass a URL, `registerWorker` (Node)
and `register_worker` (Python) read the `III_URL` environment variable. When `III_URL` is not set,
they use `ws://127.0.0.1:49134`. A URL that you pass has priority. In Rust, pass the URL to
`register_worker`, or call `register_worker_from_env`.

Compose sets `III_URL`, `III_WORKER_NAME`, and other variables for each worker that it starts. A
non-empty `III_WORKER_NAME` replaces the worker name that you set in code. See
[The worker environment](../using-iii/compose#the-worker-environment).

<Note>
  This connects with full trust, which is correct for workers that you run. To admit an untrusted
  worker, such as a browser client or the worker of a third party, keep the engine port internal and
  connect the worker through an RBAC-gated port. See [Engine-owned
  workers](../using-iii/workers#engine-owned-workers) for the rbac-proxy worker, and [Access
  Control](./worker-manager) for the `iii-worker-manager` RBAC listener.
</Note>

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    import { registerWorker } from "iii-sdk";

    const url = process.env.III_URL;
    if (!url) throw new Error("III_URL must be set");
    const worker = registerWorker(url, {
      workerName: "my-worker",
      workerDescription: "One-line summary of what this worker does",
      namespace: "orders", // scopes this worker's registrations
    });
    ```

  </Tab>
  <Tab title="Python">
    ```python
    import os
    from iii import register_worker, InitOptions

    worker = register_worker(
        os.environ.get("III_URL"),
        InitOptions(
            worker_name="my-worker",
            worker_description="One-line summary of what this worker does",
            namespace="orders",  # scopes this worker's registrations
        ),
    )
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    use iii_sdk::runtime::WorkerMetadata;
    use iii_sdk::{InitOptions, register_worker};

    let url = std::env::var("III_URL").expect("III_URL must be set");
    let worker = register_worker(
        &url,
        InitOptions {
            metadata: Some(WorkerMetadata {
                name: "my-worker".into(),
                description: Some("One-line summary of what this worker does".into()),
                ..Default::default()
            }),
            namespace: Some("orders".into()), // scopes this worker's registrations
            ..Default::default()
        },
    );
    ```

  </Tab>
</Tabs>

`namespace` scopes everything that this worker registers. Leave the option out, and the SDK reads
the `III_NAMESPACE` environment variable, which Compose sets to the project namespace. When neither
is set, the engine puts the worker in the `default` namespace. For the order of precedence, see
[Set a worker namespace](../using-iii/namespaces#set-a-worker-namespace) and
[Compose precedence](../using-iii/compose#precedence). For calls across namespaces, see
[Trigger a function in a namespace](../using-iii/namespaces#trigger-a-function-in-a-namespace). For
rejected registrations, see
[Handle a rejected registration](../using-iii/namespaces#handle-a-rejected-registration).

## Worker lifecycle

### States

The SDK tracks the state of its own connection: `disconnected`, `connecting`, `connected`,
`reconnecting`, or `failed`. Read the state with `getConnectionState()` in Node or
`get_connection_state()` in Python and Rust. When the connection drops, the SDK reconnects and
registers its triggers and functions again. The state is `failed` when the engine rejects the worker
registration, or when the Node or Python SDK uses all its reconnection retries. By default, these
SDKs retry with no limit. When the state is `failed`, the SDK stops, so restart the worker. For the
state types, see [Node](../reference/sdk-node#iiiconnectionstate),
[Python](../reference/sdk-python#get_connection_state), and
[Rust](../reference/sdk-rust#iiiconnectionstate).

The engine shows each connected worker in `engine::workers::list`, with a `status` field. When the
WebSocket of a worker closes, the engine removes the worker from the registry and fires
`engine::workers-available` with `worker_disconnected`.

### Inspecting the live registry

To see what is connected to the engine, call one of the `engine::*::list` Functions. For the list of
these functions and what each one returns, see
[Engine discovery functions](../reference/engine-protocol#engine-discovery-functions).

### Handling Worker disconnects

When a Worker's WebSocket closes, the Engine cleans up after it automatically. Its Triggers and
Functions leave the live registry, and any in-flight invocations of those Functions are cancelled.

#### In-flight requests

An in-flight request gets an `invocation_stopped` error. Catch this error and treat it as a
cancellation. A retry fails with `function_not_found` until the Worker that owns the Function
reconnects.

<Accordion title="Example: catch `invocation_stopped`">
  <Tabs>
    <Tab title="Node / TypeScript">
      ```typescript
      import { InvocationError } from "iii-sdk/errors";

      try {
        const result = await worker.trigger({
          function_id: "math::add",
          payload: { a: 1, b: 2 },
        });
      } catch (err) {
        if (err instanceof InvocationError && err.code === "invocation_stopped") {
          // Worker disconnected mid-invocation. Subscribe to `engine::functions-available`
          // (see "Subscribe to changes" below) to know when to retry.
        } else {
          throw err;
        }
      }
      ```
    </Tab>
    <Tab title="Python">
      ```python
      from iii.errors import InvocationError

      try:
          result = worker.trigger({
              "function_id": "math::add",
              "payload": {"a": 1, "b": 2},
          })
      except InvocationError as err:
          if err.code != "invocation_stopped":
              raise
          # Worker disconnected mid-invocation. Subscribe to `engine::functions-available`
          # (see "Subscribe to changes" below) to know when to retry.
      ```
    </Tab>
    <Tab title="Rust">
      ```rust
      use iii_sdk::Error;
      use iii_sdk::protocol::TriggerRequest;
      use serde_json::json;

      let result = worker
          .trigger(TriggerRequest {
              function_id: "math::add".into(),
              payload: json!({ "a": 1, "b": 2 }),
              action: None,
              timeout_ms: None,
          })
          .await;

      match result {
          Err(Error::Remote { code, .. }) if code == "invocation_stopped" => {
              // Worker disconnected mid-invocation. Subscribe to `engine::functions-available`
              // (see "Subscribe to changes" below) to know when to retry.
          }
          Err(e) => return Err(e.into()),
          Ok(value) => { /* use value */ }
      }
      ```
    </Tab>

  </Tabs>
</Accordion>

#### Subscribe to changes

You can register a Trigger against one of the engine's discovery events to react to topology changes
as they happen. This is particularly useful for continuing work when a Worker comes back online.

The engine fires `engine::workers-available` when a Worker connects, disconnects, or registers its
metadata. It fires `engine::functions-available` when the set of registered Functions changes, and
it checks for changes every 5 seconds. For the `event` values, see
[Engine discovery triggers](../reference/engine-protocol#engine-discovery-triggers).

<Accordion title="Example: subscribe to discovery events">
  <Tabs>
    <Tab title="Node / TypeScript">
      ```typescript
      worker.registerFunction(
        "discovery::on-workers",
        async (data: { event: string; worker_id: string }) => {
          if (data.event === "worker_connected") {
            // A Worker connected. Its Functions can arrive later. Use
            // engine::functions-available to know when a Function is callable.
          }
        },
      );
      worker.registerTrigger({
        type: "engine::workers-available",
        function_id: "discovery::on-workers",
        config: {},
      });

      worker.registerFunction(
        "discovery::on-functions",
        async (data: { event: string; functions: { function_id: string }[] }) => {
          // `functions` is the full snapshot after the change.
          const ids = data.functions.map((f) => f.function_id);
        },
      );
      worker.registerTrigger({
        type: "engine::functions-available",
        function_id: "discovery::on-functions",
        config: {},
      });
      ```
    </Tab>
    <Tab title="Python">
      ```python
      async def on_workers(data: dict) -> None:
          if data["event"] == "worker_connected":
              # A Worker connected. Its Functions can arrive later. Use
              # engine::functions-available to know when a Function is callable.
              pass

      worker.register_function("discovery::on-workers", on_workers)
      worker.register_trigger({
          "type": "engine::workers-available",
          "function_id": "discovery::on-workers",
          "config": {},
      })

      async def on_functions(data: dict) -> None:
          # `functions` is the full snapshot after the change.
          ids = [f["function_id"] for f in data.get("functions", [])]

      worker.register_function("discovery::on-functions", on_functions)
      worker.register_trigger({
          "type": "engine::functions-available",
          "function_id": "discovery::on-functions",
          "config": {},
      })
      ```
    </Tab>
    <Tab title="Rust">
      ```rust
      use iii_sdk::RegisterFunction;
      use iii_sdk::protocol::RegisterTriggerInput;
      use schemars::JsonSchema;
      use serde::Deserialize;
      use serde_json::{Value, json};

      #[derive(Deserialize, JsonSchema)]
      struct WorkersAvailable { event: String, worker_id: String }

      #[derive(Deserialize, JsonSchema)]
      struct FunctionsAvailable { event: String, functions: Vec<Value> }

      worker.register_function(
          "discovery::on-workers",
          RegisterFunction::new_async(|input: WorkersAvailable| async move {
              if input.event == "worker_connected" {
                  // A Worker connected. Its Functions can arrive later. Use
                  // engine::functions-available to know when a Function is callable.
              }
              Ok::<_, iii_sdk::Error>(())
          }),
      );
      worker.register_trigger(RegisterTriggerInput::new(
          "engine::workers-available",
          "discovery::on-workers",
          json!({}),
      ))?;

      worker.register_function(
          "discovery::on-functions",
          RegisterFunction::new_async(|input: FunctionsAvailable| async move {
              // `functions` is the full snapshot after the change.
              let _count = input.functions.len();
              Ok::<_, iii_sdk::Error>(())
          }),
      );
      worker.register_trigger(RegisterTriggerInput::new(
          "engine::functions-available",
          "discovery::on-functions",
          json!({}),
      ))?;
      ```
    </Tab>

  </Tabs>
</Accordion>

## Worker manifest

`iii.worker.yaml` at the worker root tells Compose how to start the worker. For each field, see
[Worker manifest](./worker-manifest). To replace the start command for one project, or to add
`pre_run` and `post_run` hooks, set `scripts` on the container in
[`worker-compose.yaml`](../using-iii/compose#scripts).

<Note>
  If a worker does not start, check its manifest, the Compose daemon output, and the result of `iii
  trigger compose::status`.
</Note>

## Shutting down a worker

Call the SDK's `shutdown` to close the WebSocket cleanly. The engine removes the worker's Triggers
and Functions from the registry, fires `engine::workers-available` with `worker_disconnected`, and
cancels in-flight invocations targeting them with `invocation_stopped`.

Without `shutdown`, an abrupt process exit reaches the same state once the engine notices the
dropped socket; graceful shutdown makes it deterministic and faster.

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    process.on("SIGTERM", async () => {
      await worker.shutdown();
      process.exit(0);
    });
    ```
  </Tab>
  <Tab title="Python">
    ```python
    import signal

    def _on_term(*_):
        worker.shutdown()
        raise SystemExit(0)

    signal.signal(signal.SIGTERM, _on_term)
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    // Sends the close signal without blocking the async runtime. It does not wait for the
    // connection thread. Call worker.shutdown() to wait for the thread and flush OpenTelemetry.
    worker.shutdown_async().await;
    ```
  </Tab>
</Tabs>

<Note>
  Shutdown is useful for one-shot workers. Kubernetes Jobs, serverless containers, or scheduled
  scripts can connect like any other Worker, do their work, and call `shutdown()`.
</Note>
