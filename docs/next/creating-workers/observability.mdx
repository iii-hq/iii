Use this page to emit logs from your workers and to read the traces of their calls. The
`iii-observability` worker always runs, so do not declare it in `config.yaml` or
`worker-compose.yaml`. For the workers that the engine injects, see
[Startup flow](../understanding-iii/engine#startup-flow).

<Note>
  This page shows how to emit logs and query traces. For the complete configuration and the full
  list of query functions, see the [iii-observability worker
  docs](https://workers.iii.dev/workers/iii-observability).
</Note>

## OpenTelemetry support

The `iii-observability` worker produces OpenTelemetry traces, metrics, and logs. It can keep them in
memory or export them to any OpenTelemetry (OTLP) collector.

To change sampling, retention, or exporter targets, edit the `iii-observability` entry of the
[configuration worker](../using-iii/configuration). A change to the trace exporter takes effect at
the next engine start. The `engine::traces::*` query functions on this page need the `memory` or
`both` exporter. `memory` is the default. For the exporter and sampling options and the data that
the worker produces, see the
[iii-observability worker docs](https://workers.iii.dev/workers/iii-observability).

## Logging

Worker code emits structured logs with the `Logger` from the iii helpers package. The Logger sends
each log line into the OpenTelemetry pipeline, so the line links to the trace it happened in.

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    import { Logger } from "@iii-dev/helpers/observability";

    const logger = new Logger();

    // each level takes a message and optional structured data
    logger.debug("cache lookup", { key });
    logger.info("processing link", { slug });
    logger.warn("retrying upstream", { attempt });
    logger.error("failed to persist", { slug, err });
    ```

  </Tab>
  <Tab title="Python">
    ```python
    from iii_helpers.observability import Logger

    logger = Logger()

    # each level takes a message and optional structured data
    logger.debug("cache lookup", {"key": key})
    logger.info("processing link", {"slug": slug})
    logger.warn("retrying upstream", {"attempt": attempt})
    logger.error("failed to persist", {"slug": slug, "err": str(err)})
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    use iii_helpers::observability::Logger;
    use serde_json::json;

    let logger = Logger::new();

    // each level takes a message and optional structured data
    logger.debug("cache lookup", Some(json!({ "key": key })));
    logger.info("processing link", Some(json!({ "slug": slug })));
    logger.warn("retrying upstream", Some(json!({ "attempt": attempt })));
    logger.error("failed to persist", Some(json!({ "slug": slug, "err": err.to_string() })));
    ```

  </Tab>
</Tabs>

You can also query recorded logs and emit one-off log lines through the observability worker's
functions, for example:

```bash
# emit a log line from the CLI
iii trigger engine::log::info message='hello from the CLI'

# find it in the stored logs
iii trigger engine::logs::list | grep -C 10 hello
```

## Traces

Traces come from worker function invocations. The iii SDK in a worker records a span each time the
worker handles a call, so you do not write instrumentation code. A trace joins the spans of one call
across all the workers that it reaches. Calls to `engine::*` functions are not traced by default
(set `III_OTEL_TRACE_BUILTINS=true` to include them), so call a worker function first to produce a
trace. If you followed the [Quickstart](../quickstart), call the TypeScript worker, which calls the
Python worker:

```bash
# run something to produce a trace
iii trigger math::add_two_numbers a=10 b=20

# count the recorded traces (workers export spans a moment after the call,
# so re-run this until it reports a non-zero count)
iii trigger engine::traces::list | jq '.total'

# grab the most recent trace id and print its span tree
TID=$(iii trigger engine::traces::list sort_order=desc limit=1 | jq -r '.traces[0].trace_id')
iii trigger engine::traces::tree trace_id=$TID
```

<Note>
  `engine::traces::tree` needs a real `trace_id` and traces export on a short delay. If
  `engine::traces::list` still reports `0` or the call above to get a `trace_id` resolves to `null`
  and fails then wait a few seconds and try again.
</Note>

<Note>
  To check the health of the observability components, call `engine::health::check`. To clear stored
  logs and traces while you develop, call `engine::logs::clear` and `engine::traces::clear`. New
  logs arrive quickly, so `engine::logs::list` can show new lines right after a clear. For the
  details of these functions, see the [iii-observability worker
  docs](https://workers.iii.dev/workers/iii-observability).
</Note>

## Seeing it in the console

The [console](../using-iii/console) shows the traces, logs, and metrics of a running system. During
development you seldom need to call the functions above yourself.
