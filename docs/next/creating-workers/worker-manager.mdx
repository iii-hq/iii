The `iii-worker-manager` worker owns the connections between workers and the engine. It always runs
a **trusted listener** (on `49134` by default) that your own workers connect to through `III_URL`.
To let an **untrusted** client connect, add an **RBAC-gated listener**. Untrusted clients include
browser tabs, third-party processes, and other processes that you do not run. On an RBAC listener, a
function that you write authenticates each connection, and an allowlist checks each call.

<Note>
  `iii-worker-manager` always runs, so you do not add it. You configure its listeners in the engine
  configuration. With `iii compose --up`, put them under `engine.workers` in `worker-compose.yaml`.
  When you start the engine with `iii` yourself, or another supervisor starts it, declare the
  listeners as a `workers:` list in `config.yaml`. See [Engine
  configuration](../using-iii/engine#engine-configuration). For the full configuration, see the
  [iii-worker-manager worker docs](https://workers.iii.dev/workers/iii-worker-manager).
</Note>

## Trusted and RBAC listeners

The default `49134` listener is **trusted**: any worker that reaches it can register functions and
call anything. Use it only for workers that you run yourself. Connect a browser or other untrusted
worker through an RBAC listener. An RBAC listener runs on its own port, gates every connection
through an `auth` function, and restricts each session to an allowlist of functions.

<Warning>
  A `iii-worker-manager#<instance>` key adds a listener. The trusted listener keeps running. A bare
  `iii-worker-manager` key replaces the trusted listener. If you declare it, set `host`, because it
  defaults to `0.0.0.0`. Under Compose, its port must also match the port in `engine.url`. Changes
  to `engine.workers` take effect only after the engine restarts.
</Warning>

Add an RBAC-gated listener on a separate port (here `3110`). The trusted listener on `49134` keeps
running.

```yaml worker-compose.yaml
engine:
  workers:
    # Browser-facing, RBAC-gated listener on a separate port.
    "iii-worker-manager#rbac":
      host: 127.0.0.1
      port: 3110
      rbac:
        auth_function_id: auth::browser
        expose_functions:
          - match: "link::create"
            namespace: browser
```

For each new connection, `iii-worker-manager` calls the function that `auth_function_id` names. The
function accepts or rejects the connection. The next section shows how to write it.

<Warning>
  `auth_function_id` resolves in the `default` namespace. Register the auth worker there. An auth
  worker in another namespace makes the listener reject every connection.
</Warning>

`expose_functions` is the allowlist of function IDs a session can call. Each entry is a
`match("...")` string, a map with a `match` key, or a map with a `metadata` key. Only the map forms
accept `namespace`. A `match` value is a glob on the function ID. A `metadata` value matches the
functions whose [`metadata`](./functions#attach-metadata) has those fields, for example
`{ public: true }`, `{ tier: "premium" }`, or `{ scopes: ["read"] }`. For the full filter syntax,
see the [iii-worker-manager worker docs](https://workers.iii.dev/workers/iii-worker-manager).

```yaml
expose_functions:
  - match("public::*") # any function with the public:: id prefix
  - match("engine::functions::list") # one specific function
  - metadata:
      public: true # any function whose metadata.public is true
```

<Warning>
  Gate access on facts that only trusted workers control. A function's metadata comes from the
  worker that registers it. A session that can register functions can set `metadata.public = true`
  on its own functions. Use `metadata` rules only for functions that your trusted workers register.
  For untrusted sessions, set `allow_function_registration` to `false` (it defaults to `true`), or
  set `on_function_registration_function_id` to a hook that rewrites the metadata.
</Warning>

### Namespace-scoped function rules

An `expose_functions` rule without a namespace applies to `default` only. To let the session call a
function in another namespace, write the rule as a map and add `namespace`:

```yaml
expose_functions:
  - match: "orders::*"
    namespace: orders
  - metadata:
      public: true
    namespace: analytics
```

The `match` value supports `*` wildcards for the function id. The `namespace` value is an exact
match and does not support wildcards. Add one rule for each namespace that the session can access.

## Write the auth function

The auth function runs during the WebSocket upgrade, before the client is connected. It receives the
request's headers, query parameters, and client IP, and returns the session's permissions. **Throw
to reject the connection.**

<Note>
  One auth function can authorize more than one type of worker. Use one auth function for workers
  that need the same permissions. Declare a separate `iii-worker-manager#<instance>` listener for each
  group of workers that needs different permissions. You can declare any number of listeners.
</Note>

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript src/index.ts
    import { registerWorker } from "iii-sdk";

    const worker = registerWorker(process.env.III_URL ?? "ws://localhost:49134", {
      workerName: "auth",
    });

    worker.registerFunction(
      "auth::browser",
      async (input: {
        headers: Record<string, string>;
        query_params: Record<string, string[]>;
        ip_address: string;
      }) => {
        const token = input.query_params.token?.[0];
        if (token !== (process.env.BROWSER_TOKEN ?? "dev-token")) {
          throw new Error("unauthorized");
        }
        return {
          allowed_functions: [], // extra IDs to allow beyond expose_functions
          forbidden_functions: [], // denied even if matched; supersedes allowed
          allow_trigger_type_registration: false, // can the worker register its own trigger types
          allow_function_registration: true, // can the worker register its own callbacks
          context: { source: "browser" }, // forwarded to middleware on every call
        };
      },
    );
    ```

The auth worker itself connects to the **trusted** `49134` port; it is one of your own workers. Only
the untrusted client connects through `3110`.

The returned object is an `AuthResult`. For its full schema, see the
[iii-worker-manager worker docs](https://workers.iii.dev/workers/iii-worker-manager).

### Scope a session to namespaces

`namespaces` maps a namespace to the function IDs the session may call inside it. An entry accepts
an exact ID or a wildcard, in either the bare or the `match("...")` spelling `expose_functions`
uses:

```json
{
  "namespaces": {
    "orders": ["svc::*", "billing::charge"],
    "analytics": []
  }
}
```

The keys also limit the namespaces that the session can register in. With this result, the session
can register only in `orders` and `analytics`. A worker on this session that declares another
namespace, `default` included, gets a `FORBIDDEN` error that lists the permitted namespaces. An
entry with an empty list, like `analytics`, grants the namespace and no functions in it. In that
namespace, the session can call only what `expose_functions` permits.

To leave the session unscoped, return an empty `namespaces` or omit it. The session can then
register in any namespace, and only `allowed_functions` and `expose_functions` apply.

<Warning>
  `allowed_functions` applies in `default` only. A grant listed there does not answer in `orders`,
  even for a session scoped to it. Put per-namespace grants in `namespaces`.
</Warning>

`forbidden_functions` holds in every namespace. It wins over `namespaces` and over the
infrastructure functions that every session can call: `engine::channels::create`,
`engine::workers::register`, `engine::log::*`, and `engine::baggage::*`.

## Connect a client

A browser connects with `iii-browser-sdk` pointed at the RBAC port. Browsers cannot set custom
WebSocket headers, so the token travels as a query parameter, the same one `auth::browser` reads:

```typescript src/iii.ts
import { registerWorker } from "iii-browser-sdk";

const token = import.meta.env.VITE_BROWSER_TOKEN ?? "dev-token";
export const worker = registerWorker(`ws://localhost:3110?token=${encodeURIComponent(token)}`, {
  namespace: "browser",
});
```

The session can now call only the functions that `expose_functions`, `namespaces`, and
`allowed_functions` permit, plus the infrastructure functions.

<Note>
  The [rbac-proxy worker](https://workers.iii.dev/workers/rbac-proxy) also gates untrusted clients.
  It runs an auth function, an `expose_functions` allowlist, middleware, and registration hooks from
  its own port, in front of the engine. Its port is `49200` by default. Namespace-scoped rules and
  `namespaces` grants work only on a `iii-worker-manager` RBAC listener. Add the proxy with `iii
  trigger compose::add worker=rbac-proxy`.
</Note>

For an end-to-end walkthrough that turns a browser tab into a worker, see
[Ch. 7: Bring in the browser](../tutorials/linkly/frontend). That chapter gates the browser with the
`rbac-proxy` worker. It uses an auth function and an `expose_functions` allowlist from its own port.

## Intercept calls with middleware

Set `middleware_function_id` on the listener to run a function on each invocation that comes through
the RBAC port. Calls to the `engine::*` functions that ship with the engine skip the middleware. The
middleware receives the call plus the session `context` from the auth result, and acts as a proxy:
forward the (optionally rewritten) call and return its result, or throw to reject.

The engine looks up the middleware in the namespace that the call targets. Register the middleware
in each namespace that sessions on this listener call. In this example, the browser session calls
functions in `browser`, so a worker in `browser` registers `auth::middleware`. The input also
carries `namespace` and `action`. Forward both, so the call keeps its target namespace and its
routing.

```yaml worker-compose.yaml {7}
engine:
  workers:
    # ...
    "iii-worker-manager#rbac":
      host: 127.0.0.1
      port: 3110
      middleware_function_id: auth::middleware
      rbac:
        auth_function_id: auth::browser
        expose_functions:
          - match: "link::create"
            namespace: browser
```

  <Tab title="Node / TypeScript">
    ```typescript
    import { registerWorker, type MiddlewareFunctionInput } from "iii-sdk";

    const worker = registerWorker(process.env.III_URL ?? "ws://localhost:49134", {
      workerName: "middleware",
      namespace: "browser",
    });

    worker.registerFunction("auth::middleware", async (input: MiddlewareFunctionInput) => {
      // stamp the authenticated caller onto every payload, then forward the call
      const payload = { ...input.payload, _source: input.context.source };
      return worker.trigger({
        function_id: input.function_id,
        payload,
        action: input.action,
        namespace: input.namespace,
      });
    });
    ```

    ```rust
    let worker = register_worker(&url, InitOptions {

                let worker = worker.clone();
                async move {
                    // stamp the authenticated caller onto every payload, then forward the call
                    let mut payload = input.payload.clone();
                    if let Some(obj) = payload.as_object_mut() {

                    let request = TriggerRequest {
                        function_id: input.function_id,
                        payload,
                        action: input.action,
                        timeout_ms: None,
                    };
                    // an absent namespace means the engine's default namespace
                    let namespace = input.namespace.unwrap_or_else(|| "default".into());
                    worker.trigger(request.namespace(namespace)).await
                }
            }
        }),
    );
    ```
