Ask the installed binary for its exact command and flag surface:

```bash
iii --help
iii <subcommand> --help
```

The generated [CLI reference](../cli-reference/index) publishes the same surface.

## Subcommands

| Subcommand                                  | What it does                                                                                        |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `iii compose`                               | Run the Compose daemon, prepare registry packages with `build`, or supervise a project with `--up`. |
| `iii call` (aliases `iii trigger`, `iii t`) | Call a registered function on a running engine.                                                     |
| `iii project`                               | Scaffold projects and generate Docker assets.                                                       |
| `iii registry`                              | Sign in to a worker registry, so Compose can install private workers.                               |
| `iii cloud`                                 | Manage hosted iii deployments.                                                                      |
| `iii update`                                | Update iii and the `iii-cloud` binary.                                                              |

The `iii console` command was removed. The iii console is ADE, a standalone application published
in the registry as `ade`; see [ADE](./ade).

Running `iii` with no subcommand starts only the engine from `./config.yaml` or `--config`. Use
`iii compose --up` for the normal project lifecycle:

```bash
iii compose build --file worker-compose.yaml
iii compose --namespace dev --up --file worker-compose.yaml
```

## Managing iii Cloud deployments

The `iii cloud` command group manages hosted deployments. See
[Deployment](./deployment#iii-cloud-deployments).

<Note>iii Cloud availability may vary by account and release.</Note>

## Signing in to a worker registry

`iii registry login` saves a download token for a registry, so Compose can install the private
workers it has access to. `iii registry whoami` shows who the saved token belongs to, and
`iii registry logout` removes it. Compose keeps the token to itself: workers never inherit it. On a
shared or persistent CI runner, prefer `III_REGISTRY_TOKEN` on the engine process for the job. See
[Private workers](./workers-registry#private-workers).

```bash
iii registry login
iii registry whoami
```

## Updating iii

`iii update` updates iii and the `iii-cloud` binary. Worker package versions are pinned
inside `worker-compose.yaml`; update one with `compose::update`:

```bash
iii call -n dev compose::update worker=state@latest
iii call -n dev compose::update worker=state@0.22.2
```

Run `iii update --list-targets` to list the binaries the installer can update.
