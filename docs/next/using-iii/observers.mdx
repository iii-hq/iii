`observe(a, b)` means: when `a` runs, `b` runs.

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    worker.observe("orders::create", "alerts::new-order");
    ```

  </Tab>
  <Tab title="Python">
    ```python
    worker.observe("orders::create", "alerts::new-order")
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    worker.observe("orders::create", "alerts::new-order");
    ```

  </Tab>
  <Tab title="Go">
    ```go
    worker.ObserveFunction("orders::create", "alerts::new-order")
    ```

  </Tab>
</Tabs>

After each successful call of `orders::create`, iii runs `alerts::new-order` with what happened: the
input of the call, its result, and who made it. `orders::create` (the observed function) can be any
function: one that your team wrote, an HTTP request (`http::on-request`), a cron tick
(`cron::on-tick`), a row change (`database::on-row-changed`). `alerts::new-order` (the target) is
any registered function. An observer observes what the function returns.

By default:

- The target runs after each successful call of the observed function.
- The target receives the [`Observed` envelope](#target-arguments) of the call, with its `input`,
  its `output`, and its `caller`.
- The caller of the observed function gets its result without waiting for the target. Each call runs
  the target at most once, and a failure of the target does not change the call.
- The observer stays `pending` until both functions are registered, in any order.

Any worker can observe any function, private ones included, unless the function is registered with
`observable: false` or RBAC restricts it (see [Authorization](#authorization)). A `private` function
can be called only by its own worker and observed by any worker.

## Observe a function

The examples on this page build on each other. They all react to `orders::create`, a regular
function registered by another worker.

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    import { registerWorker, type Observed } from "iii-sdk";
    import { Logger } from "@iii-dev/helpers/observability";

    const url = process.env.III_URL;
    if (!url) throw new Error("III_URL must be set");
    const worker = registerWorker(url);
    const logger = new Logger();

    type Order = { id: string; email: string; total: number };

    // The target: a regular function. It receives the Observed envelope of each call.
    worker.registerFunction("alerts::new-order", async (event: Observed<Order>) => {
      logger.info(`order ${event.input?.id} totals ${event.input?.total}`);
      return null;
    });

    // When orders::create runs, run alerts::new-order.
    const newOrders = worker.observe("orders::create", "alerts::new-order");
    await newOrders.ready(); // resolves once the observer is active
    ```

  </Tab>
  <Tab title="Python">
    ```python
    import os
    from iii import InitOptions, register_worker
    from iii_helpers.observability import Logger

    worker = register_worker(os.environ.get("III_URL"), InitOptions(worker_name="alerts"))
    logger = Logger()

    # The target: a regular function. It receives the Observed envelope of each call.
    def new_order(event: dict) -> None:
        order = event.get("input", {})
        logger.info(f"order {order.get('id')} totals {order.get('total')}")

    worker.register_function("alerts::new-order", new_order)

    # When orders::create runs, run alerts::new-order.
    new_orders = worker.observe("orders::create", "alerts::new-order")
    new_orders.ready()  # blocks until active; use `await new_orders.ready_async()` in asyncio code
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    use iii_helpers::observability::Logger;
    use iii_sdk::{Error, InitOptions, Observed, RegisterFunction, register_worker};
    use schemars::JsonSchema; // schemars 0.8, the version iii-sdk uses
    use serde::{Deserialize, Serialize};

    #[derive(Debug, Clone, Serialize, Deserialize, JsonSchema)]
    struct Order {
        id: String,
        email: String,
        total: f64,
    }

    let url = std::env::var("III_URL").expect("III_URL must be set");

    worker.register_function(
        "alerts::new-order",
        RegisterFunction::new(|event: Observed<Order>| {
            if let Some(order) = &event.input {
                Logger::new().info(&format!("order {} totals {}", order.id, order.total), None);
            }
            Ok::<_, Error>(())
        }),
    );

    // When orders::create runs, run alerts::new-order.
    let new_orders = worker.observe("orders::create", "alerts::new-order");
    new_orders.ready().await?; // resolves once the observer is active
    ```

    ```go
    import "github.com/iii-hq/iii/sdk/packages/go/iii/observability"

        return nil, nil
    })

    // When orders::create runs, run alerts::new-order.
    newOrders, err := worker.ObserveFunction("orders::create", "alerts::new-order")
    if err != nil {
        log.Fatal(err) // the request could not be built (a missing id)
    }
    if err := newOrders.Ready(ctx); err != nil {
        log.Fatal(err) // an *iii.ObserveRejectionError carries the engine's code
    }
    ```

From this point, `alerts::new-order` runs after each successful call of `orders::create`.

`observe` returns a [handle](#observer-handle) at once, also before the connection is up. The SDK
sends the observer when it connects and replays it with the same id after every reconnect, so you
call `observe` once at startup, like `registerFunction`. The browser SDK (`iii-browser-sdk`) has the
same `observe` API as Node.

<Info>The observer can miss calls that happen before `ready()` resolves.</Info>

### The first argument

The first argument is the id of the function to observe, or an object with these fields. All fields
are optional except `function_id`:

| Field         | Default                                                                                           | Meaning                                                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `function_id` | required                                                                                          | The function to observe.                                                                                                          |
| `namespace`   | `default` for `engine::*` and `configuration::*` functions; the worker's namespace for all others | The namespace of the function.                                                                                                    |
| `args`        | none                                                                                              | Arguments for the worker that hosts the function, for functions that document them. See [Args and filters](#args-and-filters).    |
| `filters`     | `{}` (every call)                                                                                 | Which calls reach the target. See [Filters](#filters).                                                                            |
| `on`          | `success`                                                                                         | Which calls run the target: `success`, `error`, or `complete` (both). See [`on`](#on).                                            |
| `capture`     | `["input", "output", "caller"]`                                                                   | Which parts of the call the envelope carries: any of `input`, `output`, `error`, `caller`, `metadata`. See [`capture`](#capture). |
| `deliver`     | `envelope`                                                                                        | What the target's first argument is: the `envelope`, or the observed `input` or `output` alone. See [`deliver`](#deliver).        |

The target is the id of a registered function. It can be any function except the observed function
itself and [private functions](#built-in-event-sources). To name a target in another namespace, pass
`{ function_id, namespace }`.

## Args and filters

An observer can carry `args` and `filters`. `args` are for the worker that hosts the function.
`filters` are for iii.

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    worker.observe(
      {
        function_id: "database::on-row-changed",
        args: { db: "primary", table: "orders", ops: ["insert", "update"] }, // for the database worker
        filters: { "caller.parent.worker_name": { $ne: "order-projector" } }, // for iii
      },
      "orders::project",
    );
    ```

  </Tab>
  <Tab title="Python">
    ```python
    worker.observe(
        {
            "function_id": "database::on-row-changed",
            "args": {"db": "primary", "table": "orders", "ops": ["insert", "update"]},  # for the database worker
            "filters": {"caller.parent.worker_name": {"$ne": "order-projector"}},  # for iii
        },
        "orders::project",
    )
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    use iii_sdk::Source;
    use serde_json::json;

    worker.observe(
        Source::function("database::on-row-changed")
            // for the database worker
            .args(json!({ "db": "primary", "table": "orders", "ops": ["insert", "update"] }))
            // for iii
            .filters(json!({ "caller.parent.worker_name": { "$ne": "order-projector" } })),
        "orders::project",
    );
    ```

  </Tab>
  <Tab title="Go">
    ```go
    worker.Observe(iii.Source{
        FunctionID: "database::on-row-changed",
        // for the database worker
        Args: iii.Args{"db": "primary", "table": "orders", "ops": []string{"insert", "update"}},
        // for iii
        Filters: iii.Filters{"caller.parent.worker_name": iii.Op{"$ne": "order-projector"}},
    }, "orders::project")
    ```

  </Tab>
</Tabs>

- **`args`** go to the worker that hosts the function. That worker reads them to set something up
  for the observer (a route, a schedule, a database trigger, a queue consumer) and to choose which
  calls reach it. Here the database worker captures the changes of `orders` in `primary` and
  delivers only inserts and updates. Each function documents its `args`.
- **`filters`** go to iii. They select which calls reach the target, by anything in the call:
  `input`, `output`, `error`, `caller`, and `metadata`. iii applies them the same way for every
  function. Here the filter skips the writes that `order-projector` makes, so the projector does not
  react to its own writes.

Use `args` for what the function's worker sets up for the observer, and `filters` for which calls
the target wants. A cron expression is an arg: the cron worker starts a schedule for it. "Only ticks
after 1 November" is a filter.

### Args

The engine checks `args` against the `args_format` of the function, a JSON Schema the function's
worker declares when it registers the function. The observer fails with `INVALID_ARGS` when the
`args` do not match, or when the function has no `args_format` and the `args` are not empty. The
worker can also refuse an observer whose `args` it cannot serve, with a code of its own (for example
`UNKNOWN_DB` or `HTTP_ROUTE_CONFLICT`). [Built-in event sources](#built-in-event-sources) lists the
`args` of the standard workers.

### Filters

This observer runs `alerts::big-order` only for orders with a total of 500 or more. The observer
does not set `deliver`, so the target receives the [`Observed` envelope](#target-arguments): the
order (`input`), the result (`output`), the caller (`caller`), and the duration of the call
(`duration_ms`).

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    worker.registerFunction("alerts::big-order", async (event: Observed<Order>) => {
      logger.info(
        `order ${event.input?.id} totals ${event.input?.total}, placed by ${event.caller?.worker_name}`,
      );
      return null;
    });

    // After each successful call of orders::create with total >= 500, run alerts::big-order.
    await worker
      .observe(
        { function_id: "orders::create", filters: { "input.total": { $gte: 500 } } },
        "alerts::big-order",
      )
      .ready();
    ```

  </Tab>
  <Tab title="Python">
    ```python
    def big_order(event: dict) -> None:
        order = event.get("input", {})
        caller = event.get("caller", {})
        logger.info(f"order {order.get('id')} totals {order.get('total')}, placed by {caller.get('worker_name')}")

    worker.register_function("alerts::big-order", big_order)

    # After each successful call of orders::create with total >= 500, run alerts::big-order.
    worker.observe(
        {"function_id": "orders::create", "filters": {"input.total": {"$gte": 500}}},
        "alerts::big-order",
    ).ready()
    ```

  </Tab>
  <Tab title="Rust">
    ```rust

    use serde_json::json;

        RegisterFunction::new(|event: Observed<Order>| {

                Logger::new().info(&format!("order {} totals {}", order.id, order.total), None);
            }
            Ok::<_, Error>(())
        }),
    );

    // After each successful call of orders::create with total >= 500, run alerts::big-order.
    worker
        .observe(
            Source::function("orders::create").filters(json!({ "input.total": { "$gte": 500 } })),
            "alerts::big-order",

        .await?;
    ```

  </Tab>
  <Tab title="Go">
    ```go

        }
        logger.Info(ctx, "big order", event.Input)
        return nil, nil

        FunctionID: "orders::create",

        log.Fatal(err)
    }
    if err := bigOrders.Ready(ctx); err != nil {
        log.Fatal(err)
    }
    ```

Both observers watch the same function, independently.

A filter is a JSON object. Each key is a path in the call that starts with `input`, `output`,
`error`, `caller`, or `metadata`. Each value is an operator object, for example `{ "$eq": "EUR" }`.
A literal value such as `"EUR"` is not allowed.

The operators are `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin`, `$exists`, `$prefix`,
`$and`, `$or`, `$not`, and `$any`.

```json
{
  "input.total": { "$gte": 500 },
  "input.currency": { "$in": ["EUR", "USD"] },
  "caller.worker_name": { "$ne": "importer" }
}
```

When the observer is created, the SDK and the engine check the filter. If it is not valid, the
observer fails with `INVALID_FILTER`. The engine also checks the `input.*` and `output.*` paths
against the `request_format` and `response_format` of the function. If a closed schema does not have
a path, the observer fails with `INVALID_FILTER_PATH`. If the function is not registered yet, the
engine does this check when the function registers.

A filter can read any field of the call, including the fields that `capture` leaves out. The engine
and each SDK have their own filter implementation. All of them pass the same set of test cases, so a
filter matches the same calls in all of them. See the
[filter language reference](../reference/filters) for the operators, the rules for absent and `null`
values, and the limits.

## Target arguments

Three fields of the first argument set what the target receives: `deliver`, `capture`, and `on`.

### `deliver`

`deliver` sets the target's first argument:

| `deliver`            | The target's first argument                                 |
| -------------------- | ----------------------------------------------------------- |
| `envelope` (default) | The `Observed` envelope of the call.                        |
| `input`              | The input of the call alone.                                |
| `output`             | The output of the call (the function's return value) alone. |

If the value is absent (for example, `output` after a failed call), the argument is `null`. With
`deliver: "input"`, `emails::send-receipt` receives the order that `orders::create` was called with:

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    worker.registerFunction("emails::send-receipt", async (order: Order) => {
      await sendReceipt(order.email, order);
      return null;
    });

    // After each successful call of orders::create, run emails::send-receipt with the order.
    worker.observe({ function_id: "orders::create", deliver: "input" }, "emails::send-receipt");
    ```

  </Tab>
  <Tab title="Python">
    ```python
    def send_receipt(order: dict) -> None:
        mailer.send_receipt(order["email"], order)

    worker.register_function("emails::send-receipt", send_receipt)

    # After each successful call of orders::create, run emails::send-receipt with the order.
    worker.observe({"function_id": "orders::create", "deliver": "input"}, "emails::send-receipt")
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    use iii_sdk::{Deliver, Source};

    worker.register_function(
        "emails::send-receipt",
        RegisterFunction::new(|order: Order| {
            send_receipt(&order.email, &order);
            Ok::<_, Error>(())
        }),
    );

    // After each successful call of orders::create, run emails::send-receipt with the order.
    worker.observe(
        Source::function("orders::create").deliver(Deliver::Input),
        "emails::send-receipt",
    );
    ```

  </Tab>
  <Tab title="Go">
    ```go
    worker.RegisterFunction("emails::send-receipt", func(ctx context.Context, data json.RawMessage) (any, error) {
        var order Order
        if err := json.Unmarshal(data, &order); err != nil {
            return nil, err
        }
        return nil, sendReceipt(ctx, order.Email, order)
    })

    // After each successful call of orders::create, run emails::send-receipt with the order.
    worker.Observe(iii.Source{
        FunctionID: "orders::create",
        Deliver:    iii.DeliverInput,
    }, "emails::send-receipt")
    ```

The envelope always has the ids, `status`, and the timings. It has `input`, `output`, `error`,
`caller`, and `metadata` only when [`capture`](#capture) includes them. `output` is present only
after a successful call.

| Field                          | Meaning                                                                          |
| ------------------------------ | -------------------------------------------------------------------------------- |
| `observer_id`, `activation_id` | The observer, and this activation of it.                                         |
| `function_id`, `namespace`     | The observed function.                                                           |
| `invocation_id`                | The observed call.                                                               |
| `status`                       | `success` or `error`.                                                            |
| `input`, `output`, `error`     | The observed payload, its result, or its `{ code, message, stacktrace? }` error. |
| `caller`                       | Who made the observed call. See [Caller](#caller-and-causality).                 |
| `metadata`                     | The metadata of the observed call.                                               |
| `started_at_ms`, `duration_ms` | When the observed invocation started, and how long it ran.                       |

Some functions hand each call to one observer and use its target's result, for example
[`http::on-request`](#http-routes), which answers the request with it. Their targets receive what
the function documents (`http::on-request` targets receive the HTTP request).

### `capture`

`capture` sets which parts of the call the envelope carries: any of `input`, `output`, `error`,
`caller`, and `metadata`. The default is `["input", "output", "caller"]`. The ids, `status`, and the
timings are always there.

An observer that only counts calls, or only notes that they failed (`on: "error"`), uses
`capture: []`. Its envelope has the ids, `status`, and the timings, and no payload moves to its
target.

`capture` sets only what the target receives. A [filter](#filters) can read any field of the call.
To keep observed calls small, capture only what the target reads. See
[Observed call size](#observed-call-size).

### `on`

By default, the target runs only after a successful call of the observed function. `on` changes
this:

| `on`                | The target runs after           |
| ------------------- | ------------------------------- |
| `success` (default) | a successful call               |
| `error`             | a failed call                   |
| `complete`          | each call, successful or failed |

A cancelled call (for example, its caller stopped waiting) does not run the target, for any value of
`on`. The engine counts it as a dropped call with the reason `CANCELLED` in the
`iii.observer.dropped.total` metric.

The default `capture` does not include `error`. To give the target the error, add `error` to
`capture`. This observer runs `alerts::order-failed` after each failed call of `orders::create`. The
target receives the envelope with the order (`input`) and the error (`error`):

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    worker.observe(
      { function_id: "orders::create", on: "error", capture: ["input", "error"] },
      "alerts::order-failed",
    );
    ```

  </Tab>
  <Tab title="Python">
    ```python
    worker.observe(
        {"function_id": "orders::create", "on": "error", "capture": ["input", "error"]},
        "alerts::order-failed",
    )
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    use iii_sdk::{Capture, On, Source};

    worker.observe(
        Source::function("orders::create")
            .on(On::Error)
            .capture([Capture::Input, Capture::Error]),
        "alerts::order-failed",
    );
    ```

  </Tab>
  <Tab title="Go">
    ```go
    worker.Observe(iii.Source{
        FunctionID: "orders::create",
        On:         iii.OnError,
        Capture:    []iii.Capture{iii.CaptureInput, iii.CaptureError},
    }, "alerts::order-failed")
    ```

  </Tab>
</Tabs>

With `on: "complete"`, the target runs after each call, and the envelope's `status` is `success` or
`error`.

### Metadata and the return value

The observer's `metadata` option is the target's second argument (the `metadata` parameter in
Python, `MetadataFromContext(ctx)` in Go), on every activation, including a call through the
observer from a function's deliver hook. It is different from the `metadata` field of the envelope,
which is the metadata of the observed call: the envelope carries it when `capture` includes
`metadata`. See [Policy and metadata](#policy-and-metadata).

iii discards the target's return value, except for functions that use it:
[`http::on-request`](#http-routes) answers the request with it, and
[`queue::on-message`](#queue-messages) acks the message with it. Observers of the target can see the
return value as the `output` of the target's call. See [Chain reactions](#chain-reactions).

## Policy and metadata

`observe` takes an optional third argument, the policy. The policy sets limits for the observer
itself. An activation is one run of the target.

| Option          | Default                                | Meaning                                                                                                                                                                                                                                                                                                                                   |
| --------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`            | a random UUID                          | The observer id. The same id with the same options again changes nothing. The same id with different options, or an id that another worker's observer holds, fails with `OBSERVER_ID_CONFLICT`. With an id of your own, a restarted worker takes back its `suspended` observer (see [Observer states](#observer-states)).                 |
| `max_fires`     | unlimited                              | The observer becomes `disposed` after this number of activations (reason `MAX_FIRES`).                                                                                                                                                                                                                                                    |
| `expires_in_ms` | never                                  | The observer becomes `disposed` after this time (reason `EXPIRED`).                                                                                                                                                                                                                                                                       |
| `max_in_flight` | `observers.default_max_in_flight` (64) | The maximum number of activations that run at the same time. More activations wait in a queue of `observers.max_queue_per_observer` (1024). When the queue is full, or when the queues of all observers hold 64 MiB of observed calls, the engine drops new activations (`OVERFLOW`). With `1`, activations run in the order they arrive. |
| `metadata`      | none                                   | JSON that each activation gives to the target as its second argument. See [Metadata and the return value](#metadata-and-the-return-value).                                                                                                                                                                                                |

This observer runs `alerts::payment-failed` after each failed call of `payments::charge` with an
amount of 500 or more. It runs at most 4 activations at the same time, and it gives each activation
`{ "team": "billing" }` as metadata:

    ```go
        FunctionID: "payments::charge",
        On:         iii.OnError,
        Filters:    iii.Filters{"input.amount": iii.Op{"$gte": 500}},
        Capture:    []iii.Capture{iii.CaptureInput, iii.CaptureError, iii.CaptureCaller},
    }, "alerts::payment-failed", iii.ObserverOptions{
        MaxInFlight: 4,
        Metadata:    json.RawMessage(`{"team":"billing"}`),
    })
    ```

  </Tab>
</Tabs>

Each call runs the target at most once. The engine does not retry, unless the function documents its
own delivery (the [queue](#queue-messages) retries a message). A failure of the target does not
change the observed call. The engine counts each dropped call in the `iii.observer.dropped.total`
metric, by function and reason.

## Observer handle

`observe` returns a handle with the observer's `id` and `state`, and three methods:

- `ready()` resolves when the observer is `active`. It rejects with the reason's code when the
  observer turns `error` or `disposed` first (`ObserveRejection` in Node and Python, `Error::Remote`
  carrying the code in Rust, `*iii.ObserveRejectionError` in Go). In Python, `ready()` blocks; use
  `ready_async()` in asyncio code.
- `onStateChange(listener)` (`on_state_change` in Python and Rust, `OnStateChange` in Go) reports
  each state change with its reason, and returns a way to unsubscribe. Listeners run outside the
  connection's read path, so a listener can call the worker.
- `dispose()` (`Dispose(ctx)` in Go) removes the observer. A disposed observer is not replayed.

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    const newOrders = worker.observe("orders::create", "alerts::new-order");

    newOrders.onStateChange((state, reason) => {
      logger.info(`observer ${newOrders.id}: ${state}`, { reason });
    });
    await newOrders.ready();

    // later: remove the observer
    await newOrders.dispose();
    ```

  </Tab>
  <Tab title="Python">
    ```python
    new_orders = worker.observe("orders::create", "alerts::new-order")

    def log_state(state, reason):
        logger.info(f"observer {new_orders.id}: {state}")

    new_orders.on_state_change(log_state)
    new_orders.ready()

    # later: remove the observer
    new_orders.dispose()  # or: await new_orders.dispose_async()
    ```

  </Tab>
  <Tab title="Rust">
    ```rust

        println!("observer state: {state:?} {reason:?}");
    });
    new_orders.ready().await?;

    // later: remove the observer
    new_orders.dispose().await?;
    ```

  </Tab>
  <Tab title="Go">
    ```go

        log.Fatal(err)
    ```

A target that runs in the observing worker can stop its own observer: it calls `dispose()` on the
handle, or it calls `engine::observers::dispose` with the `observer_id` from the envelope. To stop
after a number of calls or after a time, set `max_fires` or `expires_in_ms` in the
[policy](#policy-and-metadata).

### Observer states

| State       | Meaning                                                                                                                                                                                            |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending`   | Waiting. No worker hosts the function yet (`OWNER_UNAVAILABLE`), the target is not registered yet (`TARGET_UNAVAILABLE`), or the worker that hosts the function has not accepted the observer yet. |
| `active`    | The target runs for each matching call.                                                                                                                                                            |
| `suspended` | The observing worker disconnected (`OBSERVER_DISCONNECTED`), or the target was removed after the observer was `active` (`TARGET_UNAVAILABLE`).                                                     |
| `error`     | Rejected. The reason has the code, for example `INVALID_ARGS`, `FORBIDDEN`, or a code from the function's worker.                                                                                  |
| `disposed`  | Removed permanently, by `dispose()`, `max_fires`, `expires_in_ms`, or because the observing worker did not reconnect in time.                                                                      |

- Registration order does not matter. An observer of a function whose worker has not started yet
  stays `pending`, and becomes `active` when the worker registers the function and accepts it.
- An observer belongs to the connection that created it. When that worker disconnects, its observers
  become `suspended` for `observers.observer_grace_ms` (30 s by default). If the worker reconnects
  in this time, it keeps its observers and their counters. If not, the observers become `disposed`.
- A worker that restarts connects again as a new connection. An observer with an `id` of your own
  (see [Policy and metadata](#policy-and-metadata)) comes back with it: the restarted worker, under
  the same worker name and namespace, observes under that `id` again, and its observer replaces the
  `suspended` one. A queue subscriber keeps its queued messages this way. An observer with a random
  `id` stays `suspended` until the grace period ends.
- The worker name has to stay the same across restarts for this. Set it with `III_WORKER_NAME` or
  the worker name option of the SDK; a worker that [iii compose](./compose) starts gets
  `III_WORKER_NAME` from it. The default name, `hostname:pid` (a random name in the browser), changes
  when the process restarts: the restarted worker's observe of the `id` then fails with
  `OBSERVER_ID_CONFLICT` until the grace period ends.
- When a worker reconnects, its SDK sends each of its observers to the engine again, with the same
  id. The engine remembers a `disposed` observer for `observers.disposed_retention_ms` (1 hour by
  default). In this time, the engine does not create the observer again, and the handle becomes
  `disposed`. So `max_fires` and `expires_in_ms` stay in effect after a reconnect. After this time,
  the engine creates the observer again with new counters, as after an engine restart.
- To know when an observer becomes `disposed`, and why, use `onStateChange` on its handle.
  `engine::observers::list` and `get` do not show disposed observers.
- When the worker that hosts the observed function disconnects, its observers go back to `pending`
  and become `active` again when the function is registered again.

## Built-in event sources

The standard workers represent their events as functions: an HTTP request is a call of
`http::on-request`, a cron tick is a call of `cron::on-tick`. Observe them like any function. Their
`args` say what the worker sets up for the observer.

| Function                   | Worker              | Runs when                                       | Args                                                          |
| -------------------------- | ------------------- | ----------------------------------------------- | ------------------------------------------------------------- |
| `http::on-request`         | http                | A request matches the observer's route.         | `{ method, path, middleware_function_ids?, public_webhook? }` |
| `cron::on-tick`            | cron                | The observer's schedule fires.                  | `{ expression }`                                              |
| `queue::on-message`        | queue               | A message is published to the observer's topic. | `{ topic, max_retries?, backoff_ms?, queue_config?, group? }` |
| `state::on-changed`        | state               | A key is created, updated, or deleted.          | none; filter on `input.scope` and `input.key`                 |
| `database::on-row-changed` | database            | A write commits.                                | `{ db, table?, ops? }`                                        |
| `publish`                  | pubsub (deprecated) | A message is published.                         | none; filter on `input.topic`                                 |

The other workers name their event functions `<worker>::on-<event>`, and each worker's page on
[workers.iii.dev](https://workers.iii.dev) lists them with their `args` and events.

Except `publish`, which publishers call, these functions are private: only the worker that
hosts one can call it, and a call from any other worker fails with `FORBIDDEN`. Every worker can
observe them. A private function cannot be an observer's target.

One function can be the target of any number of observers, of any functions. The same report can run
on a schedule and on an HTTP request, with one observer each.

### HTTP routes

Observe `http::on-request` with a method and a path to add a route. Each request that matches the
route runs the observer's target. The target receives the request (`HttpRequest`: `method`, `path`,
`path_params`, `query_params`, `headers`, `body`), and its return value is the response
(`{ status_code, headers?, body? }`).

| Arg                       | Required | Default | Meaning                                                        |
| ------------------------- | -------- | ------- | -------------------------------------------------------------- |
| `method`                  | yes      |         | The HTTP method to match, case insensitive.                    |
| `path`                    | yes      |         | The route path, for example `/orders/:id`.                     |
| `middleware_function_ids` | no       | `[]`    | Functions that run before the target, in this order.           |
| `public_webhook`          | no       | `false` | Also serve the route on the http worker's restricted listener. |

<Tabs>


- Each request goes to the one observer whose route matches it.
- The observer's filters read the request as `input`. A request that the filters reject gets a `422`
  response, and the target does not run.
- Two observers cannot hold the same method and path shape (`/a/:x` and `/a/:y` are one shape). The
  second one fails with `HTTP_ROUTE_CONFLICT`.
- `dispose()` removes the route.

### Schedules

Observe `cron::on-tick` with a cron `expression` to run a target on a schedule. The cron worker runs
one schedule per distinct expression, and each tick is a call of `cron::on-tick` with
`{ expression, scheduled_time, actual_time }`. A tick reaches the observers of its expression.

| Arg          | Required | Meaning                                                                               |
| ------------ | -------- | ------------------------------------------------------------------------------------- |
| `expression` | yes      | A cron expression with seconds: `sec min hour day-of-month month day-of-week [year]`. |

### Queue messages

Observe `queue::on-message` with a `topic` to consume it. Each observer is a subscriber of the
topic, with its own consumer, retries, and dead-letter queue. The target receives each message that
is published to the topic. Its result acks the message. An error retries the message with backoff,
and after `max_retries` the message moves to the topic's dead-letter queue.

| Arg            | Required | Default | Meaning                                                                                                                                  |
| -------------- | -------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `topic`        | yes      |         | The topic to consume.                                                                                                                    |
| `max_retries`  | no       | `3`     | Retries of a failed delivery before the message moves to the dead-letter queue.                                                          |
| `backoff_ms`   | no       | `1000`  | The base retry delay, in milliseconds. Retries back off exponentially.                                                                   |
| `queue_config` | no       |         | More subscriber settings, such as `type` (`fifo` or `concurrent`) and `concurrency`. See [queue](https://workers.iii.dev/workers/queue). |
| `group`        | no       |         | A consumer group. Observers with the same `group` share one consumer, so the group handles each message once.                            |

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript

      await fulfil(order); // returning acks the message; throwing retries it
      return { ok: true };
    });

    // Each message on orders.created runs orders::fulfil, with up to 3 retries.
    worker.observe(
      {
        function_id: "queue::on-message",
        args: { topic: "orders.created", max_retries: 3, backoff_ms: 1000, group: "fulfilment" },
      },
      "orders::fulfil",
    );
    ```

  </Tab>
  <Tab title="Python">

- The observer's filters read the message as `input`. A message that the filters reject is acked,

  them from its observer.
- `dispose()` stops the observer's consumer.

### State changes

### Row changes

Each committed write to a database of the database worker runs `database::on-row-changed` with the
change: `{ db, schema, table, op, affected_rows, returning?, truncated?, at }`. `op` is `insert`,
`update`, `delete`, or `other`. The example in [Args and filters](#args-and-filters) observes it.

| Arg     | Required | Meaning                                                                                    |
| ------- | -------- | ------------------------------------------------------------------------------------------ |
| `db`    | yes      | A database connection of the database worker.                                              |
| `table` | no       | The table, by its bare lowercase name (`orders`). Required on a `native` capture database. |
| `ops`   | no       | The operations to deliver: any of `insert`, `update`, `delete`, `other`.                   |

The database worker refuses an observer that it cannot serve, for example with `UNKNOWN_DB`. For
writes made through the database worker, `caller.parent` names the worker that made the write, so a
filter on `caller.parent.worker_name` can skip a worker's own writes. See
[database](https://workers.iii.dev/workers/database) for the capture modes and every code.

## Engine-hosted event sources

The engine hosts event sources as functions in the `default` namespace, and you observe them with
filters on the event. A worker in any namespace observes `engine::*` and `configuration::*` sources
without naming a namespace. For `observability::*` and `stream::*` sources, a worker in another
namespace names `namespace: "default"`.

| Function                              | Event                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `engine::on-functions-changed`        | `{ event: "functions_changed", functions: [{ function_id, namespace, worker_name, description?, metadata?, args_format?, private?, observable?, observer_count }] }`. `args_format`, `private: true`, and `observable: false` appear when the function sets them. Changes within about 100 ms are coalesced into one event. |
| `engine::on-workers-changed`          | `{ event, worker_id }`, `event` one of `worker_connected`, `worker_disconnected`, `worker_metadata_updated`                                                                                                                                                                                                                 |
| `engine::on-observers-changed`        | `{ observer_id, function_id, target, state, reason? }`, one event for each state change of an observer.                                                                                                                                                                                                                     |
| `configuration::on-updated`           | `{ type: "configuration", event_type, id, name, description, schema, old_value, new_value, metadata? }`. `event_type` is `configuration:registered`, `configuration:updated`, or `configuration:deleted`.                                                                                                                   |
| `observability::on-log`               | One log record: `severity_text`, `severity_number`, `body`, `attributes`, `service_name`, `trace_id`, `span_id`, ...                                                                                                                                                                                                        |
| `observability::on-span`              | `{ trace_ids: [...] }`: the traces that recorded spans in one window of about 300 ms.                                                                                                                                                                                                                                       |
| `stream::on-changed`                  | iii-stream (deprecated): `{ event_type, timestamp, stream_name, group_id, id?, event }`, `event_type` one of `create`, `update`, `delete`, `sync`.                                                                                                                                                                          |
| `stream::on-join`, `stream::on-leave` | iii-stream (deprecated): `{ event_type, timestamp, stream_name, group_id, id? }`.                                                                                                                                                                                                                                           |

Each of them is a private function whose handler returns the event. So `input` and `output` are both
the event, and `deliver: "input"` and `deliver: "output"` both give the target the event. Their
calls never fail: an observer with `on: "error"` is accepted, but its target never runs. Their
`request_format` is closed at the top level, so an `input.*` filter path that is not in the event
fails with `INVALID_FILTER_PATH`. Only the engine calls them. A call from a worker fails with
`FORBIDDEN`. The SDKs export their ids as `EngineSources`, for example
`EngineSources.WORKERS_CHANGED` in Node.

## Chain reactions

A call of a target is a normal call, so another observer can observe the target. In a chain, each
observer observes the target of the observer before it. In this example, the inventory worker
reserves the items of each new order, and the shipping worker schedules a shipment for each
reservation. Each worker registers its own function and observer.

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    // Inventory worker: after each successful call of orders::create, reserve the items.
    inventoryWorker.registerFunction("inventory::reserve", async (order: Order) => reserveItems(order));
    inventoryWorker.observe({ function_id: "orders::create", deliver: "input" }, "inventory::reserve");

    // Shipping worker: after each successful call of inventory::reserve, schedule the shipment.
    shippingWorker.registerFunction("shipping::schedule", async (reservation: Reservation) =>
      scheduleShipment(reservation),
    );
    shippingWorker.observe(
      { function_id: "inventory::reserve", deliver: "output" },
      "shipping::schedule",
    );
    ```

  </Tab>
  <Tab title="Python">
    ```python
    # Inventory worker: after each successful call of orders::create, reserve the items.
    inventory_worker.register_function("inventory::reserve", reserve_items)
    inventory_worker.observe({"function_id": "orders::create", "deliver": "input"}, "inventory::reserve")

    # Shipping worker: after each successful call of inventory::reserve, schedule the shipment.
    shipping_worker.register_function("shipping::schedule", schedule_shipment)
    shipping_worker.observe({"function_id": "inventory::reserve", "deliver": "output"}, "shipping::schedule")
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    // Inventory worker: after each successful call of orders::create, reserve the items.
    inventory_worker.register_function("inventory::reserve", RegisterFunction::new(reserve_items));
    inventory_worker.observe(
        Source::function("orders::create").deliver(Deliver::Input),
        "inventory::reserve",
    );

    // Shipping worker: after each successful call of inventory::reserve, schedule the shipment.
    shipping_worker.register_function("shipping::schedule", RegisterFunction::new(schedule_shipment));
    shipping_worker.observe(
        Source::function("inventory::reserve").deliver(Deliver::Output),
        "shipping::schedule",
    );
    ```

  </Tab>
  <Tab title="Go">
    ```go
    // Inventory worker: after each successful call of orders::create, reserve the items.
    inventoryWorker.RegisterFunction("inventory::reserve", reserveItems)
    inventoryWorker.Observe(iii.Source{FunctionID: "orders::create", Deliver: iii.DeliverInput}, "inventory::reserve")

    // Shipping worker: after each successful call of inventory::reserve, schedule the shipment.
    shippingWorker.RegisterFunction("shipping::schedule", scheduleShipment)
    shippingWorker.Observe(iii.Source{FunctionID: "inventory::reserve", Deliver: iii.DeliverOutput}, "shipping::schedule")
    ```

  </Tab>
</Tabs>

`inventory::reserve` returns the reservation. With `deliver: "output"`, `shipping::schedule`
receives that return value as its argument. To add a step, observe the last function in the chain.
To branch, add two observers to the same function. Each step adds 1 to the depth of the call. When
the depth is more than `observers.max_observe_depth` (8 by default), the engine drops the activation
with `LOOP_GUARD`. See [Loop guard](#loop-guard).

## Inspect observers

The engine lists observers through three built-in functions:

| Function                     | Input                                   | Returns                                                                                                                                                                   |
| ---------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `engine::observers::list`    | `{ function_id?, namespace?, worker? }` | `{ observers: [...] }`: id, observed function, args, normalized filters, target, observing worker, state, reason, fires, drops and activation failures by reason, policy. |
| `engine::observers::get`     | `{ id }`                                | One observer, or `OBSERVER_NOT_FOUND`.                                                                                                                                    |
| `engine::observers::dispose` | `{ id }`                                | Disposes an observer. Only the observing worker, or a caller without RBAC restrictions, may do it.                                                                        |

The output does not include the observer's `metadata` option. With RBAC, a session sees only the
observers of functions its grants cover.

```bash
iii call engine::observers::list function_id=orders::create
```

To react to observers as they change, observe
[`engine::on-observers-changed`](#engine-hosted-event-sources).

## Errors

When an observer cannot be created, it becomes `error`, and `ready()` fails with one of these codes:

| Code                   | When                                                                                                                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `UNSUPPORTED`          | The engine is older than 0.25 (the SDK gives this code), or `on`, `capture`, or `deliver` has a value that the engine does not know.                                                                                    |
| `INVALID_ARGS`         | `args` do not match the `args_format` of the function, or the function takes no `args`. Also: an empty or too-long observer id, an empty `function_id`, or `max_fires`, `expires_in_ms`, or `max_in_flight` set to `0`. |
| `INVALID_FILTER`       | The filter is not valid, uses a literal value in place of an operator object, or is larger than a limit.                                                                                                                |
| `INVALID_FILTER_PATH`  | A filter path is not in the function's closed `request_format` or `response_format`.                                                                                                                                    |
| `NOT_OBSERVABLE`       | The function is registered with `observable: false`.                                                                                                                                                                    |
| `FORBIDDEN`            | RBAC does not allow the session to call the observed function or the target, the registration hook refused the observer, or the target is a private function.                                                           |
| `SELF_TARGET`          | The target is the observed function.                                                                                                                                                                                    |
| `LIMIT_EXCEEDED`       | The worker has `observers.max_per_connection` observers (1024 by default), or the function has `observers.max_per_function` observers (4096 by default).                                                                |
| `OBSERVER_ID_CONFLICT` | An observer with the same id and different options exists, or another worker's observer holds the id. A restarted worker under the same name and namespace replaces its own `suspended` observer with this id.          |
| `OWNER_TIMEOUT`        | The worker that hosts the function did not accept the observer in 30 seconds.                                                                                                                                           |
| `OBSERVE_REJECTED`     | The hosting worker's `onObserverAdded` threw an error other than `ObserveRejection`.                                                                                                                                    |

A worker can also reject an observer with its own code, which its documentation lists (for example
`HTTP_ROUTE_CONFLICT` or `INVALID_CRON_EXPRESSION`).

## Observed call size

The engine keeps one copy of each observed call for all observers of the function. The copy has each
field that any of these observers captures or filters on. If observers capture `input` and `output`,
both count: a function that takes a 40 MiB input and returns a 40 MiB result makes an observed call
of about 80 MiB. The engine does not deliver an observed call in these cases:

- The fields the engine keeps come to more than 64 MiB (approximate in-memory size).
- The activation is larger than the target worker accepts in one message: 64 MiB, or 16 MiB for
  browser workers and some older SDKs. See
  [Payload size](../creating-workers/channels#payload-size).
- For calls that run in the function's own worker ([local dispatch](#local-dispatch)), that SDK's
  report of the call is larger than its 8 MiB report buffer.

Each such call counts as a `TOO_LARGE` drop in the `iii.observer.dropped.total` metric. In the first
two cases it also counts in the observer's `dropped` counts
([`engine::observers::list`](#inspect-observers)), and the engine logs a warning naming the
observer, the function, the size, and the limit, at most once a minute per observer. `OVERFLOW` is
different: the queues were full when the call arrived. A call of the same size can go through when
the queues have space again.

To keep observed calls small, capture only what the target reads, for example `capture: ["input"]`.
With `deliver: "input"` or `deliver: "output"`, set a matching `capture` too: captured fields are
kept even when the target receives one value. For payloads larger than these limits, pass a
[channel](../creating-workers/channels) reference in place of the data.

## Caller and causality

Every invocation carries a `caller`: the worker that made the call and, when the call was made from
inside a handler, the function and invocation it was made from.

```json
{
  "worker_id": "3f1c...",
  "worker_name": "billing",
  "function_id": "billing::close-invoice",
  "invocation_id": "c3f...",
  "parent": { "worker_name": "api", "function_id": "api::checkout", "invocation_id": "77..." }
}
```

The engine sets `worker_id` and `worker_name` from the calling connection. It replaces any values
that the SDK sends. The calling SDK sends `function_id`, `invocation_id`, and `parent` (the caller
of that handler, one level only). Use these 3 fields for routing and filters only. A filter such as
`{ "caller.parent.worker_name": { "$ne": "search-indexer" } }` stops an indexer from reacting to its
own writes.

When the engine activates a target, the target's caller is the engine (`worker_name: "iii-engine"`,
no `worker_id`), with the observed function and invocation as `function_id` and `invocation_id`. The
current invocation's `activation` holds the `observer_id` and `activation_id`.

The SDKs propagate the caller automatically from the handler you are in. Each SDK also exposes the
current invocation (`function_id`, `invocation_id`, `caller`, `activation`, `observe_depth`):

| SDK     | Current invocation               | Notes                                                                                                            |
| ------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Node    | `worker.currentInvocation()`     | Carried across `await` with `AsyncLocalStorage`.                                                                 |
| Browser | `worker.currentInvocation()`     | Known until the handler's first `await`. Read it first and wrap later calls in `worker.withInvocation(inv, fn)`. |
| Python  | `worker.current_invocation()`    | A `contextvars` context, carried into sync handlers' threads.                                                    |
| Rust    | `iii_sdk::current_invocation()`  | A task-local. Work moved to `tokio::spawn` loses it; wrap the future in `iii_sdk::scope(ctx, fut)`.              |
| Go      | `iii.InvocationFromContext(ctx)` | Pass the handler's `ctx` to `worker.Call` so outgoing calls carry the caller.                                    |

In the browser, a call made after an `await` and outside `withInvocation` gets the depth of the
deepest invocation that runs on the page. When several invocations run at the same time, this depth
can be too high, and the loop guard can stop an observer chain early. While the page is offline, the
functions that it hosts run locally, to a maximum of 256 nested calls. A call past that limit fails
immediately with `LOCAL_DEPTH_EXCEEDED`.

## Loop guard

An observer's target can call the observed function again, directly or through other observers. This
makes a loop. To stop loops, every invocation carries an `observe_depth`, which increases by 1 on
each activation. Activations deeper than `observers.max_observe_depth` (8 by default) are dropped
and counted as `LOOP_GUARD`, and an observer whose target is the observed function itself is
rejected at creation with `SELF_TARGET`.

<Warning>
  Workers on SDKs older than 0.25 do not send the depth. For their calls, the engine uses the
  largest depth of the invocations still in flight on that worker.
</Warning>

## Local dispatch

When a worker calls a function that it registered, the SDK runs the handler in the same process. The
call does not go through the engine. If the function has no observers, the SDK sends nothing to the
engine. If the function has observers, the SDK applies their filters and sends the matching calls to
the engine in batches. Observers get local calls and engine calls in the same way.

<Note>
  The hosting SDK reports the observed values of local calls to the engine. Values JSON cannot hold,
  such as a number no double can represent, arrive as `null`, and a lone surrogate in a string or
  key arrives as U+FFFD. Filters read the values the same way. Reports are at most once: a report
  lost with a dropped connection is not sent again.
</Note>

A call runs locally when all of these hold:

1. This worker registered the function with a handler. HTTP-invoked functions always go through the
   engine. Local dispatch is on for the function.
2. The engine confirmed local dispatch for the registration. This requires an engine at 0.25 or
   later with `observers.local_dispatch` on. If the worker connects through RBAC, its session must
   have no `middleware_function_id`, and the session must be allowed to call the function.
3. The call resolves to the namespace the function is registered in.
4. The action is `Void` or a normal call. An `Enqueue` call always goes through the engine.
5. The call does not ask for the remote path.
6. The call is fewer than 64 local calls deep. Deeper calls go through the engine.

A local call returns the same result, error shape, and timeout as a remote one. The differences are
in [Upgrading from 0.24.x](../upgrading/from-0-24-x#local-dispatch). To keep a function on the
engine path:

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    // per function
    worker.registerFunction("reports::build", buildReport, { localDispatch: false });

    // per call
    await worker.call({ function_id: "reports::build", payload, dispatch: "remote" });
    ```

  </Tab>
  <Tab title="Python">
    ```python

    worker.register_function("reports::build", build_report, local_dispatch=False)

    # per call
    worker.call({"function_id": "reports::build", "payload": payload, "dispatch": "remote"})
    ```

  </Tab>
  <Tab title="Rust">
    ```rust

    use iii_sdk::{Dispatch, RegisterFunction};

        "reports::build",

    );
    ```

  <Tab title="Go">

## Make something observable

To make something observable, register a function whose handler returns the event, and call that
function whenever the thing happens. Each call runs the observers of the function. With
`private: true`, only your worker can call the function, and every worker can observe it.

<Tabs>
  <Tab title="Node / TypeScript">
    ```typescript
    type FileChanged = { path: string; event: "created" | "modified" | "deleted" };

    // Producer: a function that returns the change it is called with.
    worker.registerFunction("files::on-change", (change: FileChanged) => change, { private: true });

    // ...in your watcher loop, call it for each change.
    await worker.call({ function_id: "files::on-change", payload: { path, event: "modified" } });

    // Consumer, in any worker: when a file changes, process it.
    worker.observe("files::on-change", "csv::process");
    ```

  </Tab>
  <Tab title="Python">
    ```python
    # Producer: a function that returns the change it is called with.
    worker.register_function("files::on-change", lambda change: change, private=True)

    # ...in your watcher loop, call it for each change.
    worker.call({"function_id": "files::on-change", "payload": {"path": path, "event": "modified"}})

    # Consumer, in any worker: when a file changes, process it.
    worker.observe("files::on-change", "csv::process")
    ```

  </Tab>
  <Tab title="Rust">
    ```rust
    use iii_sdk::protocol::CallRequest;
    use iii_sdk::{Error, RegisterFunction};
    use serde_json::{Value, json};

    // Producer: a function that returns the change it is called with.
    worker.register_function(
        "files::on-change",
        RegisterFunction::new(|change: Value| Ok::<_, Error>(change)).private(),
    );

    // ...in your watcher loop, call it for each change.
    worker
        .call(CallRequest::new("files::on-change", json!({ "path": path, "event": "modified" })))
        .await?;

    // Consumer, in any worker: when a file changes, process it.
    worker.observe("files::on-change", "csv::process");
    ```

  </Tab>
  <Tab title="Go">
    ```go
    // Producer: a function that returns the change it is called with.
    worker.RegisterFunction("files::on-change", func(ctx context.Context, data json.RawMessage) (any, error) {
        return data, nil
    }, iii.FunctionOptions{Private: true})

    // ...in your watcher loop, call it for each change.
    worker.Call(ctx, iii.CallRequest{
        FunctionID: "files::on-change",
        Payload:    json.RawMessage(`{"path":"/data/orders.csv","event":"modified"}`),
    })

    // Consumer, in any worker: when a file changes, process it.
    worker.ObserveFunction("files::on-change", "csv::process")
    ```

  </Tab>
</Tabs>

A function can also set something up for each observer from its `args`, for example watch only the
paths its observers name, or decide which observers get each call. See
[Observable functions](../creating-workers/observable-functions). You observe such a function the
same way, with [args](#args).

## Authorization

If your worker connects with RBAC, it can observe a function only when its grants
(`expose_functions`, `namespaces`) cover both the observed function and the target. Otherwise
`observe` fails with `FORBIDDEN`. A private function is observable by any session whose grants cover
it. When the observed function or the target registers again later, the engine does the check again.
To change or deny observers in the RBAC configuration, see
[Worker manager](../creating-workers/worker-manager#intercept-calls-with-middleware).

## Compatibility

- With an engine older than 0.25, `observe` fails with `UNSUPPORTED`.
- With a 0.25 engine, observers work. A function registered with `args_format`, `private: true`, or
  `observable: false`, or that sets `onObserverMatch` or `onObserverDeliver`, needs a 0.26 engine:
  the SDK does not register it on a 0.25 engine, so its observers stay `pending`. The
  [built-in event sources](#built-in-event-sources) are such functions.
- Functions hosted by workers on older SDKs are observable. The engine evaluates the filters for
  routed calls of functions hosted on SDKs without `observe.v2`, and the hosting SDK reports its own
  local calls.
- Workers on SDKs older than 0.25 cannot observe.
