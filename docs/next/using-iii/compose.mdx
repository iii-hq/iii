Compose runs a group of workers as one project. The daemon reads a `worker-compose.yaml`, is able to
resolve, start, and stop each worker in dependency order, handles engine registration tasks, and
supervises running workers.

## The daemon

The daemon is itself a worker. It registers under the name `compose` and exposes the `compose::*`
functions, so every project operation is a standard [function call](./functions#call-a-function).

Bare `iii compose` is the command to start the compose worker/daemon. It reads `worker-compose.yaml`
in the working directory and starts only the compose worker.

`iii compose --up` is provided as a convenience. It starts the compose worker, the iii engine, and
the workers specified in `worker-compose.yaml`. It is approximately the equivalent of running `iii`,
`iii compose`, and `iii call compose::up` as separate commands.

`iii compose --up` combines engine and project startup for development. Independent `iii` and
`iii compose` daemons provide separate lifecycle control for production deployments.

The engine that `--up` starts is tied to the Compose process. If Compose exits for any reason,
including an abrupt kill such as `SIGKILL` during startup, the managed engine is terminated too, and
the next `iii compose --up` starts a fresh engine. Run `iii` and `iii compose` separately when the
engine needs its own lifecycle.

Workers are tied to the Compose process in the same way. Compose starts a small reaper process next
to its workers. When Compose exits without stopping them, whether from `SIGKILL`, a crash, or a
second `Ctrl^C`, the reaper sends each worker `SIGTERM`, waits up to 10 seconds, then sends
`SIGKILL`. A worker's child processes stop with it. A worker that is still running when Compose
starts again, left by a Compose that is gone, is stopped and started fresh rather than reused. The
reaper runs on Linux and macOS.

### Starting a project with the daemon

```text
iii compose [OPTIONS]
```

| Option                 | Description                                                                                                                                              |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--engine <URL>`       | Existing engine WebSocket address. Overrides the compose file and III_URL. The local default is used when none of them supplies a URL                    |
| `-n, --namespace <NS>` | Namespace this daemon answers `compose::*` in and applies to every project it loads. Several daemons attach to one engine; this is what tells them apart |
| `--up`                 | Serve with one project brought up first, starting its declared engine unless `--engine` selects an existing one                                          |
| `--frozen`             | With `--up`, require the compose file and existing lock to match and skip package resolution                                                              |
| `-f, --file <PATH>`    | The compose file. Only valid with `--up`. Defaults to `./worker-compose.yaml`, the same fallback `compose::up` uses when a call names no file            |

`Ctrl^C`, `SIGINT`, `SIGTERM` and `SIGHUP` all gracefully stop the daemon, every worker run by the
daemon, and the iii engine if compose was started with `--up`. When `--up` has started the engine,
every project and worker stops before the engine process is stopped. `compose::stop` is the function
equivalent of this operation.

A second signal during that shutdown makes Compose exit at once, and the reaper stops the remaining
workers. Signals that arrive within 200 milliseconds of the first count as the same request: a
wrapper such as `dotenv --` or a package-manager script forwards the terminal's `Ctrl^C` to Compose,
which already received it, and one key press must not skip the orderly shutdown.

Compose only stops an engine it started itself. An external engine, selected with `--engine`,
`III_URL`, or an external engine in the compose file, keeps running when Compose exits. If the
engine's listener port is already in use, `--up` fails. Compose never adopts or kills an unrelated
engine.

`compose::*` functions as documented below are the intended way to manage a running compose daemon.

### Process names on Linux

Compose includes its resolved namespace in the process label. The daemon uses `iii:c:<namespace>`,
and an engine started by that daemon uses `iii:e:<namespace>`. The namespace comes from
`--namespace`, then `namespace:` in the compose file, then `default`.

For example, `iii compose --namespace orders --up` produces these labels when it starts an engine:

```text
iii:c:orders
  +-- iii:e:orders
```

Use `ps -p <PID> -o pid,ppid,comm,args` to inspect both fields. The `args` field retains the full
namespace and the original command arguments. Linux limits `comm` to 15 bytes, so namespaces longer
than nine characters use their first two characters, `~`, and six hexadecimal hash characters in
that field. Use `args` to read the full namespace when a short label is abbreviated.

The daemon sets its command label through an early re-exec with the same PID, before starting
the runtime or any children. Existing external engines keep their names. On other operating
systems, process names retain their previous behavior.

### Compose logs

Compose logs stdout and stderr output from started workers to `logs/` in the state directory.
The default state directory is `<project-dir>/.iii/compose/<namespace>/`. When `III_COMPOSE_STATE_DIR`
is set, it is `$III_COMPOSE_STATE_DIR/<project-slug>/<namespace>/`. The managed engine writes to
`engine.log` in that same state directory.

Logs are rotated every 10 MiB. Compose keeps up to 40 MiB of logs. Compose strips terminal control
sequences before persisting the engine output.

You can use the logs client for a recent snapshot or a live view:

```bash
iii compose logs                         # last 100 lines from every worker
iii compose logs queue --tail 200        # one worker
iii compose logs queue --follow          # keep waiting for new output
iii compose logs queue --stream stderr   # only stderr
iii compose logs queue --namespace dev --engine ws://127.0.0.1:49134
```

| Option                 | Description                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------- |
| `[WORKER]`             | Worker to read. Omit to read every worker in the project                              |
| `--engine <URL>`       | Existing engine WebSocket address. The compose file and III_URL are used when omitted |
| `-n, --namespace <NS>` | Namespace of the Compose daemon that owns the project                                 |
| `-f, --file <PATH>`    | Compose file path on the daemon host. The daemon's default file is used when omitted  |
| `--tail <TAIL>`        | Number of recent lines to show before following new output [default: 100]             |
| `-F, --follow`         | Continue waiting for new output until interrupted                                     |
| `--stream <STREAM>`    | Restrict output to one process stream [possible values: stdout, stderr]               |

Each line is prefixed with the worker name, and stderr uses a bold prefix on a terminal.

### Running it in the background

Compose does not background or daemonize itself.

Standard process-management tooling, such as shell backgrounding or systemd, runs the daemon
in the background. Bash and zsh support the following invocation:

```bash
iii compose --namespace dev --engine ws://127.0.0.1:49134 >> ~/iii-compose.log 2>&1 &
```

Or on a server with systemd support you can use a unit file. This is a basic example:

```ini
[Unit]
Description=iii compose
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/iii compose --namespace prod --engine ws://127.0.0.1:49134
Restart=always

[Install]
WantedBy=multi-user.target
```

<Warning>
  Use `Type=simple`. `Type=notify` waits for an `sd_notify` readiness message, which compose does
  not send.
</Warning>

## The `compose::*` functions

These are the functions that control the compose worker and are the canonical way of interacting
with it and making basic changes to the `worker-compose.yaml` file.

| Function            | Takes                                                       | Returns                                                                    |
| ------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| `compose::up`       | `file`, `container`, `frozen`                               | An operation result.                                                       |
| `compose::down`     | `file`, `container`                                         | An operation result.                                                       |
| `compose::status`   | `file`                                                      | Namespace, file, state directory, daemon pid, host targets, worker states. |
| `compose::ps`       | `file`                                                      | The daemon pid and the operating-system processes of its projects.         |
| `compose::logs`     | `file`, `container`, `cursors`, `tail`, `stream`, `wait_ms` | Bounded stdout/stderr entries and one cursor per worker.                   |
| `compose::list`     | nothing                                                     | The daemon name, namespace, pid, host targets, and every project it holds. |
| `compose::validate` | `file`                                                      | A validation report.                                                       |
| `compose::add`      | `file`, `workers`                                           | What the edit did, changed workers restarted, and new workers started.     |
| `compose::remove`   | `file`, `worker`                                            | The worker removed, its targeted stop, and the idempotent `up`.            |
| `compose::restart`  | `file`, `container`                                         | The `down` and the `up`, or one worker's restart.                          |
| `compose::update`   | `file`, `worker`                                            | The resolved version and a restart when the package content changed.       |
| `compose::build`    | `file`, `worker`, `operation_id`                            | An accepted operation; per-container build results when it finishes.       |
| `compose::stop`     | nothing                                                     | The daemon name, its pid, and the projects it is about to stop.            |
| `compose::schema`   | `function_id`                                               | Request/response JSON Schemas, descriptions, timeouts, and retry safety.   |

`file` is not required. Left out, it names the project the daemon serves when it holds exactly one,
such as the file it was started with by `iii compose --up -f worker-compose.dev.yaml`. A daemon that
holds no project falls back to a `worker-compose.yaml` in its own working directory, and fails with
`NO_COMPOSE_FILE` without one. A daemon that holds several projects uses that `worker-compose.yaml`
when it is one of them, and otherwise fails with `COMPOSE_FILE_AMBIGUOUS`, which lists them. A
relative `file` path is considered relative to the daemon's directory, not the caller's working
directory. You may pass an absolute path as well.

```bash
iii call compose::up      --namespace dev file=./worker-compose.yaml
iii call compose::up      --namespace dev file=./worker-compose.yaml frozen=true
iii call compose::up      --namespace dev file=./worker-compose.yaml container=api
iii call compose::status  --namespace dev file=./worker-compose.yaml
iii call compose::logs    --namespace dev file=./worker-compose.yaml worker=api tail=100
iii call compose::down    --namespace dev file=./worker-compose.yaml
iii call compose::list    --namespace dev
iii call compose::add     --namespace dev file=./worker-compose.yaml worker=database worker=web
iii call compose::remove  --namespace dev file=./worker-compose.yaml worker=state
iii call compose::restart --namespace dev file=./worker-compose.yaml
iii call compose::build   --namespace dev file=./worker-compose.yaml worker=onboarding
iii call compose::schema  --namespace dev function_id=compose::up
iii call compose::stop    --namespace dev
```

### Starting a project

`compose::up` starts every worker in the compose file, in dependency order. Workers that are already
ready stay as they are.

| Field       | Description                                                                                  |
| ----------- | -------------------------------------------------------------------------------------------- |
| `file`      | The project to start.                                                                        |
| `container` | Starts that worker and the workers it depends on, and nothing else.                          |
| `frozen`    | Requires a current `worker-compose.lock` and does not resolve package selectors when `true`. |

A container whose `scripts.build` has no `.iii/build/<container>/build.json` yet gets its first
build before it runs. The operation reports the build as a `building` step of that container. See
[The first build](#the-first-build).

#### compose::up failures

A worker is not required by default. If it fails to start, its failure is reported against that
worker, nothing is rolled back, and the operation still returns `ok`. Workers that name it in
`start_after` start anyway, because `start_after` is a start order and not a claim that the dependent
cannot run without it. The response lists every worker that failed this way in
`not_required_failures`. A response with `status: ok` has no top-level `error`; that field is present
only when the operation returns `status: failed`.

Set `required: true` when a worker must fail the operation:

```yaml
containers:
  database:
    worker: path://./workers/database
    required: true
```

A required failure ends the command with `PROJECT_DID_NOT_START`. Partial starts are rolled back in
reverse dependency order.

Use `required_default` to change the fallback for all containers in the file. An explicit container
value wins over the file value:

```yaml
required_default: true

containers:
  queue:
    worker: package://queue
    version: "0.21.9"
    required: false
  state:
    worker: package://state
    version: "0.22.5-rc.1"
```

In this example, `state` inherits `required_default: true`, while `queue` remains false. If both
fields are absent, the effective value is false.

#### Retrying a worker that fails

By default, a failed first start settles immediately. A worker that exits after it was ready takes
its dependents down with it and stays down. To retry either case, declare a restart policy:

```yaml
containers:
  api:
    worker: path://./workers/api
    restart: on-failure
```

`no` is the default. `on-failure` retries a failed start or a worker that exits with a non-zero
status. `always` also restarts it when it exits successfully after it was ready.

The short form uses five attempts, a 500ms base delay, a 30-second maximum delay, and a 60-second
stability window. Use the object form to change these values for one worker:

```yaml
containers:
  api:
    worker: path://./workers/api
    restart:
      condition: on-failure
      delay: 500ms
      max_delay: 30s
      max_attempts: 5
      window: 60s
```

| Field | Description | Default |
| ----- | ----------- | ------- |
| `condition` | Required in the object form. Accepts `no`, `on-failure`, or `always`. | `no` in the short form |
| `delay` | Base delay for exponential backoff after a replacement fails. | `500ms` |
| `max_delay` | Maximum delay between replacement attempts. | `30s` |
| `max_attempts` | Maximum replacement attempts after the original process fails. | `5` |
| `window` | Time a ready worker must stay active before its run-time attempt budget resets. | `60s` |

The first replacement is immediate. If it fails, later attempts use exponential backoff from
`delay` up to `max_delay`. During `up`, the progress row shows the current attempt and wait. For a
run-time exit, only the named worker bounces: workers that name it in `start_after` keep running and
see their connection drop and reconnect. VM workers cannot outlive the sandbox adapter: when it
crashes and its own policy restarts it, they exit with it and each one follows its own policy, so a
VM worker with no policy ends `failed` and one with `restart: always` spends an attempt.
`compose::status` reports the worker as `restarting` while it waits for a run-time replacement. Once
`max_attempts` is spent, `required` controls whether the startup operation fails. At run time, the
worker is marked `failed`, its dependents are stopped, and `last_error` says the supervisor gave up.

### Stopping a project

`compose::down` stops the project in reverse dependency order.

| Field       | Description                                                            |
| ----------- | ---------------------------------------------------------------------- |
| `file`      | The project to stop.                                                   |
| `container` | Stops that worker and the workers that depend on it, and nothing else. |

### Adding workers

`compose::add worker=state worker=./workers/api` declares one or more workers in the compose file
and reconciles the project once. On the CLI, repeat `worker=` for each worker. Each value takes a
registry package name (`state`), a package name with a version (`state@0.21.4`), or a directory
(`./workers/api`).

A JSON payload can mix worker names and container objects in the same list. Each object accepts
the container fields from `worker-compose.yaml`. The container key comes from the last part of
the worker name or directory path.

```bash
iii call compose::add --namespace dev file=./worker-compose.yaml --json '{
  "workers": [
    "database",
    {
      "worker": "./workers/api",
      "start_after": ["database"],
      "scripts": {
        "pre_run": "pnpm build",
        "pre_run_timeout": "60s",
        "run": "pnpm start",
        "post_run": "echo stopped"
      },
      "config_name": "api",
      "config_override": { "port": 3000 },
      "working_dir": "./workers/api",
      "environment": { "NODE_ENV": "development" },
      "env_file": ["./api.env"],
      "startup_timeout": "30s"
    }
  ]
}'
```

| Field     | Description                                    |
| --------- | ---------------------------------------------- |
| `file`    | The project to edit.                           |
| `workers` | A JSON list of worker names or container objects. |
| `worker`  | One worker. Repeatable on the CLI.             |

A container object accepts these fields:

| Field             | Description                                                                                                                         |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `worker`          | Required. A package name, `name@version`, registry reference, or local path. Also accepts `package://` and `path://` sources.       |
| `version`         | Package version. Must agree with a version included in `worker`.                                                                    |
| `start_after`     | Container keys to start first. Compose adds the package's resolved dependencies to this list.                                       |
| `scripts`         | `pre_run`, `pre_run_timeout`, `build`, `build_timeout`, `run`, and `post_run`. `build` and `run` are refused for `binary` packages. |
| `config_name`     | Name of the worker's base configuration.                                                                                            |
| `config_override` | Configuration value applied over the base configuration.                                                                            |
| `working_dir`     | Working directory, relative to the compose file.                                                                                    |
| `environment`     | Environment variables with string values.                                                                                           |
| `env_file`        | List of environment file paths, relative to the compose file.                                                                       |
| `startup_timeout` | Maximum wait for worker registration, such as `30s`.                                                                                |

A package without a version pins to the latest available version, for example `0.23.1`. An explicit
selector such as `state@next` stays as `next` in `worker-compose.yaml`.
Unknown fields and invalid field types are rejected. Compose validates the complete edited file
before it writes any changes.

For an existing container, omitted fields other than `version` keep their values. A supplied field replaces that entire
field, including maps such as `scripts`, `environment`, and `config_override`. Use `{}` or `[]` to
clear maps or lists. An omitted `start_after` keeps existing dependencies; a supplied list replaces
them and includes any required package dependencies.

Workers whose declarations did not change remain running. Existing workers whose source, version,
dependencies, or settings changed restart in place. Newly declared workers start through the normal
dependency plan. If the resolved declaration already matches the file, the call makes no file
changes and causes no restart.

For a VM worker, `compose::add` writes the explicit VM mode into the file: the adapter's container
key in `start_after`, `scripts.build: iii sandbox build`, and `scripts.run: iii sandbox run`. Other
keys you set are kept. The container gets its first build when it starts. [VM workers](#vm-workers)
lists which containers run in a VM.

### Package lock

Compose writes `worker-compose.lock` beside `worker-compose.yaml`. The compose file keeps the
requested selector. The lock keeps the resolved dependency graph, versions, package types,
artifact URLs, SHA-256 digests, and default configuration returned by the registry.

```text
worker-compose.yaml: next
          |
          v
worker-compose.lock: 0.22.8 + SHA-256
          |
          v
package cache: verified artifact
```

Normal starts and restarts use the lock without resolving `next` again. If the cache is empty,
Compose downloads the URL in the lock and verifies its SHA-256 digest. Compose also verifies the
extracted cache contents before reuse. A changed cache entry is downloaded again from the locked
URL.

Each project also gets a copy of every locked package in `.iii/workers/<container>/`. See
[The project tree](#the-project-tree).

Use `iii compose build --frozen` in CI to require the compose file and lock to match. Use
`iii compose --up --frozen` or `compose::up frozen=true` to apply the same rule during startup.
Frozen mode never resolves selectors, changes the lock, or edits the compose file. It can download a
missing artifact only from the URL already in the lock. A file with a container that Compose would
rewrite into the explicit VM mode fails under frozen mode with `VM_SCRIPTS_MISSING`. See
[Rewriting files from older releases](#rewriting-files-from-older-releases). Commit the lock so
development, CI, and deployments use the same package content.

### Removing a worker

`compose::remove worker=state` removes the named worker and every reference to it. The changes are
validated before a worker is removed. Compose then stops only that worker and runs an idempotent
`up`.

Compose first stops a build of that container that is still running, from `compose::build` or a
first build. Until the remove ends, a start or rebuild of that container gives up. Removing a
container also deletes its `.iii/build/<container>/` and `.iii/workers/<container>/` directories.
For a VM worker, Compose has the sandbox adapter destroy the VM's data disk.

| Field    | Description           |
| -------- | --------------------- |
| `file`   | The project to edit.  |
| `worker` | The worker to remove. |

Removal does not resolve the registry graph or remove other workers that were added with this
worker. Those remain declared until they are removed explicitly.

### Restarting one worker

`compose::restart worker=state` stops that specified worker and starts it again. All other workers,
including dependencies, are left unchanged. A restart never runs `scripts.build`.

The sandbox adapter is the one exception, because a VM worker ends with the adapter that hosts it.
A VM worker is a container whose `scripts.run` is `iii sandbox run`.
`compose::restart worker=sandbox-libkrun` restarts the adapter and then each VM worker it was
running, dependencies first, without spending any of their `restart` attempts. The response names
those workers in `affected_workers`. A `required` VM worker that does not come back fails the
operation. Otherwise, one that does not come back is listed in `not_required_failures`. If the adapter
itself does not come back, no VM worker is started and those same rules apply to each one it was running, which
`compose::status` then reports as `failed`, with a `last_error` that names the adapter. Once
the adapter is fixed, `compose::up` starts them all again. A sandbox that was running under the adapter does not come back.

`compose::restart` without a worker argument restarts the entire compose project. It is
approximately the equivalent of `compose::down` followed by `compose::up`.

| Field    | Description             |
| -------- | ----------------------- |
| `file`   | The project to restart. |
| `worker` | The worker to restart.  |

### Updating workers

`compose::update` without `worker` or `workers` updates every declared `package://` worker to its
registry's latest version. It keeps each worker's registry reference and skips `path://` workers.
The container that runs the sandbox adapter (`sandbox-libkrun`, or the one `engine.sandbox.adapter`
names) moves only to the newest release in `^0.4`, the releases that implement sandbox contract 1.3
with `worker.build`.

```bash
iii call compose::update
iii call compose::update file=worker-compose.yaml
```

`compose::update worker=state` resolves the selector already in the compose file. A tag such as
`next`, a range, and an exact version all remain unchanged in the file. Use
`worker=state@<selector>` to change the selector. For example, use `worker=state@latest` to move an
exact version to the registry's latest channel.

Update resolves the complete dependency graph. It adds new dependencies, updates changed
dependencies, and removes stale dependencies that Compose generated and no remaining package root
uses. Manually declared workers are not removed.

Compose downloads and verifies the new artifact before it changes the lock or stops a worker. A
failed resolve or download leaves the prior lock and running workers unchanged. If the resolved
artifact and default configuration did not change, Compose updates lock metadata when needed and
does not restart the project.

An update that changes the package of a container with a non-empty `scripts.build` rebuilds it
before restarting it, and logs `<container>: package changed (<old> -> <new>); rebuilding`.
`compose::add` does the same when it changes a container's package. See [Rebuilds](#rebuilds) for a
rebuild that fails or is cancelled.

If all selected workers already use the requested versions, the operation leaves the file and
running processes unchanged, unless an earlier add or update left a rebuild unfinished. See
[Rebuilds](#rebuilds). A project with only `path://` workers also stays unchanged.

| Field     | Description                                                   |
| --------- | ------------------------------------------------------------- |
| `file`    | The project to edit.                                          |
| `worker`  | Optional worker spec: `name` or `name@version`.                 |
| `workers` | Optional non-empty list of specs. Takes precedence over `worker`. |

```text
worker=state            resolve the selector already declared in the compose file
worker=state@0.21.4     that version, which is also how a downgrade is spelled
worker=state@next       the version currently selected by the next tag
worker=state@latest     the version currently selected by the latest tag
```

The worker has to be declared already in order to be updated, and it has to be a `package://`. Use
[`compose::add`](#adding-workers) to add new workers.

Workers specified with `path://` are not versioned, any updates to these workers will be reflected
the next time the worker is restarted.

<Note>An update that changes package content or graph topology restarts the whole project once.</Note>

### Building workers

`compose::build` runs `scripts.build` for one container, or for every container that has a
non-empty one. It is a mutation, like `compose::restart`.

```text
iii call compose::build [file=<path>] [worker=<container>]
```

| Field          | Description                                                                 |
| -------------- | --------------------------------------------------------------------------- |
| `file`         | The project to build.                                                       |
| `worker`       | A container key. Omitted, every container with a non-empty `scripts.build`. |
| `operation_id` | Optional, as for other mutations.                                           |

- It is asynchronous. It answers `{ operation_id, status: "accepted", requested }`, holds the
  project's mutation lock while it runs, and reports progress per container (`building`, `built`,
  `failed`) through `compose::on-operation-progress`.
- A container whose `scripts.build` is `""` is reported as `skipped`.
- It starts the adapter first when the project is down, as `compose::remove` does.
- It never restarts a container. A running container keeps its current build until it restarts.
- `compose::cancel` of the operation and `compose::down` stop it, and `compose::remove` stops the
  build of the containers it removes. Compose stops the `iii sandbox build` processes, which aborts
  their builds. `down` cancels a running `compose::build` first, then takes the lock.

The finished operation carries one result per container:

```text
results: [{ worker, status: "built" | "failed" | "skipped", build_id?, error?: { code, message } }]
```

`iii sandbox build <container>`, run outside Compose, calls this function and waits for its result.
See [Sandboxes](../creating-workers/sandboxes#build-an-image-with-iii-sandbox-build).

### Checking status

`compose::status` reports each declared worker with its `state`, its `version` (the locked package
version, or `local` for a `path://` worker), its `requested` selector, the active process `pid` when
one exists, an `owned` flag, its rotating `log_path`, and `last_error` when there is one. `owned` is
`false` for a worker this daemon has knowledge of but does not manage (ie. was not started by the
compose daemon).

`requested` is the `version` a `package://` worker declares in `worker-compose.yaml`, after variable
expansion: a tag such as `latest`, a semver range, or an exact version. It is the selector that
`compose::update worker=<name>` resolves again, so the release it selects now is the version that
call moves to; a release outside it needs `worker=<name>@<selector>`. A `compose::update` without
`worker` or `workers` resolves `latest` for every package instead. `version` is present only while
the lock holds a result for that selector, so a worker whose selector changed in the file reports no
`version` until Compose resolves it. A `path://` worker reports no `requested`.

The response also carries the platform Compose resolves packages for. `target` is the target triple
the daemon sends first as `target` to the registry's `POST /resolve`. `targets` lists every triple
the host runs, preferred first: a static musl build of iii on a glibc Linux host lists
`x86_64-unknown-linux-musl`, then `x86_64-unknown-linux-gnu`, and Compose resolves for the second

checks the registry for updates itself can follow the same order to find a build Compose would
install. Both fields are absent when iii has no target triple for the platform it was built for.

#### Worker states

| State        | Meaning                                                                                       |
| ------------ | --------------------------------------------------------------------------------------------- |
| `starting`   | Spawned. The engine has not registered it yet.                                                |
| `ready`      | Registered in the engine under `(namespace, container)`.                                      |
| `restarting` | Waiting for the next configured retry. No process or PID is active.                           |
| `failed`     | Exited unsuccessfully with no eligible retry, exhausted its retries, failed to start during `up` or a restart before it registered (a failed `pre_run` hook included), or did not register again within its `startup_timeout` after an engine reconnect and was stopped. After a daemon restart, also a worker that exited while the daemon was away or while it was being adopted, or whose live PID Compose cannot prove is the one it started. That process is left running and never signalled. `last_error` says why. |
| `stopped`    | Stopped by the daemon, or exited successfully without an eligible restart.                    |

### Listing processes

`compose::ps` lists what the operating system sees for this daemon's projects, or for one project
when `file` is set: the daemon, its managed engine, every worker, and the processes those workers
started. Each entry has `pid`, `ppid`, `kind` (`engine`, `compose` or `worker`), `name` (the worker's
container key), `ports`, `compose_file`, `orphan`, `started_at` (seconds since the Unix epoch), and
`command`. `orphan` is `true` for a worker of the project that no Compose daemon supervises.

```bash
iii call compose::ps --namespace dev file=./worker-compose.yaml
```

To see every iii process on the machine, including other projects, use [`iii ps`](#finding-and-stopping-iii-processes).

### Viewing logs

`compose::logs` returns recent stdout and stderr for the workers of one project.

| Field     | Description                                                                          |
| --------- | ------------------------------------------------------------------------------------ |
| `file`    | The project to read.                                                                 |
| `worker`  | One worker. Returns every compose-orchestrated worker when omitted.                  |
| `tail`    | Recent lines returned when no cursor is sent. Default 100, maximum 1000.             |
| `cursors` | The `cursor` from the last response, keyed by worker. The call continues from there. |
| `stream`  | `stdout` or `stderr`. Omit for both.                                                 |
| `wait_ms` | Wait this many milliseconds for new output. Maximum 5000.                            |

The response holds one entry per worker with `container`, `entries`, `cursor`, and `truncated`. Each
entry in `entries` has `stream` and `message`. A `cursor` has `generation` and `offset`. `truncated`
is `true` when the cursor sent is older than the retained archives.

```bash
iii call compose::logs --namespace dev worker=api tail=200
iii call compose::logs --namespace dev worker=api stream=stderr wait_ms=5000
```

### Listing projects

`compose::list` returns the daemon name, its namespace, its pid, the same `target` and `targets` as
`compose::status`, and every project it holds with its namespace, file, and worker states.

### Validating a file

`compose::validate` validates a compose file and is intended for package develpment work. It takes
`file`. Validation is offline, so `package://` workers are reported under `deferred_packages` and
not resolved.

`compose::validate` never edits the file. When the next `up` would rewrite containers into the
explicit VM mode, it reports a warning that names them. It reads the lock to know which packages
are bundles, so a package the lock does not record yet is not named:

```text
migration due: <c>, <c>; the next up rewrites them
```

#### Validation reports

| Field               | Type   | Description                                               |
| ------------------- | ------ | --------------------------------------------------------- |
| `namespace`         | string | Namespace the project's workers register in.              |
| `start_order`       | array  | Worker names in dependency order.                         |
| `deferred_packages` | array  | `package://` workers, which need the registry to resolve. |
| `warnings`          | array  | Warnings, such as the containers the next `up` rewrites.  |

### Stopping the daemon

`compose::stop` stops the compose project, all associated workers, and optionally the engine if
started with (`--up`). The compose daemon will also exit. Before exiting the daemon will return its
name, pid, and the projects it is about to stop.

<Warning>
  There is no `compose::start` equivalent to `compose::stop`. Stopping a compose daemon means it
  must be restarted from the server it is running on.
</Warning>

### Viewing schema

`compose::schema` takes a `function_id` argument. With no `function_id`, it returns every
`compose::*` schema. Pass a function id to return the schema for a given function_id. The pseudo-id
`worker-compose.yaml` returns the file's JSON Schema as `request` and a complete small example as
`response`.

Each entry holds `function_id`, `description`, `request`, `response`, `default_timeout_ms`, and
`idempotent`. The same schemas, descriptions, and metadata are also published through
`engine::functions::info`.

```bash
iii call compose::schema --namespace dev
iii call compose::schema --namespace dev function_id=compose::up
iii call compose::schema --namespace dev function_id=worker-compose.yaml
```

## Configure a namespace

Set the namespace in `worker-compose.yaml` or pass `--namespace` when starting Compose. Use the same
namespace in function calls and observers that target the project's workers. For the daemon
namespace, project namespace, and routing model, see
[Compose architecture](../understanding-iii/compose).

### Precedence

| Value                    | Sets                                                                          |
| ------------------------ | ----------------------------------------------------------------------------- |
| `-n, --namespace <NS>`   | The daemon namespace, and the project namespace of every project it loads.    |
| `namespace:` in the file | The daemon namespace when `--namespace` is absent, and the project namespace. |
| Neither                  | `default`.                                                                    |

`namespace` is commonly defined in `worker-compose.yaml` but can be overridden on compose daemon
startup with the `--namespace` flag.

Likewise, compose's own `compose::*` functions will exist within the same declared namespace.

### What a namespace may hold

A valid namespace is made up of the lowercase characters `a-z`, `0-9`, `-` and `_`. All other
characters are not permitted and will result in an `INVALID_NAMESPACE` error; including uppercase
letters. To prevent naming conflicts there is no coercion of invalid namespaces to valid namespaces.

### One daemon to a namespace

Two compose daemons with different namespaces can share an engine. However, a second daemon claiming
a namespace that is already served is refused at registration with `DAEMON_ALREADY_SERVING`.

<Warning>
  Only one Compose daemon can serve a namespace on a iii engine. Set `namespace:` in the compose
  file or pass `--namespace` when several daemons must share one iii engine.
</Warning>

## `worker-compose.yaml`

Below is an example of version 1 of a worker compose file. Unknown keys and duplicate keys are
errors. Durations can specify a unit such as: `500ms`, `30s`, `2m`.

```yaml
namespace: shop
startup_timeout: 60s
stop_timeout: 10s
engine:
  url: ws://127.0.0.1:49134
  workers:
    configuration:
      adapter:
        name: fs
        config:
          directory: ./config
containers:
  database_1: # Worker names do not need to match package names
    worker: package://database
    version: "0.21.4"
  api:
    worker: path://./workers/api
    start_after: [database_1]
    config_name: shop-api
    config_override:
      log_level: debug
    env_file: [./.env] # specify .envs, later in list overwrites earlier declarations
    environment:
      RUST_LOG: info # specify environment variables directly
      MY_ENV: ${MY_ENV:-defaultValue} # assign an environment variable from the execution environment
    scripts:
      pre_run: npm run migrate
      pre_run_timeout: 2m
      run: npm start
      post_run: ./scripts/cleanup.sh
  state:
    worker: package://state
    version: "0.21.4"
```

### Top-level fields

| Field              | Type    | Default | Description                                                                                         |
| ------------------ | ------- | ------- | --------------------------------------------------------------------------------------------------- |
| `namespace`        | string  | absent  | Namespace the project's workers register in. A project that declares none lands in `default`.       |
| `startup_timeout`  | string  | `60s`   | Readiness budget for every worker. A worker may override it.                                        |
| `stop_timeout`     | string  | `10s`   | Grace between the polite stop and the forced kill.                                                  |
| `required_default` | boolean | `false` | Fallback for workers that omit `required`. An explicit worker value wins.                            |
| `engine`           | map     | absent  | Present when this Compose invocation owns and configures the engine.                                |
| `containers`       | map     | empty   | Project workers. May be empty only when `engine:` is present.                                       |

### Engine fields

| Field                             | Type    | Default                | Description                                                                              |
| --------------------------------- | ------- | ---------------------- | ---------------------------------------------------------------------------------------- |
| `url`                             | string  | `ws://127.0.0.1:49134` | Managed engine endpoint used by Compose and its workers.                                 |
| `registration_namespace_grace_ms` | integer | engine default         | Namespace-registration grace passed to the engine.                                       |
| `observers`                       | map     | engine defaults        | Observer limits and timeouts passed to the engine as written. See [Observers](./configuration#observers). |
| `workers`                         | map     | empty                  | Direct configs for engine-owned workers. Values must be mappings; use `{}` for defaults. |
| `sandbox`                         | map     | absent                 | Binds the engine's `sandbox::*` router to an adapter. See below.                         |

Allowed worker keys are `configuration`, `iii-worker-manager`, `iii-http-functions`, and
`iii-stream` (deprecated; still accepted). Use `#instance` for another instance of an allowed type, for example
`iii-worker-manager#rbac`. The engine injects `iii-engine-functions`, `iii-telemetry` for anonymous
usage analytics, `iii-observability` for OpenTelemetry traces, metrics, and logs, and the
`iii-sandbox` router. Do not declare these workers. A file that declares `iii-sandbox` under
`engine.workers` fails with `SANDBOX_CONFIG_MOVED`, which prints the replacement; see [Upgrading to
the sandbox worker](../upgrading/sandbox-worker).

`engine.sandbox` takes `adapter`, the adapter's function prefix (`sandbox-libkrun` by default), and
`namespace`, where the adapter runs (this project's namespace by default). A managed engine is bound
to an adapter whether or not the section is present. Setting the section, with `namespace` unset or
this project's, also makes Compose install that adapter, as does a container whose `scripts.run`
starts with `iii sandbox run`, or `iii call compose::add worker=iii-sandbox`. See
[Sandboxes](../creating-workers/sandboxes).

<Warning title="Deprecated">
  `iii-stream` is deprecated (iii-stream) and will be removed in an upcoming release.
  Behavior is unchanged for now. See
  [Migrate from iii-stream and pubsub](../upgrading/migrate-from-streams).
</Warning>

<Note>
  Changes to these worker configurations take effect only after the engine restarts.
</Note>

#### Which engine Compose uses

Compose takes the engine address from the first of these that supplies one: the `--engine` flag,
the `III_URL` environment variable, the `engine:` section of the compose file, then
`ws://127.0.0.1:49134`.

An address from `--engine` or `III_URL` names an engine that already runs, so Compose connects to
it and starts no engine of its own, even with `--up`. Only the compose file can give Compose an
engine to own, and only `--up` takes it: an `engine:` section carries the engine's whole
configuration, not only an address.

### Worker fields

Each key under `containers` is the name the worker registers under. It also names the container's
directories, `.iii/build/<key>/` and `.iii/workers/<key>/`, so it must be a plain directory name: a
key that is empty, holds `/` or `\`, starts with `.`, or holds a NUL fails with
`INVALID_CONTAINER_KEY`.

| Field             | Type           | Default              | Description                                                                                                |
| ----------------- | -------------- | -------------------- | ---------------------------------------------------------------------------------------------------------- |
| `worker`          | string         | required             | `path://<dir>` or `package://<name>`. A package may name its registry: `package://<registry-host>/<name>`. |
| `version`         | string         | absent               | Version range. Required, and not empty, for `package://`. A `path://` worker ignores it.                   |
| `start_after`     | array          | empty                | Workers that must start first (ie. a worker dependency). Self-dependencies and cycles are rejected.        |
| `config_name`     | string         | absent               | The [configuration worker](./configuration) entry this worker owns.                                        |
| `config_override` | mapping        | absent               | Merged on top of the fetched configuration; a mapping whose `name` changes is replaced whole.              |
| `working_dir`     | path           | the worker directory | Resolved against the compose file's directory.                                                             |
| `environment`     | map            | empty                | Environment variables for this worker.                                                                     |
| `env_file`        | array of paths | empty                | Read at start time, in declaration order. A later file wins on conflicting entries.                        |
| `startup_timeout` | string         | the file's value     | Readiness budget for this worker.                                                                          |
| `required`        | boolean        | `false`              | Whether a failed start fails the operation. `false` reports the failure and lets the operation carry on.   |
| `restart`         | string         | `no`                 | What happens after a failed start or a run-time exit. `no`, `on-failure`, or `always`.                     |
| `scripts`         | mapping        | absent               | See below.                                                                                                 |

`path://` directories resolve against the compose file's directory. A missing directory fails with
`MISSING_WORKER_DIRECTORY`, and a missing `env_file` fails with `MISSING_ENV_FILE` during
validation.

A `path://` worker runs as a host process unless its `scripts` run it in a VM. A non-empty
`runtime.base_image` in its `iii.worker.yaml` is the base image of its VM build. Such a worker stays
on the host only when it declares its own `scripts.build`; without one, Compose rewrites it into the
VM. See [VM workers](#vm-workers). An invalid image reference fails instead of falling back to the
host or to another image.

`sandbox-libkrun` 0.3.1 and later hide the `.iii` directory, which holds Compose's state and the
project's token, from a VM, both in its copy of the worker's directory and in the source share that
copy is made from. Earlier versions do not, so there a VM worker whose directory contains the compose
file, such as `path://.`, can read that token. Its disk keeps those bytes after the upgrade, so stop
Compose and run `iii compose --up` once to replace the token: updating or restarting the adapter keeps it.

A managed engine also writes `data/` and `config/` in the directory `iii compose --up` runs from, and
`data/` holds the payloads of traced function calls. A VM worker whose directory contains them can
read them on any version. So keep the compose file and the directory you start Compose from outside
the worker's directory, as in `path://./api`. `III_COMPOSE_STATE_DIR` moves Compose's state and the
token, but not `data/` or `config/`. Point it outside the worker's directory, because only the name
`.iii` is hidden.

### Worker kinds

Worker packages can be released in multiple different "kinds". A kind compose cannot run fails with
`UNSUPPORTED_PACKAGE_KIND`.

| Kind     | How it runs                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------ |
| `binary` | A child process on the host.                                                                     |
| `bundle` | A VM, through `iii sandbox build` and `iii sandbox run`, or the host when `scripts.run` says so. |
| `path`   | A path to a worker stored locally on disk.                                                       |

A VM worker runs in the `sandbox-libkrun` worker, a container of the project that the VM worker
names in `start_after`. Compose adds that container when the project needs it. Its guest and its
build VM receive the container's `environment` and `env_file` variables and the reserved `III_*`
variables, not the host's environment: declare under `environment` what the worker needs, such as a
provider key. The adapter is built for three targets only: `aarch64-apple-darwin`,
`x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`. On a musl Linux or Intel Mac host
Compose fails with `UNSUPPORTED_PLATFORM`. On Linux the user running Compose needs read and write
access to `/dev/kvm`, and `libcap-ng0` must be installed. Every other worker kind is unaffected.

On Windows, a bundle fails with `BUNDLE_NEEDS_A_VM` before anything is downloaded, and
`iii sandbox run`, and `iii sandbox build` inside Compose, fail with `SANDBOX_UNSUPPORTED_PLATFORM`.
Run compose under WSL, where the VM still needs `/dev/kvm` and a guest rootfs to boot. Every other
worker kind runs on windows as it always has.

Bundle support can be refused machine-wide with `III_BUNDLE_WORKERS_DISABLED=1`, which compose
honours.

### Scripts

| Field             | Type   | Default | Description                                                          |
| ----------------- | ------ | ------- | -------------------------------------------------------------------- |
| `pre_run`         | string | absent  | Runs to completion before the worker is spawned, after any build.    |
| `pre_run_timeout` | string | `60s`   | Budget for `pre_run`. Rejected without a `pre_run`.                  |
| `build`           | string | absent  | Build command. `""` declares that there is no build step. See below. |
| `build_timeout`   | string | `20m`   | Budget for `build`, outside `startup_timeout`.                       |
| `run`             | string | absent  | Start command. Rejected for `binary` packages.                       |
| `post_run`        | string | absent  | Runs after the worker's exit is confirmed.                           |

Both hooks run with the worker's environment, working directory, and their own process group. A
`post_run` runs after the worker stops but before the compose daemon exits. The top-level
`stop_timeout` argument is a global timer for a compose daemon to stop. If this time is exceeded all
scripts will be exited along with the compose daemon.

A path worker's start command is `scripts.run` in `worker-compose.yaml`, or `scripts.start` in the
worker's own `iii.worker.yaml` when `run` is absent. A worker with neither fails with
`MISSING_START_COMMAND`.

#### `scripts.build`

| Property          | Value                                                                                                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Type              | A shell command, run like `scripts.run` (`sh -c` on Unix).                                                                                                                           |
| Working directory | The container's working directory, as for `scripts.run`.                                                                                                                             |
| Environment       | The container's environment, as for `scripts.run`. For `iii sandbox build`, the guest of the build VM gets the same variables as the worker's guest, not the host's environment.     |
| Timeout           | `scripts.build_timeout`, default `20m`, outside `startup_timeout`. Compose passes it to `iii sandbox build` as `III_BUILD_TIMEOUT_MS`.                                               |
| Output            | Captured into the container's logs (`compose::logs`), each line prefixed with `[build] `.                                                                                            |
| Nothing to build  | `scripts.build: ""` declares that there is no build step: nothing runs and no `build.json` is written.                                                                               |
| Failure           | `BUILD_FAILED`. From `iii sandbox build`: the code and message of its last line. From any other command: code `EXIT_<status>` (or `TIMED_OUT`), message the last 20 lines of output. |
| When              | The [first build](#the-first-build), [`compose::build`](#building-workers), and a [package update](#rebuilds).                                                                       |

### Configuration precedence

Lowest to highest: the configuration a package ships, the entry in the configuration worker, then
`config_override`. Maps merge key by key; arrays and scalars replace. A mapping whose `name` the
override changes is replaced whole: the keys beside `name` belong to the variant it picks. The
merged result is delivered through `configuration::set` with `flush: false` before the worker starts,
unless it is null: an injected null would hide the stored entry, including the default a worker
seeds there with `configuration::ensure`.
`III_CONFIG_NAME` identifies the entry read through `configuration::get`. Compose does not create
an execution snapshot file or set `III_CONFIG`. The persistent `config/<id>.yaml` remains unchanged
by this memory-only update. `configuration::ensure` seeds defaults only into the base and preserves
the active value. `configuration::set` with `flush: true` (the default) persists the complete
submitted object, including values originally supplied by an override. Both forms notify consumers.
Each start reads the current configuration with `configuration::get` and `raw: true`, then applies
the declared override. Removing a field from the override keeps its current value; it does not
restore the value from disk. Stopping a worker leaves the active value available. Restarting the
configuration service discards unsaved memory values and reloads its adapter. Read or update failures
stop startup with `CONFIG_FETCH_FAILED`, rather than silently falling back to defaults.

### Readable configuration names and migration

Without an explicit `config_name`, the entry id is exactly `<namespace>-<container-key>`.
For example, `default` plus `harness` uses `default-harness` and the filesystem adapter stores
`config/default-harness.yaml`. The id must match `[a-z0-9_-]{1,64}`. Compose rejects an invalid or
long generated name with `INVALID_CONFIG_NAME` and asks for an explicit `config_name`; it never
sanitizes, truncates, or adds a hash. Explicit names remain unchanged and are never auto-migrated.

Before reading configuration or starting the child, Compose asks the configuration authority to
migrate the exact hashed id produced by the previous algorithm for that namespace and key.
`default-harness-a14f3656efb8d5ea` therefore becomes `default-harness`. Stored raw values (including
`${VAR}`, `false`, `0`, and `null`), name, description, metadata, and available schema are preserved.
The filesystem adapter updates both filename and internal id, and the authority updates its caches
and notifies subscribers. It re-reads the source so manual edits awaiting the watcher are retained.

Migration gives the legacy source priority over an existing destination.
After that, the `default` namespace adopts the exact bare container key (`state` becomes
`default-state`), even when the destination already exists. The bare source replaces the
whole destination entry, preserving raw values and metadata rather than merging defaults.
Another container's explicit ownership blocks this adoption; other namespaces and explicit
`config_name` values never adopt bare entries.

After publishing the destination, the fs adapter archives the original source as
`<source>.yaml.bak` (for example, `state.yaml.bak`). The previous destination is replaced,
not backed up. Files ending in `.yaml.bak`, `.bak.yaml`, or `.bkup.yaml` are ignored during
loading, watching, and legacy directory migration. Repeated starts with no source perform
no writes. An existing identical backup permits recovery after interrupted cleanup; a
conflicting backup is never overwritten and stops migration with an error.

Migration commits the complete destination before archiving the source. I/O failures stop startup; failure after publication can leave two recoverable copies.
The filesystem adapter requires same-directory hard-link support and may normalize YAML formatting
or remove comments on the one migration rewrite; values and unknown document fields are retained.
Stop source consumers before migration: Compose checks that the child is not already registered,
and its restart path stops the old child first. Do not run two configuration authorities against
the same directory or edit the source concurrently with migration.

The bridge delegates migration to the remote authority. Upgrade that authority together with
Compose: an absent `configuration::migrate` or unsupported adapter fails with
`CONFIG_MIGRATION_FAILED`, never a read/copy/delete fallback that could reset stored values.

Within one project, a generated name colliding with another container's explicit name is rejected
before startup. Sharing is allowed only when both names are explicit. Across namespaces, `a-b` / `c`
and `a` / `b-c` both produce `a-b-c`; choose unambiguous namespaces or distinct explicit `config_name`
values. Readable names do not claim cross-project ownership.

## The worker environment

A worker's environment combines the following sources, from lowest to highest precedence:

1. The machine environment visible to the Compose daemon. Variables are inherited even when
   neither `env_file` nor `environment` is declared. Non-Unicode names and values are skipped.
2. The worker's `env_file` entries, in declaration order. Later files override earlier files.
3. The worker's `environment` map. Nonempty values override env files; an empty string preserves
   an existing env-file value, or supplies an empty value when no env file defines the key.
4. The reserved variables, which the daemon owns.

Export machine variables before starting the daemon. Changing another shell's environment does
not update an already-running daemon. Workers and hooks inherit the daemon's Unicode machine
variables, including credentials, subject to the daemon-owned values above and the project identity
exception below; only start workers you trust with that environment.

`III_HOST_USER_ID` is not inherited from the machine: it comes from the current project's
`.iii/project.ini`, or is absent when the project has no device ID. An explicit `env_file` or
`environment` value can still override it, including an empty value.

| Variable                | Value                                                                         |
| ----------------------- | ----------------------------------------------------------------------------- |
| `III_URL`               | The engine address the daemon is connected to.                                |
| `III_NAMESPACE`         | The project's namespace.                                                      |
| `III_COMPOSE_NAMESPACE` | The supervising Compose daemon's namespace for explicit `compose::*` routing. |
| `III_COMPOSE_FILE`      | Canonical path of the compose file that owns this worker.                     |
| `III_COMPOSE_DIR`       | Canonical directory that contains the owning compose file.                    |
| `III_WORKER_NAME`       | The key under `containers`.                                                   |
| `III_CONFIG_NAME`       | The explicit configuration id or `<namespace>-<container-key>`, always present.        |

Declaring a reserved variable in `environment` or an `env_file` fails with `RESERVED_ENV_OVERRIDE`.

Compose hands `iii sandbox build` and `iii sandbox run` the sandbox variables listed in
[Sandboxes](../creating-workers/sandboxes#environment-variables), plus these five, which are
reserved too:

| Variable                 | Value                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------- |
| `III_BUILD_DIR`          | `<project>/.iii/build/<container>`.                                                   |
| `III_BUILD_TIMEOUT_MS`   | `scripts.build_timeout`, for `iii sandbox build`.                                     |
| `III_BUILD_COMPOSE_FILE` | The compose file's canonical path, as in `III_COMPOSE_FILE`, for `iii sandbox build`. |
| `III_PACKAGE_DIR`        | `<project>/.iii/workers/<container>`, for a bundle.                                   |
| `III_PACKAGE_NAME`       | The bundle's manifest name, for a bundle.                                             |

A bundle that runs on the host gets `III_PACKAGE_DIR` and `III_PACKAGE_NAME` too.

### Expanding values from environment variables

Variables can be expanded with `${VAR}`. References expand in any value, not only in `environment`.
For example:

```yaml
containers:
  queue:
    worker: path://${WORKERS_DIR}/queue
    environment:
      RUST_LOG: ${RUST_LOG:-info}
```

| Written        | Means                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------------- |
| `${VAR}`       | The value from compose's own environment. Unset, the file is refused with `UNDEFINED_VARIABLE`. |
| `${VAR:-text}` | The value, or `text` when it is unset. `${VAR:-}` makes it optional and empty.                  |
| `$VAR`         | Nothing. A bare name is left alone, so a `scripts.run` holding `$PWD` still reaches the shell.  |
| `$${VAR}`      | A literal `${VAR}`.                                                                             |

<Warning>
  `config_override` is never expanded, all values are treated as literals.

```yaml
config_override:
  # Reaches the worker exactly as written.
  api_key: ${ANTHROPIC_API_KEY}
```

</Warning>

## VM workers

A VM worker says so in `worker-compose.yaml`: `scripts.build` is `iii sandbox build` and
`scripts.run` is `iii sandbox run`. The build runs locally in the sandbox adapter and leaves an
image in the project. The run boots that image, and nothing is installed at boot. Compose starts
both as processes, like any other command. The sandbox adapter is a container like any other,
reached through `start_after`. Moving a worker between a VM, the host, and Docker is an edit of
`scripts`. For the commands themselves, see [Sandboxes](../creating-workers/sandboxes#vm-workers).

```yaml worker-compose.yaml
namespace: default
engine:
  url: ws://127.0.0.1:49134

containers:
  # added by compose::add
  sandbox-libkrun:
    worker: package://api.workers.iii.dev/sandbox-libkrun
    version: "0.4.0"

  state:
    worker: package://api.workers.iii.dev/state
    version: "0.23.0"

  # A registry bundle in a VM. compose::add writes start_after and scripts.
  # added by compose::add
  onboarding:
    worker: package://api.workers.iii.dev/onboarding
    version: "0.2.0"
    start_after: [sandbox-libkrun, state]
    scripts:
      build: iii sandbox build
      run: iii sandbox run
    environment:
      OPENAI_API_KEY: ${OPENAI_API_KEY}   # the guest gets only what is declared

  # A local worker in a VM: the base image comes from runtime.base_image in its iii.worker.yaml.
  link:
    worker: path://./link
    start_after: [sandbox-libkrun]
    scripts:
      build: iii sandbox build
      run: iii sandbox run

  # The same kind of worker on the host: moving it is an edit of scripts.
  api:
    worker: path://./api
    scripts:
      build: npm ci && npm run build
      run: node dist/index.js
```

`sandbox-libkrun` 0.4.0 is the first release with `worker.build`.

### Which containers run in a VM

| Rule                                                                                                                  | Error                                                                                       |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `scripts.run: iii sandbox run` only on a `bundle` package, or on a `path://` whose manifest sets `runtime.base_image` | `SANDBOX_RUN_NOT_A_VM_WORKER`                                                               |
| `scripts.build: iii sandbox build` only together with `scripts.run: iii sandbox run`                                  | `SANDBOX_BUILD_WITHOUT_RUN`                                                                 |
| `scripts.run: iii sandbox run` with a `scripts.build` other than `iii sandbox build`                                  | `SANDBOX_RUN_WITHOUT_BUILD`                                                                 |
| `iii sandbox run` on Windows                                                                                          | `SANDBOX_UNSUPPORTED_PLATFORM` (a bundle already fails at install with `BUNDLE_NEEDS_A_VM`) |
| `scripts.run` or `scripts.build` on a `binary` package                                                                | `RUN_NOT_ALLOWED_FOR_PACKAGE`                                                               |
| `--command <cmd>` on a bundle                                                                                         | Refused by `iii sandbox run`                                                                |

A project needs the adapter when a container's `scripts.run` starts with `iii sandbox run`, or when
`engine.sandbox` names the project's own namespace. Compose then adds the generated adapter
container, marked `# added by compose::add`, when the file does not declare one. The start order on
the adapter is in `start_after`, in the file.

These rules apply after the rewrite of older files: a missing `scripts.build`, a missing adapter in
`start_after`, or a bundle without `scripts.run` is rewritten, not refused. See
[Rewriting files from older releases](#rewriting-files-from-older-releases).

### Keeping a worker on the host

A `path://` whose manifest sets `runtime.base_image` runs on the host only when it declares
`scripts.build`, `""` when there is nothing to build:

```yaml
  link:
    worker: path://./link   # its iii.worker.yaml sets runtime.base_image
    scripts:
      build: ""
      run: node index.js
```

Without `scripts.build`, Compose rewrites it into the VM. A `build:` key without a value counts as
absent.

A bundle runs on the host when its `scripts.run` is a host command. It runs `scripts.build` and
`scripts.run` in `.iii/workers/<container>/`, and gets `III_PACKAGE_DIR` and `III_PACKAGE_NAME`.
Binary packages keep their working directory. Both moves are edits of `scripts`, and later runs
leave them alone, with or without a lock.

### The project tree

```text
my-project/
├── worker-compose.yaml
├── worker-compose.lock
├── .iii/                    # hidden from VMs by name
│   ├── project.ini          # the project's id, written by iii project init
│   ├── compose/             # Compose state and the project token; III_COMPOSE_STATE_DIR moves it
│   ├── workers/             # packages, one directory per container; like node_modules
│   │   ├── .gitignore       # "*", written by Compose
│   │   ├── .packages.json   # container -> { name, version, sha256 }
│   │   ├── .lock            # held while Compose copies packages
│   │   ├── onboarding/
│   │   ├── sandbox-libkrun/
│   │   └── state/
│   └── build/               # one directory per container that has a build
│       ├── .gitignore       # "*", written by Compose
│       ├── onboarding/
│       │   ├── image.erofs  # the image the run boots (VM containers)
│       │   ├── image.id     # its build_id, written by the adapter
│       │   └── build.json
│       ├── link/
│       └── api/
│           └── build.json   # host builds record build.json without an image
└── link/                    # a path:// worker, as today

~/.iii/cache/                # global: base images (docker.io/iiidev/node, .../python, ...)
~/.iii/compose/packages/     # global: extracted packages, unchanged; the source of .iii/workers/
~/.iii/sandbox/workers/      # adapter-owned: each VM's persistent data disk
```

- `.iii/workers/` and `.iii/build/` are always in the `.iii/` beside the compose file, also when
  `III_COMPOSE_STATE_DIR` moves Compose's state: the sandbox adapter reads only under the compose
  file's directory and the package cache. Nothing of Compose's lands at the project root, and a VM
  never sees either directory, `path://.` included.
- `.iii/workers/` is rebuilt from `worker-compose.lock`, and `.iii/build/` by a build. Both stay out
  of git like `node_modules`. Compose writes a `.gitignore` containing `*` in each, so a migrated
  project is covered without editing its own `.gitignore`, which keeps the rest of `.iii/`, such as
  `project.ini`.
- `.iii/workers/<container>/` is a copy of the extracted package from the global cache, which keeps
  its own layout. `.iii/workers/.packages.json` records which artifact each directory holds. It is
  stored outside the package directories, so no guest can write it.
- One copy runs at a time: the daemon and `iii compose build` both hold `.iii/workers/.lock` while
  they copy packages. A directory whose record matches the lock stays as it is, with what a host
  build wrote into it. Compose removes only what it made: the directories of containers no longer
  locked, and the temporary copies an interrupted run left.
- When Compose copies a container's package directory again because it was missing or its record
  could not be read, it deletes that container's host-build `build.json`, so the next start runs
  the first build again. A package update keeps the record and rebuilds. A VM build keeps its
  record: its image holds its own copy of the package.
- The image is one file, `image.erofs`, never a directory tree: a Linux tree on a case-insensitive
  filesystem (APFS) would be corrupted.

```json .iii/workers/.packages.json
{ "schema": 1, "containers": { "onboarding": { "name": "onboarding", "version": "0.2.0", "sha256": "sha256:8c3406..." } } }
```

### The flow

1. `iii call compose::add worker=onboarding` resolves the package, writes the container with
   `start_after` and `scripts`, and reconciles.
2. A container whose `scripts.build` has no `.iii/build/<container>/build.json` yet gets its first
   build when it starts, then runs.
3. `scripts.run` starts the worker. For a VM container, `iii sandbox run` boots
   `.iii/build/<container>/image.erofs`.
4. A restart, or an adapter restart, repeats `scripts.run` only.
5. A rebuild is explicit (`iii sandbox build <container>`), followed by a restart of that
   container. `compose::update` of a package rebuilds it.
6. `compose::remove` stops the container, has the adapter destroy the VM's data disk, and deletes
   `.iii/build/<container>/` and `.iii/workers/<container>/`.

### The first build

A container gets its first build when it starts, after its `start_after` containers are ready, if
`scripts.build` is set and non-empty and `.iii/build/<container>/build.json` is missing. This covers
`compose::add`, `up`, and a migrated container.

- The build runs within `scripts.build_timeout`. The container's `startup_timeout` then starts for
  the run.
- The container's logs show `<container>: no build yet; running scripts.build`, then the build
  output.
- `compose::add` and `compose::up` report the build as a progress step of the container
  (`building`). Their operation finishes after the run started or failed.
- A failed build fails the container with `BUILD_FAILED`, carrying `{ code, message }` as
  [`scripts.build`](#scriptsbuild) defines them. Nothing is rolled back, as for any failed start.

### Rebuilds

`iii sandbox build <container>` or `iii call compose::build worker=<container>` rebuilds. The
running container keeps its current image until it restarts:

```bash
iii sandbox build link
iii call compose::restart worker=link
```

`compose::add` or `compose::update` that changes a container's package (`source` in `build.json` no
longer matches the lock) rebuilds it before restarting it, and logs
`<container>: package changed (<old> -> <new>); rebuilding`. The container keeps running on its old
build while the new one builds, so the restart that follows only runs the new build.

- **A failed rebuild** keeps the container running on its old build, and Compose does not restart
  it. The operation fails with `BUILD_FAILED`. The file and the lock already name the new version:
  retry the add or update, or run `iii sandbox build <container>` then
  `iii call compose::restart worker=<container>`, to finish it.
- **A retried add or update** finishes what an earlier one left: it rebuilds a container still on
  the build of its old package, and restarts one it rebuilt but did not restart.
- **An explicit build**, from `compose::build` or `iii sandbox build`, does not make a later add, or
  a retried add or update, restart its container: that restart is yours. An update that changes a
  package still restarts the whole project, this container included.
- **A cancel** of the add or update (`compose::cancel`) builds nothing more and restarts nothing. It
  fails with `OPERATION_CANCELLED` and, when it already rebuilt some, the message lists them
  (`rebuilt and not yet restarted: <container>`). Retry the add or update to restart them.
- **A VM whose adapter restarts** in the same operation cannot stay on its old build: it ends with
  the adapter, starts again, and builds then.

### Builds that are out of date

Before `scripts.run` (on `up`, a restart, or a crash replacement), Compose compares the container's
current inputs with `build.json`: `source`, `dependency_files`, and `image.base_image.declared`. A
container without `build.json` is not checked. A difference in `dependency_files` or
`base_image.declared` only logs, once per start, one line per kind of change:

```text
link: dependencies changed since the last build (package.json); run `iii sandbox build link`
link: base image changed since the last build (docker.io/iiidev/node -> docker.io/iiidev/python); run `iii sandbox build link`
```

When one side declares no `runtime.base_image`, the line names `the adapter's default` for it. The
container then runs on its current build. A change of `source` is a package update and rebuilds (see
[Rebuilds](#rebuilds)). A change of code alone, outside the dependency files, is not a change: a
`path://` worker's code keeps syncing live into the guest.

### `build.json`

```json .iii/build/onboarding/build.json
{
  "schema": 1,
  "container": "onboarding",
  "source": { "kind": "package", "name": "onboarding", "version": "0.2.0", "sha256": "sha256:8c3406..." },
  "command": "iii sandbox build",
  "dependency_files": { "package.json": "sha256:2f1c...", "package-lock.json": "sha256:9a07..." },
  "image": {
    "file": "image.erofs",
    "build_id": "sha256:7d41...",
    "base_image": { "declared": null, "reference": "docker.io/iiidev/node:latest", "digest": "sha256:b1e2..." },
    "adapter": { "name": "sandbox-libkrun", "version": "0.4.0" },
    "contract": { "major": 1, "minor": 3 }
  },
  "built_at": "2026-11-10T14:03:22Z"
}
```

A `path://` container records `"source": { "kind": "path", "dir": "./link" }`: the declared path,
relative to the compose file. A host build writes the same keys without `image`.

- Every hash is written `sha256:<hex>`. Times are RFC 3339 UTC.
- `dependency_files` holds the hash of each of these files that exists at the root of the worker
  directory: `package.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`,
  `requirements.txt`, `pyproject.toml`, `uv.lock`, `poetry.lock`, `Cargo.toml`, `Cargo.lock`,
  `go.mod`, `go.sum`.
- `image.base_image.declared` is the manifest's `runtime.base_image`, or `null` when the adapter
  chose the image. `reference` and `digest` are what the adapter reports, and `digest` is `null`
  when it does not know it.
- For a VM build, `iii sandbox build` writes `build.json` after the adapter renamed the new image
  into place. For a host build, Compose writes it after `scripts.build` exited 0.
- Writes are atomic: a temporary file beside `build.json`, then a rename. Leftover temporary files
  are swept. A `build.json` whose `build_id` does not match the image fails the run with
  [S508](../creating-workers/sandboxes#S508). The fix is a rebuild.

### What the guest sees

- **Data.** The VM's data disk is persistent and independent of the build. It keeps whatever the
  worker writes (its home, databases, caches, and the files it writes in `/workspace`) across
  restarts and rebuilds. Only `iii sandbox destroy` and `compose::remove` reset it. It stays
  adapter-owned under `~/.iii/sandbox/workers/<vm_id>/`.
- **Root filesystem.** The guest's root is the build image, read-only, with the data disk on top. A
  file the worker modified inside a directory the build also writes, for example under
  `node_modules`, keeps the worker's copy after a rebuild. `iii sandbox destroy` clears it.
- **Code.** A bundle's code is in the image. Its `.iii/workers/<container>/` is the build's input
  only. A `path://` worker's code keeps syncing live into `/workspace`. One list of names decides
  what a run neither copies nor syncs, including for `path://.`: the adapter's ignore list plus
  `.iii`, which also keeps Compose's `.iii/build/` and `.iii/workers/` out. The list holds
  dependency, cache, build-output, VCS, and editor directories, such as `node_modules`, `.venv`,
  `vendor`, `target`, `dist`, and `.git`.
  - `build`, `out`, `obj`, `coverage`, and `deps` match only a directory at the worker's root:
    projects also keep source under these names deeper down. Every other name, `target` and `dist`
    included, matches at any depth.
  - The build's input copy uses the same list except `vendor`, which goes into the build: Go keeps
    vendored source there.
- **Boot cleanup.** A boot never deletes what the build installed or what the worker wrote in
  `/workspace`. Each copy records what it extracted in a manifest on the data disk, outside
  `/workspace`, and the next boot removes only the entries the host no longer has. The cleanup
  never removes through a symlink, never touches a name the copy leaves out (a run keeps the
  build's `vendor/` until the next build), and skips names with a newline or a backslash. A disk
  that an older adapter wrote has no manifest: its first boot skips the cleanup and logs it.
- **Dependencies.** They come from the build. To add one, edit `package.json`, run
  `iii sandbox build <container>`, and restart the container.
- **Environment.** The guest gets the container's `environment` and `env_file` variables and the
  reserved `III_*` variables, except the five build and package variables of
  [The worker environment](#the-worker-environment). It never gets the host's environment. The
  build VM gets the same set.

### Rewriting files from older releases

There is no implicit VM path. Compose rewrites the containers that 0.26 ran in a VM and that the
file does not place anywhere else, and logs
`<container>: migrated to the explicit VM mode (scripts.build/scripts.run: iii sandbox ...)`. The
check is per container and idempotent, keyed on `scripts` alone. The rewrite does not change the
lock format.

The rewrite runs in `compose::up` (and `iii compose --up`), `compose::add`, `compose::update`,
`compose::restart`, `compose::build`, and `iii compose build`. `compose::validate`, `compose::ps`,
`compose::status`, `iii compose logs`, `compose::down`, and `compose::remove` never edit the file.
`--frozen` never edits the file either: a file with a container to rewrite fails with
`VM_SCRIPTS_MISSING`, naming the containers and asking for one `iii compose --up` without
`--frozen`. That check comes first: a file with a container to rewrite and no adapter fails with
`VM_SCRIPTS_MISSING`, not `SANDBOX_ADAPTER_NOT_DECLARED`, and the `up` it asks for adds the adapter
too.

Before it rewrites, Compose brings the adapter in line, with the lock. It updates a generated
adapter container outside `^0.4` to the newest release in that range, and adds the generated adapter
container when the project declares none, so the `start_after` it writes names a declared
container. An adapter container you declared outside the range fails with `SANDBOX_ADAPTER_TOO_OLD`.

[Upgrading from 0.26.x](../upgrading/from-0-26-x) lists the containers Compose rewrites, what it
writes, the sandbox adapter update, and what happens to the data of 0.26 VMs.

## Build registry packages

```text
iii compose build [-f, --file <PATH>] [--frozen]
```

| Option              | Description                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------- |
| `-f, --file <PATH>` | Compose file whose registry packages should be downloaded [default: worker-compose.yaml] |
| `--frozen`          | Require an existing current lock and skip package selector resolution                     |

`build` reads and validates the compose file, prepares `worker-compose.lock`, then downloads every
`package://` worker into the same cache used by `compose::up`. The file defaults to
`./worker-compose.yaml`. The command does not connect to an engine, start a worker, or run lifecycle
hooks. Local `path://` workers and engine-managed workers need no registry download and are skipped.

Before it installs, `build` updates or adds the generated sandbox adapter and rewrites the
containers that 0.26 ran in a VM, as `compose::up` does, then writes the file and the lock. It then
copies each package into `.iii/workers/<container>/`, from the lock, under `--frozen` too. Under
`--frozen` it edits nothing: a container to rewrite fails with `VM_SCRIPTS_MISSING`, then a missing
adapter with `SANDBOX_ADAPTER_NOT_DECLARED`, then, in a project with a VM worker, an adapter outside
`^0.4` with `SANDBOX_ADAPTER_TOO_OLD`. `build` does not run `scripts.build`: `iii sandbox build` and
`compose::build` do.

```bash
iii compose build --file worker-compose.yaml
iii compose build --file worker-compose.yaml --frozen
iii compose --up --file worker-compose.yaml --frozen
```

The cache is shared under `~/.iii/compose/packages`, or under `$III_COMPOSE_STATE_DIR/packages` when that
variable is set. A later `compose::up` reuses a valid cached artifact if it exists.

## Readiness

A worker is considered up when the engine reports a worker of that name in the project's namespace.
Compose polls `engine::workers::list` every 200 ms until the worker's `startup_timeout` runs out.

| Outcome                                                        | Code                               |
| -------------------------------------------------------------- | ---------------------------------- |
| The worker never appeared.                                     | `STARTUP_TIMEOUT`                  |
| The process exited while compose was waiting.                  | `CHILD_EXITED_BEFORE_REGISTRATION` |
| It registered in `default` instead of the project's namespace. | `WORKER_IGNORED_NAMESPACE`         |
| It registered under a different name in the right namespace.   | `WORKER_NAME_MISMATCH`             |
| Its functions landed outside the project's namespace.          | `FUNCTIONS_IN_WRONG_NAMESPACE`     |
| Another worker already held that name in the namespace.        | `CONTAINER_NAME_TAKEN`             |

After a worker is ready, the daemon checks it every 250 ms. Its restart policy determines what
happens after it exits. An eligible retry keeps its dependents running and reports `restarting`
between attempts. A successful exit without an eligible retry is recorded as `stopped`. An
unsuccessful exit without an eligible retry, or one that exhausts its retries, is recorded as
`failed`. When no retry remains, its transitive dependents stop. When the engine connection drops
and comes back, every running worker gets its `startup_timeout` to register again.

Dependency shutdown is dependent upon when a shutdown happens:

| When                      | What comes down                                                                                                                  |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| During `up`               | The operation ends. Everything it started is stopped in reverse order, and workers later in the start order are never attempted. |
| After the worker is ready | Its transitive dependents. Everything else keeps running.                                                                        |

## Where compose keeps state

Compose state is stored in `<project-dir>/.iii/compose/<namespace>/`. `<project-dir>` is the directory
containing the canonical compose file, including when `--file` points outside the current working
directory or follows a symbolic link. `<namespace>` is the daemon's namespace.

| Path                 | Contents                                                                                      |
| -------------------- | --------------------------------------------------------------------------------------------- |
| `engine.lock`        | Lock for the managed engine in this project and namespace.                                     |
| `engine-config.yaml` | Generated engine configuration, removed after clean shutdown.                                  |
| `engine.log`         | Rotating stdout and stderr for the managed engine.                                             |
| `state.json`         | Child process records for the project. Owner-only.                                             |
| `config/`            | Resolved worker configuration files.                                                          |
| `logs/`              | Rotating stdout and stderr for project workers.                                                |

VM workers keep their data disk outside this directory: the sandbox adapter stores it in
`~/.iii/sandbox/workers/<vm_id>/`, and Compose has it deleted when you remove the container. Builds
and package copies are in `.iii/build/` and `.iii/workers/` beside the compose file, even when
`III_COMPOSE_STATE_DIR` moves this directory. See [The project tree](#the-project-tree). Compose
reads a 0.26 `state.json` that holds a `vm` record once: it stops that VM and drops the record.

Two projects can use `default` with separate engines on different ports. Starting the same project
and namespace twice is refused. Two daemons on the same engine must use different namespaces.
With the default state layout, two compose files in the same directory must also use different
namespaces.

For a read-only project directory, set `III_COMPOSE_STATE_DIR` to a writable directory. Project state
is then stored at `$III_COMPOSE_STATE_DIR/<project-slug>/<namespace>/`. The slug combines the project
directory name with a hash of the canonical compose file path, keeping projects with the same
directory name separate. With this override, two compose files in the same directory have separate
state directories and can use the same namespace on separate engines.

The package cache stays shared at `~/.iii/compose/packages`, or `$III_COMPOSE_STATE_DIR/packages`.
Add `**/.iii/compose/` to the repository's `.gitignore` to exclude generated state, including state
from nested projects, from version control.

```bash
iii call compose::status --namespace dev file=./worker-compose.yaml
# ... "state_dir": "/home/you/shop/.iii/compose/dev"
ls /home/you/shop/.iii/compose/dev/logs/
```

Before upgrading from the shared namespace layout, stop existing Compose daemons with the old
version and confirm that their engines and workers have stopped. The new version does not migrate
old process records or logs. Previous state remains under `~/.iii/compose/<namespace>/` (or the old
`III_COMPOSE_STATE_DIR` layout); keep any logs or VM data you need before removing it.

## Finding and stopping iii processes

`iii ps` lists every iii process the current user runs: engines with the ports they listen on,
Compose daemons, and workers with the project each belongs to.

```text
$ iii ps
PID    KIND     NAME   PORT   STATUS     UPTIME  COMPOSE
41200  engine   -      49134  running    2h5m    ~/shop
41198  compose  -      49134  running    2h5m    ~/shop
41260  worker   api    49134  running    2h5m    ~/shop
38811  worker   cron   5202   orphan     3d2h    ~/billing
```

`STATUS` is `orphan` for a worker whose Compose daemon is gone, and `no engine` for a worker whose
engine port has no engine listening. `iii ps --json` prints the same list as JSON.

`iii kill` stops a selection of those processes:

| Option             | Stops                                                                                         |
| ------------------ | --------------------------------------------------------------------------------------------- |
| `--port <PORT>`    | The engine listening on `PORT`, the Compose daemon that manages it, and every worker using it. |
| `--compose [PATH]` | A project's daemon, managed engine and workers. `PATH` is the compose file or its directory.   |
| `--orphans`        | Every worker whose Compose daemon is gone.                                                     |
| `--force`          | Sends `SIGKILL` at once instead of waiting for a graceful exit.                                |

Compose daemons receive `SIGTERM` first, so each one stops its project in reverse dependency order.
The remaining processes then receive `SIGTERM`, and `SIGKILL` after 15 seconds. `iii kill` exits
with `1` when nothing matches or a process is still running afterwards.

Compose marks each worker through its environment (`III_COMPOSE_FILE`, `III_WORKER_NAME`, `III_URL`),
which identifies it whichever SDK version it was built with. Engines and SDK workers started outside
Compose write a marker file, `~/.iii/run/<kind>-<pid>.json`, while they run. `iii ps` deletes
markers whose process is gone.
