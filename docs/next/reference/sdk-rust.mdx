### trigger

Invoke a function.


The routing behavior depends on the `action` field of the request:
- No action: synchronous, waits for the function to return.
- `TriggerAction::Enqueue`: async via named queue.
- `TriggerAction::Void`: fire-and-forget.

A function this worker registered itself runs in-process once the
engine allowed it ("local dispatch", see `Dispatch`): same result,
error shape and timeout, and nothing on the wire unless an observer's
filters match the call. A sync handler then runs inline on the
caller's task, where the timeout cannot interrupt it: a sync handler
that can block should be async, or registered with
`RegisterFunction::local_dispatch(false)`.
`TriggerRequest::dispatch` with `Dispatch::Remote`
forces the engine path. Calls made from inside a handler carry that
handler as their `caller`.

**Signature**


### observe

Observes `source` and invokes `target` once per matching event.

Returns at once, before the engine answered: the handle starts
`pending`; `ObserverHandle::ready` resolves on `active` and fails on
`error` (`INVALID_ARGS`, `INVALID_FILTER`, `FORBIDDEN`, an owner
rejection, `UNSUPPORTED` against an engine without observe). There is
no inline handler: `target` is a registered function, and the observer
stays `pending` until it is registered.

### shutdown_async

Shutdown the III client.

This stops the connection loop and sends a shutdown signal, but it
does not join `connection_thread`.

This method returns without waiting for `run_connection()` to finish,
making it safe to call from an async context without stalling the
executor; `shutdown` blocks and joins the thread.
The OpenTelemetry flush (`telemetry::shutdown_otel()`) still runs inside the connection thread
after `run_connection()` returns, so it may not complete unless
`shutdown` is used to join the thread.

**Signature**

```rust
async shutdown_async()
```

#### Example

```rust
worker.shutdown_async().await;
```

#### RegisterFunction

Function registration builder.

The function ID is supplied separately at registration time via
`IIIClient::register_function`, `RegisterFunction` only carries the handler
and optional metadata.

Constructors:
- `RegisterFunction::new`: sync function. Accepts both typed handlers
  (schemas auto-extracted via `schemars`) and `Fn(Value, Option<Value>) -> Result<Value, Error>`
  closures. The second argument is the per-invocation metadata sidecar and
  is `None` when absent.
- `RegisterFunction::new_async`: async equivalent of `new`.
- `RegisterFunction::http`: function invoked over HTTP (Lambda,
  Cloudflare Workers, etc.).

Builder methods (all consume `self`):
- `description`
- `metadata`
- `request_format`: overrides any auto-extracted schema.
- `response_format`: overrides any auto-extracted schema.
- `observe`: how observers of the function are delivered,
  and the hooks that run when one is added or removed.
- `local_dispatch`: opt out of in-process calls.

#### Observe

The observe descriptor of a function, for
`RegisterFunction::observe`.

- `Observe::auto`: the function's invocations are the events; every
  observer is offered every invocation and the SDK reports the matching
  ones. It takes no args.
- `Observe::owner`: the function's owner reads each observer's args, sets
  up what they ask for and hands each event to the observers it belongs to
  with `Observer::emit` or `Observer::call`.

hooks.

| `args_format` | `fn() -> Self` | Yes | The JSON Schema of the observers' args, generated from `T`. The engine validates every `observe` against it (`INVALID_ARGS`) before `ObserveHandler::on_observer_added` runs. `#[serde(deny_unknown_fields)]` on `T` rejects argument typos. |
| `args_format_value` | `fn(schema: Value) -> Self` | Yes | `args_format` from a JSON Schema value. |
| `auto` | `fn() -> Self` | Yes | Auto delivery (the default): every invocation is an event. |
| `handler` | `fn(handler: H) -> Self` | Yes | The callbacks that run when an observer is added to or removed from this function. |

---

#### ObserveHandler

Callbacks of an observable function, run once per observer added or
removed, one at a time per function and in the engine's order.

`on_observer_added` runs before the SDK acknowledges the observer, so what
it puts in the owner's index is in place before the engine marks the
observer `active`. Returning an error rejects the observer: an
`ObserveRejection` sets the code, a plain error is `OBSERVE_REJECTED`,
and a callback still running after 30 s is `OWNER_TIMEOUT`.

A callback past the timeout is cancelled (its future is dropped at its
next `.await`) so the function's next callback can run; anything it
spawned keeps running and may overlap that next callback. Callbacks run on
the connection's runtime: do not block in them.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `on_observer_added` | fn(obs: &'life1 [`Observer`](#observer)) -&gt; Pin&lt;Box&lt;dyn Future + Send&gt;&gt; | No | An observer was attached to the function. Index it by its args here. |
| `on_observer_removed` | fn(obs: &'life1 [`Observer`](#observer)) -&gt; Pin&lt;Box&lt;dyn Future + Send&gt;&gt; | No | An observer was detached (unobserve, disposal, its worker left for good, a reconnect that no longer lists it). Cannot fail. |

#### Dispatch

Which path `IIIClient::trigger` takes.

A call to a function registered by this same worker runs in-process
("local dispatch") when all of these hold:

1. the function has a handler here (not `RegisterFunction::http`)
   and was not registered with `RegisterFunction::local_dispatch(false)`;
2. the engine confirmed it with `functionregistered { local_dispatch: true }`;
3. the call resolves to the namespace the function is registered in;
4. the action is not `TriggerAction::Enqueue` (a `Void` call runs
   locally, fire-and-forget);
5. the dispatch is not `Dispatch::Remote`.

Otherwise the call goes through the engine as before. A local call returns
the same result, error shape and timeout as a remote one, and is reported
to the engine only when an observer's filters match it.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `Auto` | `unit` | Yes | Run in-process when the five conditions above hold, else remote. |
| `Remote` | `unit` | Yes | Always route through the engine (engine-side effects, tests). |

#### TriggerRequest

```rust
TriggerRequest {
    function_id: "my::function".to_string(),

    action: None,
    timeout_ms: None,

TriggerRequest {

TriggerRequest {
    function_id: "my::function".to_string(),
```
