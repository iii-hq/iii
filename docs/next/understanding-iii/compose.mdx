## What compose is for

A worker is a single process with an identity on the engine. A real deployment is several of them
with an order between them: a database before the API, the API before the web front end, a migration
before either. The engine holds workers and routes calls to them. Something has to own the order,
the environment each process starts with, and the response when one of them dies.

That is compose. A `worker-compose.yaml` declares the group, and a daemon turns the declaration into
running processes it keeps watching.

## The compose environment

Compose files provide reproducibility. A project starts the same way from a login shell, a systemd
unit, or a CI runner, because the daemon's own environment plays no part in it. Everything a
container needs is in the compose file, which makes the file a complete description of how the
project runs and makes a reviewer able to see the whole contract in one place.

Strictness in the compose file serves the same end and ensures that an incomplete "system" cannot be
started accidentally.

## Three names, three jobs

A compose call names three things, and confusing any two of them is the mistake worth naming up
front.

The **daemon namespace** is which machine. It comes from `--namespace`, and it is where that daemon
answers `compose::*`, so `iii call compose::up --namespace dev` reaches one daemon and not its
neighbour. Several daemons attach to one engine, which is what lets compose supervise workers where
their resources are rather than only beside the engine.

The **file** is which project. A daemon holds as many as it is given, and the compose file is the
only thing that identifies one.

The **project namespace** is where that project's workers register. It comes from `namespace:` in
the compose file: the engine's routing dimension, the same one every other worker uses.

### Why the project has no name of its own

An earlier design gave each project an id the operator chose on the first `up`. It read well and was
wrong, because it was a second identity for something the file already identified. Two identities
have to be kept in agreement, and the failure was silent in both directions: an id could be pointed
at a different file, and a mistyped id became a new empty project reporting that it had nothing to
stop, reporting success for a command that did nothing.

Deriving the project from its file removes the question. The same file reached twice is the same
project however it was spelled, a mistyped file is a file that will not open, and an error existed
only to police the divergence that can no longer happen.

The namespace stays exactly what the compose file says, so an operator can read it off the file and
type it into `iii call --namespace` or pass it to `worker.call`. Predictability is what makes a
namespace usable by hand, and it comes from being declared rather than derived.

Two copies of one project therefore share a project namespace and collide, which is how the engine
reports a duplicate for every other worker as well.

## Why the daemon owns seven variables

A container's environment is its own, with seven exceptions the daemon sets and refuses to let a
container replace. The rule is not that static configuration outranks an environment variable, which
would be the wrong way round for most settings. It is that each of these seven is already declared
somewhere in the compose file, and a second declaration of the same thing is a disagreement nobody
resolves.

`III_URL` is the daemon's connection. Readiness is observed over it, so a container pointed at
another engine is invisible to the daemon that started it, however healthy it is. The failure would
arrive as a startup timeout over a worker that is running and serving, which is the least
diagnosable shape a failure can take. Two engines mean two daemons.

`III_NAMESPACE` and `III_WORKER_NAME` are the pair readiness watches. Letting a container change
either would mean compose waiting in one place while the child registers in another, so the override
would have to be threaded through readiness, the child record and `compose::status` before it could
work at all. Both are already declared: the namespace by the file, the name by the container key.

`III_COMPOSE_NAMESPACE`, `III_COMPOSE_FILE`, and `III_COMPOSE_DIR` identify the supervisor and
project that started the container. The project namespace cannot route to the daemon namespace, and
one daemon can supervise several files, so a managed worker needs the namespace and file to make an
explicit, unambiguous `compose::*` call. The directory is the canonical parent of the file and gives
workers one stable base for project-owned data. Letting the container replace these values could
send a lifecycle edit to another project or write data outside that project.

`III_CONFIG_NAME` identifies the configuration service entry. Compose reads the current value,
merges execution overrides, and calls `configuration::set` with `flush: false` before spawn. Workers
read that value through the same GET. Explicit saves persist the submitted object. Removing an
override does not restore an older disk value. No snapshot file is delivered. The retired
`III_CONFIG` name is rejected in explicit `environment` and `env_file` declarations with
`RETIRED_CONFIG_ENV`; stale inherited values are removed. Matching is case-sensitive on Unix and
follows native case-insensitive rules on Windows.

### A container that belongs in another namespace

The case the reserved contract genuinely refuses is a container joining a namespace other than its
project's, a shared one addressed by two projects for instance. That is not an oversight. A
namespace is declared per file, and a project is its file, so a container that registers somewhere
else is describing a different project. Declaring it in a second compose file says exactly that, and
keeps the property that reading one file tells you where everything in it lands.

## Why state belongs to the project

A project's process records, resolved configuration and worker output are stored in
`<project-dir>/.iii/compose/<namespace>/`. Its managed engine uses the same directory for its lock,
generated configuration and log. The project directory comes from the canonical compose file path,
so running `iii compose --up --file` from another directory keeps state beside that file. Builds are
in `<project-dir>/.iii/build/` and package copies in `<project-dir>/.iii/workers/`, and the sandbox
adapter keeps each VM's data disk in `~/.iii/sandbox/workers/`. See
[The project tree](../reference/vm-workers#the-project-tree).

The engine lock belongs to the project and namespace together. Two checkouts can each use `default`
with engines on different ports. A second managed invocation for the same project and namespace is
refused. Within one engine, each Compose daemon still needs its own namespace.

For read-only checkouts, `III_COMPOSE_STATE_DIR` moves project state to
`$III_COMPOSE_STATE_DIR/<project-slug>/<namespace>/`. The slug includes a hash of the canonical
compose path so different checkouts remain separate under a shared root. `compose::status` reports
the resolved `state_dir` for either layout. The default layout requires a `.iii/compose/` entry in
the project's ignore rules to exclude generated state from version control.

The variable does not move `.iii/workers/` and `.iii/build/`: Compose still writes them beside the
compose file when the project locks a package or a container has a non-empty `scripts.build`, a VM
build included. A read-only checkout therefore works only without packages and builds.

Installed packages remain shared at `~/.iii/compose/packages`, or `$III_COMPOSE_STATE_DIR/packages`.
The cache is keyed by name, version and target, so projects can reuse downloaded workers.

## Engine observed readiness

Compose determines ready state through the engine rather than locally as this is the one way to
ensure dependencies are ready for a given worker. For example when `api` starts after `database`,
`start_after` guarantees the engine can already route a call to `database`, so `api` can reliably
use the `database` dependency from boot. A check on the process alone would guarantee only that
something was launched.

The engine's view is also detailed enough to report clear statuses to the user.

## Scoped shutdown

When one container in an `up` fails, compose stops what that operation started, in reverse order,
and leaves everything else running. The rule is that an operation undoes itself, which makes `up`
safe to retry.

Teardown follows the graph backwards, so dependents stop before the containers they depend on and
nothing is left using a worker that no longer exists. A container that stops on its own takes the
same path, so its dependents come down in the same order as a deliberate stop.

### The blast radius depends on the clock

Those two sentences describe two different rules, and it is worth being plain about the gap between
them. During an `up`, the first container that fails ends the operation: everything that operation
started is rolled back, and everything after it in the start order is never attempted. On a first
`up` of a five-container project, a failure in the last one leaves the whole project down, including
containers that have nothing to do with it. Once a container is ready, the supervisor is narrower:
it takes that container's transitive dependents down and leaves the rest alone.

So a `mailer` that nothing depends on would end the whole start if it failed during `up`, and be
contained if it failed a minute later. The same declaration, the same container, two blast radii
separated only by timing.

Each rule is useful for a different project. Compose therefore makes the start-time choice part of
the file instead of assuming that every container has the same blast radius.

### Saying it in the file

A container is not required by default. Its failed start is reported against that container, nothing
is rolled back, and the operation carries on. Set `required: true` when one container must make the
operation fail:

```yaml
containers:
  database:
    worker: path://./workers/database
    required: true
```

Use `required_default` to set the fallback for every container in a file. A container-level value
always wins:

```yaml
required_default: true

containers:
  queue:
    worker: path://./workers/queue
    required: false
  state:
    worker: path://./workers/state
```

Here, `state` inherits `true`, while `queue` remains false. When neither `required` nor
`required_default` is present, the effective value is false.

Dependents of a non-required container carry on too. A container that names it in `start_after`
starts as if it had come up, because `start_after` is a start order rather than a claim that the
dependent cannot run without it. A dependent that genuinely cannot run without it says so by failing
on its own.

That moves what `status: ok` means. It used to say every planned container is up; it now says every
required one is, so the return names the rest in `not_required_failures` rather than leaving a
caller to compare the plan against a later status call. A successful result has no top-level error.

`required` controls the result after Compose finishes trying. A second field controls whether
Compose retries before it accepts that result.

### Retry policy

A container declares what Compose does when its first start fails or when it exits after it was
ready:

```yaml
containers:
  api:
    worker: path://./workers/api
    restart: on-failure
```

`no` is the default. A failed first start settles immediately, and an exit after `Ready` takes the
container's transitive dependents down. `on-failure` retries a failed start or a non-zero run-time
exit. A clean run-time exit with `on-failure` is recorded as `stopped`. `always` retries a clean
run-time exit, which is the answer for a worker that is only correct while it is running.

A supervised restart is the same act as `compose::restart`: one container stops and starts, and the
graph around it is left alone. So its dependents stay up while it is gone. This is the same
reasoning that non-required starts use: `start_after` is a start order rather than a claim that the
dependent cannot run without it. What that costs is a dependent holding a connection that drops and
has to reconnect, which is the cost the file asked for by declaring a policy at all. The one
operator restart that reaches further is `compose::restart` of the sandbox adapter, which also
restarts the VM workers it hosts, because they end with it. When the adapter crashes and its own
policy restarts it, its VM workers exit with it and each one follows its own policy: a VM worker
with no policy ends `failed`.

Replacement attempts are capped at five. The first retry is immediate. Later retries wait from 500ms
up to a ceiling of 30 seconds. Both limits are load-bearing: a policy with no backoff turns a crash
loop into a busy loop, and a policy with no cap never lets the operator find out. A container that
holds ready for a minute has recovered, so its run-time budget refills. A worker that crashes once
an hour is therefore restarted every time, rather than five times ever.

When the budget runs out the supervisor does what it would have done with no policy at all. It fails
the container, takes its dependents down, and says which in the log. That is the shape worth
keeping: `restart` changes how many times compose tries, and never what happens when trying is over.

`compose::status` reports a container waiting on a run-time replacement as `restarting`. It is not
`ready`, because nothing is running under that name, and not `failed`, because the supervisor has
not given up on it. It has no PID until the next process starts. During `up`, the active progress
row shows the retry attempt, its wait, and the successful recovery.

## Updating packages

`compose::update worker=state` resolves the selector already in the compose file. A tag such as
`next`, a range, and an exact version all stay unchanged in the file; `worker=state@<selector>`
changes the selector, for example `worker=state@latest` moves an exact version to the registry's
latest channel.

Update resolves the complete dependency graph. It adds new dependencies, updates changed
dependencies, and removes stale dependencies that Compose generated and no remaining package root
uses. Manually declared workers are not removed.

Compose downloads and verifies the new artifact before it changes the lock or stops a worker. A
failed resolve or download leaves the prior lock and running workers unchanged. If the resolved
artifact and default configuration did not change, Compose updates lock metadata when needed and
does not restart the project.

If all selected workers already use the requested versions, the operation leaves the file and
running processes unchanged, unless an earlier add or update left a rebuild unfinished. See
[Rebuilds](#rebuilds). A project with only `path://` workers also stays unchanged.

An update that changes the package of a container with a non-empty `scripts.build` rebuilds it
before restarting it. See [Rebuilds](#rebuilds).

The container that runs the sandbox adapter (`sandbox-libkrun`, or the one `engine.sandbox.adapter`
names) moves only to the newest release in `^0.5`, the releases that implement sandbox contract 1.4
with `worker.build`, `worker.binary`, and `worker.prune`.

## VM workers

A VM worker's build and run are two calls that Compose starts like any other command.
`scripts.build` (`iii call sandbox::build`) runs in the sandbox adapter and leaves an image in the
project. `scripts.run` (`iii call sandbox::start`) boots that image and installs nothing at boot.
The run lasts as long as the VM: when the call ends, the VM stops, and when the VM stops, the call
ends. Compose hands both calls the rest of each request in `III_CALL_DEFAULTS`, and the sandbox
adapter is a container like any other, reached through `start_after`. Moving a worker between a VM,
the host, and Docker is therefore an edit of `scripts`. For the rules and the files involved, see
[Reference / VM workers](../reference/vm-workers).

### The flow

1. `iii call compose::add worker=onboarding` resolves the package, writes the container with
   `start_after` and `scripts`, and reconciles.
2. A container whose `scripts.build` has no `.iii/build/<container>/build.json` yet gets its first
   build when it starts, then runs.
3. `scripts.run` starts the worker. For a VM container, `iii call sandbox::start` boots
   `.iii/build/<container>/image.erofs` and stays with the VM.
4. A restart, or an adapter restart, repeats `scripts.run` only.
5. A rebuild is explicit (`iii call compose::build worker=<container>`), followed by a restart of
   that container. `compose::update` of a package rebuilds it.
6. `compose::remove` stops the container, has the adapter destroy the VM's runtime state while it
   keeps the data disk (`prune=true` deletes that too), and deletes `.iii/build/<container>/` and
   `.iii/workers/<container>/`.

### The first build

A container gets its first build when it starts, after its `start_after` containers are ready, if
`scripts.build` is set and non-empty and `.iii/build/<container>/build.json` is missing. This covers
`compose::add`, `up`, and a migrated container.

A `build.json` of the other kind than `scripts.build` makes is rebuilt the same way: a host build
where `scripts.build` is now `iii call sandbox::build`, or an image where it is now a host command.
Only the kind is compared, not the command's text. The log line names the change, for example
`<container>: its build is a host build, and scripts.build now builds a VM image; rebuilding`.

- The build runs within `scripts.build_timeout`. The container's `startup_timeout` then starts for
  the run.
- The container's logs show `<container>: no build yet; running scripts.build`, then the build
  output.
- `compose::add` and `compose::up` report the build as a progress step of the container
  (`building`). Their operation finishes after the run started or failed.
- A failed build fails the container with `BUILD_FAILED`, carrying `{ code, message }` as
  [`scripts.build`](../using-iii/compose#scriptsbuild) defines them. Nothing is rolled back, as for any failed start.

### Rebuilds

A rebuild is explicit: `iii call compose::build worker=<container>`, then a restart of that
container, since the running container keeps its current image until it restarts. See
[Using iii / Compose](../using-iii/compose#rebuild-a-vm-worker) for the commands.

`compose::add` or `compose::update` that changes a container's package (`source` in `build.json` no
longer matches the lock) rebuilds it before restarting it, and logs
`<container>: package changed (<old> -> <new>); rebuilding`. The container keeps running on its old
build while the new one builds, so the restart that follows only runs the new build.

- **A failed rebuild** keeps the container running on its old build, and Compose does not restart
  it. The operation fails with `BUILD_FAILED`. The file and the lock already name the new version:
  retry the add or update, or run `iii call compose::build worker=<container>` and, once it built,
  `iii call compose::restart worker=<container>`, to finish it.
- **A retried add or update** finishes what an earlier one left: it rebuilds a container still on
  the build of its old package, and restarts one it rebuilt but did not restart.
- **An explicit build**, from `compose::build`, does not make a later add, or a retried add or
  update, restart its container: that restart is yours. An update that changes a
  package still restarts the whole project, this container included.
- **A cancel** of the add or update (`compose::cancel`) builds nothing more and restarts nothing. It
  fails with `OPERATION_CANCELLED` and, when it already rebuilt some, the message lists them
  (`rebuilt and not yet restarted: <container>`). Retry the add or update to restart them.
- **A VM whose adapter restarts** in the same operation cannot stay on its old build: it ends with
  the adapter, starts again, and builds then.

### Builds that are out of date

Before `scripts.run` (on `up`, a restart, or a crash replacement), Compose compares the container's
current inputs with `build.json`: `source`, `dependency_files`, and `image.base_image.declared`. A
container without `build.json` is not checked. A difference in `dependency_files` or
`base_image.declared` only logs, once per start, one line per kind of change:

```text
link: dependencies changed since the last build (package.json); run `iii call compose::build worker=link`
link: base image changed since the last build (docker.io/iiidev/node -> docker.io/iiidev/python); run `iii call compose::build worker=link`
```

When one side declares no `runtime.base_image`, the line names `the adapter's default` for it. The
container then runs on its current build. A change of `source` is a package update and rebuilds (see
[Rebuilds](#rebuilds)). A change of code alone, outside the dependency files, is not a change: a
`path://` worker's code keeps syncing live into the guest.

### What the guest sees

- **Data.** The VM's data disk is persistent and independent of the build. It keeps whatever the
  worker writes (its home, databases, caches, and the files it writes in `/workspace`) across
  restarts, rebuilds, and a `compose::remove` without `prune`. Only `compose::remove prune=true`
  resets it. It stays adapter-owned under
  `~/.iii/sandbox/workers/<vm_id>/`.
- **Root filesystem.** The guest's root is the build image, read-only, with the data disk on top. A
  file the worker modified inside a directory the build also writes, for example under
  `node_modules`, keeps the worker's copy after a rebuild. `compose::remove prune=true` clears it.
- **Code.** A bundle's code is in the image, and so is a binary's Linux build. Its
  `.iii/workers/<container>/` is the build's input only. A `path://` worker's code keeps syncing
  live into `/workspace`. One list of names decides what a run neither copies nor syncs, including
  for `path://.`: the adapter's ignore list plus `.iii`, which also keeps Compose's `.iii/build/`
  and `.iii/workers/` out. The list holds dependency, cache, build-output, VCS, and editor
  directories, such as `node_modules`, `.venv`, `vendor`, `target`, `dist`, and `.git`.
  `sandbox-libkrun` 0.4 and later also skip directories named `.build` and `.workers`, at any depth,
  so a worker's own directory of either name stays on the host.
  - `build`, `out`, `obj`, `coverage`, and `deps` match only a directory at the worker's root:
    projects also keep source under these names deeper down. Every other name, `target` and `dist`
    included, matches at any depth.
  - The build's input copy uses the same list except `vendor`, which goes into the build: Go keeps
    vendored source there.
- **Boot cleanup.** A boot never deletes what the build installed or what the worker wrote in
  `/workspace`. Each copy records what it extracted in a manifest on the data disk, outside
  `/workspace`, and the next boot removes only the entries the host no longer has. The cleanup
  never removes through a symlink, never touches a name the copy leaves out (a run keeps the
  build's `vendor/` until the next build), and skips names with a newline or a backslash. A disk
  that an older adapter wrote has no manifest: its first boot skips the cleanup and logs it.
- **Dependencies.** They come from the build. To add one, edit `package.json`, run
  `iii call compose::build worker=<container>`, and restart the container.
- **Environment.** The guest gets the container's `environment` and `env_file` variables and the
  reserved `III_*` variables, except `III_CALL_DEFAULTS` and the build and package variables of
  [The worker environment](../using-iii/compose#the-worker-environment). It never gets the host's environment. The
  build VM gets the same set.

### How `compose::build` runs

- It is asynchronous. It answers `{ operation_id, status: "accepted", requested }`, holds the
  project's mutation lock while it runs, and reports progress per container (`building`, `built`,
  `failed`) through `compose::on-operation-progress`.
- A container whose `scripts.build` is `""` is reported as `skipped`, named or not.
- It starts the adapter first when the project is down, as `compose::remove` does.
- It never restarts a container. A running container keeps its current build until it restarts.
- `compose::cancel` of the operation and `compose::down` stop it, and `compose::remove` stops the
  build of the containers it removes. Compose stops the `iii call sandbox::build` processes, which
  aborts their builds. `down` cancels a running `compose::build` first, then takes the lock.

### Removing a VM worker

Compose first stops a build of that container that is still running, from `compose::build` or a
first build. Until the remove ends, a start or rebuild of that container gives up. Removing a
container also deletes its `.iii/build/<container>/` and `.iii/workers/<container>/` directories.
For a VM worker, Compose has the sandbox adapter destroy the VM's runtime state and keep its data:
the data disk. The log says where the data stayed. Add
`prune=true` to delete the data too. Keeping the data needs an adapter with `worker.prune`; with an
older one, Compose leaves the VM's state where it is and says so.

The kept data belongs to the container key. A container added again under the same key, with any
package, boots on that data disk, and files the old worker wrote where the new build also writes
hide the image's. To discard the data, remove the container with `prune=true` in the first place,
add it again and remove it with `prune=true`, or delete the VM directory containing the printed
paths while no VM of that container runs. For example, a kept path
`/srv/adapter/.iii/sandbox/workers/<vm_id>/upper.ext4` is a file: delete its parent
`/srv/adapter/.iii/sandbox/workers/<vm_id>/`, including the seal and pre-build copies. Use the
adapter's reported paths, not the client's HOME; the adapter may be on another host.

### Restarting the sandbox adapter

A VM worker ends with the adapter that hosts it, so restarting the adapter restarts its VM workers
too.
`compose::restart worker=sandbox-libkrun` restarts the adapter and then each VM worker it was
running, dependencies first, without spending any of their `restart` attempts. The response names
those workers in `affected_workers`. A `required` VM worker that does not come back fails the
operation. Otherwise, one that does not come back is listed in `not_required_failures`. If the
adapter itself does not come back, no VM worker is started and those same rules apply to each one it
was running, which `compose::status` then reports as `failed`, with a `last_error` that names the
adapter. Once the adapter is fixed, `compose::up` starts them all again. A sandbox that was running
under the adapter does not come back.
