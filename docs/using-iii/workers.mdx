Workers connect to iii over WebSocket and register functions and trigger types. The descriptor-native
runtime has two explicit entry points:

- `iii worker add <registry-ref>` installs an immutable Registry package.
- `iii compose` runs local catalog workers and Registry packages declared by a root
  `worker-compose.yaml`.

## Registry-managed workers

```bash
iii worker add state@next
iii worker list
iii worker status state
iii worker logs state --follow
iii worker sync --frozen
```

The lock stores the exact `package_descriptor`, descriptor digest, version, and artifacts. Bundles
start from the descriptor sidecar; OCI workers start the digest-pinned image in the lock. No bundle
contains or reads project metadata.

## Local workers with Compose

Run `iii worker init my-worker` to create a root `worker-compose.yaml`, or add a strict
`workers.<slug>` definition yourself. Reference that definition from a stack with
`catalog://<slug>`:

```yaml
stacks:
  default:
    namespace: dev
    containers:
      my-worker:
        worker: catalog://my-worker
```

Stacks contain only `namespace` and `containers`; containers contain `worker`, optional
`start_after`, and optional `config`. Build/runtime/toolchain fields belong to the worker's compiled
PackageDescriptor and cannot be overridden by a stack.

```bash
iii compose validate --file worker-compose.yaml --stack default
iii compose --up --file worker-compose.yaml
```

See [Worker Registry](./workers-registry) for package installs and
[Package Descriptor](../creating-workers/worker-manifest) for the compiler-owned contract.
