SDK 0.27 · Streams

Streams now go right in the payload.

Before, you created a channel, wired the file into it, and passed the ref along. In 0.27 you put the file in the payload, and the handler gets an InputStream to read. The engine stays the same.

bytes
  • no createChannel
  • the SDK handles the ref
  • still a plain call
  • returning closes the stream

How it works

Three new things.

The side that gets the stream reads from an InputStream or writes to an OutputStream. Creating the pipe, swapping the file for a ref, and closing it at the end are up to the SDK.

InputStream

The side that reads.

Your handler gets one when the caller puts a file, a Readable, or a generator in the payload.

How to read

In chunks (for await), all at once (bytes(), text()), by line (lines()), or by JSON message (messages()). To hand it to a native API: toReadable() or toWebStream().

A stream has one reader. For two copies, call tee() before reading.

OutputStream

The side that writes.

Your handler gets one when the caller passes a destination: a Writable, a file to create.

How to write

write(bytes) for bytes, send(value) for a JSON message, close() to finish, abort(reason) to fail.

The receiving side doesn't have to close it: returning closes, throwing aborts. To keep writing after you answer, use keepOpen().

pipe()

When you want both ends.

Handy when the stream has to exist before the data, or to get progress messages while the call runs.

Details

Put the end the other side uses in the payload and keep the other one. Whoever calls pipe() owns the pipe and has to stay connected until the other side connects to its end.

The engine holds up to 64 frames between the ends. In TypeScript and the browser, pipe({ bufferSize }) changes that (up to 1024).

Rust

    FAQ

    Before you ask.

    I put together the questions that tend to come up next, each with a small example to play with. The examples are in TypeScript; the other SDKs work the same way.

    Why not send everything as JSON?

    A call is a JSON message: it has a 64 MiB limit, has to be complete before it leaves, and sits whole in the receiver's memory. With a stream, the call carries only a small ref; the bytes go through the pipe.

    Details

    The limit applies to the whole JSON envelope, measured in UTF-8 bytes. The Node, Python, Rust, and Go SDKs go up to 64 MiB; the browser SDK sends and receives up to 16 MiB. Above that, the call fails with payload_too_large.

    A stream carries the bytes outside the envelope, so only the ref counts toward the limit.

    Do I still need to create a channel before the call?

    No. createChannel, readerRef, and writerRef are gone. Put the stream straight in the payload.

    Details

    It's a breaking change, with no legacy aliases, in all five SDKs. Only workers that upgrade the SDK have to migrate, and only the code that uses channels. The engine doesn't change.

    The field name stays the same: it's your function's contract. The step-by-step guide is in Upgrading from 0.26.x.

    What becomes a stream and what stays JSON?

    The SDK only turns into a stream what it recognizes as a source (becomes an InputStream) or a destination (becomes an OutputStream). Strings, buffers, objects, and arrays stay JSON. Tap the values:

    Details

    A call can carry as many streams as you want, in any field. The SDK creates the pipes in parallel before sending the call; if a pipe can't be created, the call fails before it leaves.

    Rust and Go don't detect anything: the payload is a serde value (Rust) or JSON you build (Go). Use the constructors: InputStream::from_reader, iii.InputStreamFromReader, iii.OutputStreamToWriter.

    How do I read an InputStream?

    Once, whichever way makes sense. This stream has four frames: three of bytes and one JSON message. See what each way of reading gives you:

    Details

    A stream carries two kinds of frame, in a single order: bytes (you write them with write) and messages (you send them with send). Reading bytes skips the messages, messages() skips the bytes, and frames() gives you both.

    Leaving the loop before the end cancels the stream. cancel() does the same, on purpose.

    Do I need to close the stream?

    In the common case, no. When the handler finishes, the SDK closes, aborts, or cancels the streams it received. Build the case:

    Details

    To answer right away and keep writing, call keepOpen() and close (or abort) it yourself:

    A received InputStream doesn't stay open after the return: finish reading first. A read that is still running fails with STREAM_CLOSED.

    Exception: in a call that goes through an observer (like the HTTP worker calling a route), an OutputStream the handler didn't use is only closed if the handler returns nothing. The HTTP worker reads an untouched response with a result as a buffered response.

    What if something fails mid-transfer?

    The reader gets what already arrived and then a STREAM_ABORTED error. A cut stream never looks complete.

    Details

    A stream aborts when the source the SDK pumps fails, when a handler throws after using an OutputStream, when someone calls abort(reason), or when the writing worker goes down.

    The engine doesn't pass along the writer's reason: the reader sees the engine's own text. To say why, fail the call or put the cause in the result.

    Does a slow reader fill up memory?

    No. write only resolves when the chunk is accepted, so a slow reader slows the writer down. Change the reader's speed:

    Details

    The engine holds up to 64 frames between the ends (8 squares here, to fit the screen). With pipe({ bufferSize }) you change that, up to 1024.

    Exception: in the browser, reading has no backpressure, because a page can't pause the socket. Read as it arrives, or cancel.

    Can I read the same stream twice?

    No: a stream has a single reader. The second read fails with STREAM_IN_USE. For two copies, call tee() before the first read.

    Details

    The tee() copies share a small buffer (16 frames): read both at the same time. Reading one to the end before starting the other one hangs.

    tee() exists in TypeScript, the browser, and Python. In Go, read once and copy with io.TeeReader or io.MultiWriter.

    Can I pass a stream to another function without reading it?

    Yes. An InputStream nobody has read travels as a ref: the bytes go straight to the destination, without passing through the worker in the middle.

    Details

    Forwarding doesn't change the pipe's owner. An OutputStream the handler didn't use is also forwarded as a ref. A stream that was already read, or that the handler created itself, is pumped by the forwarding worker.

    When do I use pipe() instead of a destination?

    With a destination, the call waits for the file to be complete. With pipe(), it resolves when the handler returns, and the messages come through.

    Details

    Use pipe() when the stream has to exist before the data, when it goes to a call made later, or for a two-way conversation (two pipes).

    A destination only gets bytes: messages (send) are dropped. If the handler fails before writing to a pipe's output, the reader waits until the end expires; observe the call too.

    Does it work with a queue (Enqueue)?

    No. A stream needs a live call: the queue job can run after the pipe has expired, and a retry can't read the stream again.

    Can an observer read the stream?

    No. In place of the stream, it gets a StreamInfo: { stream: true, direction, id }. That way an observer never steals the bytes from the function it observes.

    Details

    The other fields arrive as usual and filters keep working. A function called through an observer (like the route the HTTP worker calls with request_body and response) gets live streams.

    Note: on the wire, the ref with the access key is still in the observed payload. A target on a 0.26 SDK gets that ref; don't open it, or you take the stream away from the observed function.

    What about the browser?

    Same API, with Web streams. A File from an <input type="file"> goes straight in the payload. Pick a file (nothing leaves this page):

    Details

    Sources: ReadableStream, Blob and File, async generators, and InputStream. Destinations: WritableStream and OutputStream. The native bridge is toWebStream().

    The browser aborts with code 4011 (it can't send 1011); the engine treats it as an abort. write resolves while the socket has up to 1 MiB pending. Reading has no backpressure. JSON messages go up to 16 MiB.

    Do I need to upgrade the engine? What about workers that stay on 0.26?

    The engine doesn't need to change: a 0.26 engine serves 0.27 SDKs. The ref is the same JSON in every SDK, so 0.26 and 0.27 workers talk to each other in the same project. See what each one gets:

    Details

    Only the worker whose SDK you upgrade has to migrate, and in it only the channel code. You can migrate one worker at a time.

    The 0.27 closing rules apply only on the 0.27 side. A 0.26 handler that gets a writer still has to close it, and a 0.27 caller that passed a destination waits until that happens.
